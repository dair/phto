# 0011 — Archive File Support (ZIP, tar.gz, tar.bz2)

## Goal

Add support for looking inside archive files (`.zip`, `.tar.gz`, `.tar.bz2`) and processing all supported image/video files found within them. Each file extracted from an archive is validated, hashed, and stored individually through the existing `addImage` pipeline. The source path of each extracted file encodes both the archive's location and the entry's path within it, e.g. `photos/vacation.zip/DCIM/IMG_1234.JPG`.

Nested archives (an archive inside another archive) are explicitly deferred to a second phase.

## Background

### Why archive support?

Users commonly receive or back up photos in archive form — a friend sends `wedding-photos.zip`, a camera dump arrives as a tarball, or cloud exports produce `.tar.gz` bundles. Currently, the user must manually extract these before feeding individual files to `imagestore`. Archive support eliminates this manual step.

### What archives contain

In practice, photo/video archives contain:
- Supported media files (`.jpg`, `.jpeg`, `.png`, `.heic`, `.heif`, `.nef`, `.mov`, `.mp4`)
- Sidecar files (`.aae` — see plan 0010)
- Unsupported files (`.txt`, `.html`, `.ds_store`, nested directories, metadata files)
- Potentially other archives (`.zip` inside `.tar.gz` — deferred to phase 2)

The system should silently skip unsupported files within an archive and process only those with extensions matching registered validators.

### Current behavior

Archive files passed to `imagestore` are read into a Blob and sent to `addImage`, which returns `UnsupportedFormat` since no validator is registered for `.zip`, `.tar.gz`, or `.tar.bz2`. The archive is skipped and (if `--errors` is set) recorded as an error.

### Library choice: libarchive

**libarchive** is the standard C library for reading archives across formats. A single API handles ZIP, tar, tar+gzip, tar+bzip2, tar+xz, and many more. It is:
- Available on all major Linux distributions (`libarchive-dev`)
- Stream-oriented — entries can be read sequentially without extracting the full archive to disk
- Well-maintained and widely used (used by `bsdtar`, `cmake`, `pkg`)
- C API with stable ABI

libarchive provides `archive_read_open_memory()` which operates on an in-memory buffer — fitting the existing Blob-based pipeline. For large archives that exceed reasonable memory limits, it also supports `archive_read_open_filename()` for file-based reading.

## Supported extensions

| Extension | Format | Notes |
|-----------|--------|-------|
| `.zip` | ZIP archive | Most common for photo sharing |
| `.tar.gz`, `.tgz` | tar + gzip | Common on Unix/macOS |
| `.tar.bz2`, `.tbz2`, `.tbz` | tar + bzip2 | Less common, higher compression |

libarchive auto-detects compression and container format, so a single code path handles all variants. The extension is used only to decide whether to treat a file as an archive.

## Design overview

### Architecture decision: imagestore-level, not library-level

Archive handling is an **input source concern**, not a storage concern. The core library (`libimager`) stores individual files — it has no reason to know about archives. The processing belongs in the `imagestore` batch utility and a supporting `archive` module.

The layering is:

```
imagestore (batch CLI)
  ├── reads paths from stdin
  ├── detects archive extensions
  ├── for regular files: read → Blob → addImage (existing flow)
  └── for archives: open → iterate entries → extract each → Blob → addImage
          │
          ├── archive/ module (new): ArchiveReader class
          │     wraps libarchive, provides entry iteration
          └── imager/ (unchanged): addImage processes individual files
```

### Virtual source paths

Each file extracted from an archive is passed to `addImage` with a virtual path that encodes its provenance:

```
<path-to-archive>/<archive-filename>/<entry-path-inside-archive>
```

Examples:
- Input path: `/photos/vacation.zip`, archive entry: `DCIM/IMG_1234.JPG`
  - Virtual path passed to addImage: `/photos/vacation.zip/DCIM/IMG_1234.JPG`
- Input path: `backup.tar.gz`, archive entry: `photos/IMG_5678.HEIC`
  - Virtual path passed to addImage: `backup.tar.gz/photos/IMG_5678.HEIC`

This virtual path serves two purposes:
1. **Sidecar pairing** (plan 0010): the `source_dir` component extracted from the virtual path ensures that sidecars pair correctly within their archive context. `vacation.zip/DCIM/IMG_1234.AAE` pairs with `vacation.zip/DCIM/IMG_1234.JPG`, not with an `IMG_1234.JPG` from a different archive or filesystem location.
2. **Provenance tracking**: the original location of each file is preserved for debugging and the error file.

### Temporary file strategy

libarchive can read entries directly into memory, so for most files **no temporary files are needed**. The entry data is read into a `Blob` and passed directly to `addImage`.

However, for extremely large entries (video files exceeding available memory), a fallback path extracts to a temporary file:

- Temporary directory: `/tmp/imager-<PID>/` (created on first use, cleaned up on exit)
- Files are written to `/tmp/imager-<PID>/<random-suffix>.<ext>` and deleted immediately after processing
- The PID in the directory name ensures uniqueness across concurrent `imagestore` instances
- Cleanup is performed both on normal exit and via an `atexit` handler to handle crashes

In practice, the in-memory path will handle the vast majority of files. The temp fallback exists only for multi-GB video files inside archives, and even those typically fit in memory on modern systems.

### Entry filtering

Not every file in an archive should be processed. The filtering logic:

1. Skip directories (entry type is directory)
2. Skip entries with no extension
3. Extract the extension and lowercase it
4. Check if any registered validator supports this extension (reuse the same extension list from `Imager`)
5. If no validator matches, skip silently (not an error)
6. If validator matches, extract and process

This means `.DS_Store`, `Thumbs.db`, `.txt`, `.html` and other non-media files are silently ignored.

### Handling of archive-level errors

| Condition | Behavior |
|-----------|----------|
| Archive cannot be opened (corrupt header) | Report as error for the archive path, skip entirely |
| Individual entry is corrupt/truncated | Report as error for the virtual path, continue to next entry |
| Entry fails validation (BrokenFile) | Report as error for the virtual path, continue to next entry |
| Entry is a duplicate | Report as duplicate (normal DuplicateFile handling), continue |
| I/O error reading entry | Report as error for the virtual path, continue |

The archive itself is never stored — only its individual media files are stored. A fully-processed archive (all entries either stored or skipped) is considered successful even if some entries were unsupported.

### Public interface

```cpp
// archive/ArchiveReader.h
#pragma once

#include <cstddef>
#include <cstdint>
#include <functional>
#include <string>
#include <vector>

namespace archive {

/// Information about a single entry within an archive.
struct ArchiveEntry {
    std::string path;       // Full path within the archive (e.g., "DCIM/IMG_1234.JPG")
    std::string filename;   // Bare filename (e.g., "IMG_1234.JPG")
    std::string extension;  // Lowercase with dot (e.g., ".jpg")
    uint64_t size;          // Uncompressed size in bytes (0 if unknown)
    bool isDirectory;       // True if entry is a directory
};

/// Result of reading an archive entry's data.
struct EntryData {
    std::vector<uint8_t> data;  // Uncompressed file content
};

/// Callback invoked for each processable entry in an archive.
/// Return true to continue iteration, false to stop.
using EntryCallback = std::function<bool(const ArchiveEntry& entry, EntryData&& data)>;

/// Check if a file extension indicates an archive format.
/// Accepts lowercase extensions with leading dot.
bool isArchiveExtension(const std::string& ext);

/// Open an in-memory archive and iterate over its entries.
/// Calls `callback` for each non-directory entry.
/// Returns the number of entries yielded (excluding skipped directories).
/// Throws std::runtime_error on archive-level errors (corrupt, unreadable).
int readArchive(const uint8_t* data, size_t size, EntryCallback callback);

/// Open a file-based archive and iterate over its entries.
/// Same behavior as the memory-based overload but reads from disk.
/// Use this for archives too large to fit in memory.
int readArchive(const std::string& path, EntryCallback callback);

} // namespace archive
```

### Implementation notes

The `readArchive` implementation:

1. Create `archive*` handle via `archive_read_new()`
2. Enable all format support: `archive_read_support_format_all()`
3. Enable all compression support: `archive_read_support_filter_all()`
4. Open from memory: `archive_read_open_memory(a, data, size)`
5. Loop: `archive_read_next_header(a, &entry)` until `ARCHIVE_EOF`
6. For each entry:
   - Get path via `archive_entry_pathname(entry)`
   - Get size via `archive_entry_size(entry)`
   - Skip if `archive_entry_filetype(entry)` is directory
   - Read data via `archive_read_data(a, buf, size)` into `EntryData`
   - Invoke callback with `ArchiveEntry` + `EntryData`
7. Cleanup: `archive_read_free(a)`

RAII wrapper ensures cleanup even on exceptions.

### `isArchiveExtension` implementation

```cpp
bool isArchiveExtension(const std::string& ext) {
    // Simple extension check
    if (ext == ".zip") return true;
    if (ext == ".tgz") return true;
    if (ext == ".tbz2" || ext == ".tbz") return true;
    return false;
}
```

For compound extensions (`.tar.gz`, `.tar.bz2`), the check requires looking at the last two extension components. A helper `getCompoundExtension(filename)` extracts the compound extension:
- `"photos.tar.gz"` → `".tar.gz"`
- `"photos.tar.bz2"` → `".tar.bz2"`
- `"photos.zip"` → `".zip"`
- `"photos.jpg"` → `".jpg"`

This helper is also used in `imagestore` to detect archives before deciding how to process each input path.

## imagestore integration

### Modified processing flow

The main loop in `imagestore/main.cpp` currently:
1. Reads a path from stdin
2. Reads the file into a Blob
3. Calls `addImage(blob, filename)`

With archive support, the flow becomes:
1. Read a path from stdin
2. Detect if it's an archive (by extension)
3. **If not an archive**: existing flow (read → Blob → addImage)
4. **If archive**: open with `ArchiveReader`, iterate entries:
   a. For each entry with a supported extension:
      - Construct virtual path: `<archive-path>/<entry-path>`
      - Create Blob from entry data
      - Call `addImage(blob, virtualPath)`
      - Record result (OK / DUP / ERR) per-entry
   b. Skip unsupported entries silently

### Statistics changes

Archive processing reports per-entry statistics, not per-archive:
- Each media file extracted from an archive increments `processed`, `added`, `duplicates`, or `errors` as appropriate
- A new counter `archives` tracks total archives opened (for summary reporting)
- Verbose output shows the virtual path for each entry

### Error file interaction

- If an archive itself fails to open: record the archive path in the error file
- If an individual entry fails: record the virtual path (`archive.zip/path/to/entry.jpg`) in the error file
- On re-run, the skip check uses the virtual path, so successfully-processed entries from a partially-failed archive are skipped on retry
- The archive path itself is NOT added to the error file unless it completely fails to open — partial success is normal

### Concurrency

Each archive entry is processed sequentially within the archive (libarchive is stream-oriented — random access within archives is limited). However, multiple archives can be processed concurrently via the existing semaphore-based job system.

For archives with many entries, a refinement could dispatch each entry to the thread pool, but this is not needed for v1 — sequential processing within an archive is simpler and avoids holding the entire archive in memory while entries are in flight.

## Risk analysis

### Zip bombs / decompression bombs

A malicious archive could contain entries that decompress to enormous sizes (zip bomb). Mitigations:
- **Per-entry size limit**: if `archive_entry_size()` reports a size exceeding a configurable threshold (e.g., 4 GB), skip the entry with a warning
- **Total extracted size limit**: track cumulative extracted bytes per archive; abort if total exceeds a threshold (e.g., 50 GB)
- **Ratio check**: if the compression ratio (compressed/uncompressed) exceeds 100:1, flag as suspicious and skip
- These limits are conservative defaults that handle legitimate large video files while rejecting obvious bombs

### Memory pressure from large archives

An archive file itself might be very large (tens of GB). Two mitigations:
- **File-based reading**: `readArchive(path, callback)` reads from disk without loading the entire archive into memory. imagestore should use this path for large files (heuristic: if file size > 1 GB, use file-based path)
- **Sequential entry processing**: entries are processed one at a time, so only one entry's data is in memory at any time

### Compound extensions (.tar.gz, .tar.bz2)

Standard extension detection (substring after last `.`) yields `.gz` for `photos.tar.gz`, not `.tar.gz`. The `getCompoundExtension()` helper addresses this by checking the last two dots:
- If filename ends with `.tar.gz` → extension is `.tar.gz`
- If filename ends with `.tar.bz2` → extension is `.tar.bz2`
- Otherwise → standard last-dot extraction

This is applied in imagestore's archive detection logic, not in the core library.

### Symlinks within archives

Archives can contain symlinks that point outside the archive (path traversal). libarchive handles this safely — `archive_read_data()` reads the entry's actual data, not the symlink target. Symlink entries should be skipped (they are not regular files).

### Character encoding in entry paths

Archive entry paths may use different encodings (UTF-8, Shift-JIS, CP437 for old ZIPs). libarchive normalizes to the locale's encoding by default. For virtual path construction, the entry path is used as-is from libarchive. Non-UTF-8 characters in filenames may produce garbled virtual paths but will not cause processing failures.

### Interaction with plan 0010 (AAE sidecars)

Virtual paths from archives naturally work with the sidecar pairing mechanism from plan 0010. If an archive contains both `DCIM/IMG_1234.JPG` and `DCIM/IMG_1234.AAE`, and the archive is at `/photos/vacation.zip`, the virtual paths are:
- `/photos/vacation.zip/DCIM/IMG_1234.JPG`
- `/photos/vacation.zip/DCIM/IMG_1234.AAE`

The sidecar's `source_dir` becomes `/photos/vacation.zip/DCIM` and `base_name` becomes `img_1234`, correctly pairing within the archive context.

**Ordering note**: since archive entries are processed sequentially, the order within the archive matters for sidecar pairing. If the AAE comes before its parent JPG, it becomes an orphan and is resolved when the JPG arrives (plan 0010 Scenario B). This works correctly with no special handling.

## Comparison with existing patterns

| Aspect | Media validators (JPEG/HEIC/MOV) | Archive support (this plan) |
|--------|----------------------------------|----------------------------|
| Integration level | Core library (libimager) | Utility layer (imagestore + archive module) |
| Validation | Deep (decode pixels/frames) | Container only (can archive be opened?) |
| Storage | Individual file stored | Individual entries stored (archive not stored) |
| External dependency | Various per-format | libarchive (single library, all formats) |
| Blob lifecycle | Single file → single Blob → addImage | Archive → multiple Blobs → multiple addImage calls |
| Error granularity | Per-file | Per-archive (open failure) and per-entry (extraction/validation failure) |
