# 0007 — HEIC Image Format Support via libheif

## Goal

Add HEIC/HEIF image validation so that `.heic` and `.heif` files are accepted, validated, and stored like JPEG and PNG images are today. This is the first format that uses a **system-installed library** rather than a bundled one, establishing the pattern for future system-dependency validators.

## Background

HEIC (High Efficiency Image Container) is the default photo format on modern iPhones and iPads. It uses the HEIF container format (ISO/IEC 23008-12) with HEVC (H.265) compression. HEIF can also wrap other codecs (AV1 for AVIF, JPEG, VVC), but the `.heic` extension specifically implies HEVC-compressed content.

**libheif** (v1.21.2 on this host) is the reference open-source implementation. It provides a C API for reading HEIF/HEIC files from memory, parsing the container, and decoding the image content via codec plugins. The `libheif-dev` Debian package provides headers, CMake config files, and a shared library.

### Key differences from JPEG/PNG validators

| Aspect | JPEG / PNG | HEIC |
|--------|-----------|------|
| Library source | Bundled in `validations/*/lib*/src/` (readonly) | System-installed (`libheif-dev` package) |
| CMake integration | Built as internal static lib target | `find_package(libheif REQUIRED)` |
| Validation API | Custom C functions (`validateJpeg`/`validatePng`) | libheif C API: context + from-memory read + image handle |
| File extensions | `.jpg`, `.jpeg` / `.png` | `.heic`, `.heif` |
| Magic bytes | `FF D8` / `89 50 4E 47 ...` | ISOBMFF ftyp box (offset 4: `ftyp`, brand: `heic`, `heix`, `mif1`, etc.) |

## Supported extensions

| Extension | Meaning |
|-----------|---------|
| `.heic` | HEIF container with HEVC (H.265) compression — the standard iPhone photo format |
| `.heif` | Generic HEIF container — may use HEVC or other codecs; libheif handles both |

AVIF support (`.avif`) is deliberately out of scope for this plan. While libheif can also decode AVIF, it is a distinct format with its own conventions and should be its own validator if added later.

## Validation strategy

Validation must confirm that the data is a structurally valid HEIC/HEIF file that libheif can parse and that contains at least one decodable image. The approach mirrors the existing validators: attempt a full decode of the primary image to catch both container-level and codec-level corruption.

### Validation steps

1. **Quick rejection** — check minimum size (12 bytes) and verify ISOBMFF ftyp box signature at offset 4 (`ftyp` in ASCII: `0x66 0x74 0x79 0x70`). If absent, return `WRONG`.
2. **Container parse** — create a `heif_context`, call `heif_context_read_from_memory_without_copy()` to parse the HEIF container from the in-memory buffer. If this fails, return `INVALID`.
3. **Primary image handle** — call `heif_context_get_primary_image_handle()` to obtain a handle to the primary image. Failure means the container is valid ISOBMFF but contains no usable image — return `INVALID`.
4. **Full decode** — call `heif_decode_image()` on the primary handle to fully decode the image pixel data. This exercises the HEVC decoder plugin and catches codec-level corruption. Failure → `INVALID`.
5. **Cleanup** — release `heif_image`, `heif_image_handle`, and `heif_context` in reverse order. Return `VALID`.

Using `heif_context_read_from_memory_without_copy()` (not the deprecated `heif_context_read_from_memory()`) avoids an unnecessary copy of the input buffer, which matters for multi-megabyte iPhone photos. The caller must keep the buffer alive for the lifetime of the context, which is satisfied since the context is created and destroyed within the validation function.

### RAII considerations

The libheif C API uses manual resource management (`heif_context_alloc` / `heif_context_free`, `heif_image_handle_release`, `heif_image_release`). The validation function must ensure cleanup on all paths, including early returns. A simple approach is sequential cleanup with early returns (matching the existing PNG validator's `setjmp`-based cleanup pattern), since libheif reports errors via return codes rather than `setjmp`/`longjmp`.

### Error classification

| libheif error code | Validator result | Rationale |
|---|---|---|
| `heif_error_Ok` | `VALID` | File parsed and decoded successfully |
| `heif_error_Unsupported_filetype` | `WRONG` | Not a HEIF file at all |
| `heif_error_Invalid_input` | `INVALID` | HEIF container is corrupt |
| `heif_error_Unsupported_feature` | `INVALID` | Valid HEIF but uses a codec/feature this libheif build cannot handle |
| `heif_error_Decoder_plugin_error` | `INVALID` | Codec-level decode failure (corrupt image data) |
| All other errors | `INVALID` | Treat any unexpected error as invalid |

## Public interface

### `heic_validator.h`

```cpp
#pragma once

#include <cstddef>

enum ValidationResult {
  INVALID = -1, // the input is HEIC/HEIF data that is actually broken
  VALID = 0,    // the input is valid HEIC/HEIF data
  WRONG = 1,    // the input is not HEIC/HEIF data at all
};

ValidationResult validateHeic(const void* data, size_t dataSize);
```

This follows the exact same pattern as `jpeg_validator.h` and `validate_png.h`: a single free function returning the same `ValidationResult` enum. The enum is defined locally per TU to avoid cross-validator conflicts (the same strategy used by the existing validators).

## Facade integration

### `imager/src/HeicValidatorImpl.cpp` (new file)

A new translation unit implementing the `validation::IValidator` adapter, exactly mirroring `JpegValidatorImpl.cpp` and `PngValidatorImpl.cpp`:

```cpp
#include "Validators.h"
#include "heic_validator.h"

namespace {

class HeicValidator final: public validation::IValidator {
public:
  bool supportsExtension(const std::string& ext) const override {
    return ext == ".heic" || ext == ".heif";
  }

  validation::ValidationResult validate(const uint8_t* data, size_t size) const override {
    switch (validateHeic(data, size)) {
      case VALID:
        return {true, ""};
      case INVALID:
        return {false, "HEIC/HEIF data is corrupted or incomplete"};
      case WRONG:
        return {false, "Data is not a HEIC/HEIF file"};
    }
    return {false, "Unknown validation result"};
  }
};

} // namespace

namespace imager {

std::unique_ptr<validation::IValidator> createHeicValidator() {
  return std::make_unique<HeicValidator>();
}

} // namespace imager
```

## Validation implementation detail

### `heic_validator.cpp` pseudocode

```cpp
#include "heic_validator.h"
#include <libheif/heif.h>
#include <cstdint>
#include <cstring>

ValidationResult validateHeic(const void* data, size_t dataSize) {
    // Step 1: Quick rejection — check for ISOBMFF ftyp box
    if (!data || dataSize < 12) return WRONG;
    const auto* bytes = static_cast<const uint8_t*>(data);
    if (std::memcmp(bytes + 4, "ftyp", 4) != 0) return WRONG;

    // Step 2: Create context and parse from memory
    heif_context* ctx = heif_context_alloc();
    if (!ctx) return INVALID;

    heif_error err = heif_context_read_from_memory_without_copy(ctx, data, dataSize, nullptr);
    if (err.code != heif_error_Ok) {
        heif_context_free(ctx);
        return (err.code == heif_error_Unsupported_filetype) ? WRONG : INVALID;
    }

    // Step 3: Get primary image handle
    heif_image_handle* handle = nullptr;
    err = heif_context_get_primary_image_handle(ctx, &handle);
    if (err.code != heif_error_Ok) {
        heif_context_free(ctx);
        return INVALID;
    }

    // Step 4: Full decode of primary image
    heif_image* img = nullptr;
    err = heif_decode_image(handle, &img, heif_colorspace_RGB, heif_chroma_interleaved_RGB, nullptr);
    if (err.code != heif_error_Ok) {
        heif_image_handle_release(handle);
        heif_context_free(ctx);
        return INVALID;
    }

    // Step 5: Cleanup and return success
    heif_image_release(img);
    heif_image_handle_release(handle);
    heif_context_free(ctx);
    return VALID;
}
```

The full RGB decode (`heif_colorspace_RGB`, `heif_chroma_interleaved_RGB`) is intentional: it forces the HEVC decoder to actually decompress the image data, catching codec-level corruption that container-only parsing would miss. This matches the JPEG validator (which does a full scanline decode) and the PNG validator (which reads all rows).

### Test data

A minimal HEIC test file is needed. Options:
1. **Generate at build time** — use `heif-enc` (from `libheif-examples` package) to encode a 1x1 or 8x8 solid-color image from a raw PPM. This keeps the test self-contained but adds a build dependency.
2. **Embed as byte array** — include a small (~500 byte) pre-generated HEIC file as a `constexpr uint8_t[]` in the test source. This avoids external dependencies but makes the test data opaque.
3. **Ship a test fixture file** — place a minimal `.heic` file under `validations/heic/test/fixtures/`. This is the simplest approach and matches how one might test validators manually.

**Recommended**: option 3 (fixture file), with the file generated once by running `heif-enc` manually and committed to the repo. A single 8x8 solid-color HEIC file should be well under 1 KB. The truncated/corrupted variants can be derived from it programmatically in the test code (read the fixture, truncate or flip bytes).

## Risk: HEVC decoder availability

libheif is a container library — actual HEVC decoding requires a codec plugin. On Debian, the `libheif1` package depends on codec plugins, but the available HEVC decoder depends on the system configuration:

- **libde265** (LGPL) — the most common open-source HEVC decoder plugin for libheif
- **x265** — primarily an encoder, but can be used
- **ffmpeg** — if the ffmpeg plugin is available

If no HEVC decoder plugin is installed, `heif_context_read_from_memory_without_copy()` will succeed (container parsing doesn't need a codec), but `heif_decode_image()` will fail with `heif_error_Unsupported_feature` or `heif_error_Decoder_plugin_error`.

**Mitigation**: the validation function treats decode failure as `INVALID`, which is the correct user-facing behavior (the system cannot verify this file's integrity). The test suite should verify that `heif_have_decoder_for_format(heif_compression_HEVC)` returns true before running full-decode tests, and skip them otherwise with a clear message. The build system should document that `libde265-dev` (or equivalent) is needed at runtime.

## Comparison with existing bundled-library pattern

This is intentionally different from the JPEG and PNG validators. Those bundle their library sources to guarantee build reproducibility and avoid system dependency variance. HEIC uses a system library because:

1. **libheif is large and actively developed** — bundling it would mean maintaining a snapshot of a complex C++ library with its own plugin system
2. **Codec plugins** — libheif's value comes from its plugin architecture for loading HEVC/AV1/etc decoders; bundling just libheif without its plugin ecosystem would be useless
3. **Licensing** — HEVC decoding involves codec-specific licenses; using system packages lets the system administrator manage codec availability
4. **Precedent** — OpenSSL is already a system dependency; libheif follows the same model

This establishes a clean pattern: simple, self-contained libraries (libjpeg, libpng) are bundled; complex libraries with external dependencies (libheif, OpenSSL) use `find_package`.
