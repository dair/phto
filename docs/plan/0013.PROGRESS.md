# 0013 — Runtime Pipeline Progress Tracking

## Goal

Expose real-time progress visibility into the `addImage` pipeline so that consuming applications (e.g., `imagestore`) can display how many files have completed each processing stage, how many bytes have been processed, and how many files are currently in-flight at each stage. Additionally, introduce a new file-path-based entry point (`addFile`) that internalizes file reading, creating an observable read queue with its own progress counters.

All tracking is in-memory, lock-free, read-only for the library consumer — the application polls the existing `Metrics` object. No disk persistence, no new public types beyond what `Metrics` already provides.

## Background

### Current state

The `Metrics` class (plan 0005) already provides:

- **Histograms** for latency at each pipeline stage (validate, hash, storage_write, db_insert, etc.)
- **Counters** for throughput (`images_added`, `images_failed`, `storage_bytes_written`, `storage_bytes_read`)
- **Gauges** for resource usage (`pool_queue_depth`, `pool_active_threads`, `blobs_alive`, `blob_bytes_alive`)

What's missing:

1. **Per-stage cumulative counters**: how many files have *completed* each stage (read, validated, hashed, written, inserted). Currently only the final outcome is counted (`images_added`/`images_failed`).
2. **Per-stage cumulative byte counters**: how many bytes have been processed at each stage. `storage_bytes_written` exists but there's no equivalent for validation or hashing.
3. **Per-stage in-flight gauges**: how many files are *currently* at each stage. With multiple concurrent `addImage` calls (as `imagestore` does), these gauges reveal queue buildup and bottlenecks.
4. **File reading inside the library**: currently file I/O happens outside libimager (in `imagestore/main.cpp`). A library-level `addFile(path)` method would create an observable read stage.

### Pipeline stages

The `addImage` pipeline, as seen from concurrent callers:

```
[caller reads file]  ->  addImage:
                           1. validate  \  (parallel)
                           2. hash      /
                           3. mutex_wait
                           4. dedup_check
                           5. storage_write
                           6. db_insert
```

With the new `addFile` entry point:

```
addFile(path):
  0. read_file (new, inside library)
  1. validate  \  (parallel)
  2. hash      /
  3. mutex_wait
  4. dedup_check
  5. storage_write
  6. db_insert
```

Each numbered stage gets: a cumulative file counter, a cumulative byte counter, and an in-flight gauge.

## Design

### Part A — Per-stage counters and gauges on `addImage` (no flow changes)

Since `addImage` is synchronous and callers invoke it from many threads simultaneously, at any moment different threads are at different stages. We add gauges that increment on stage entry and decrement on stage exit, giving a live view of concurrency per stage.

#### New metrics added to `Metrics` class

**Cumulative file counters** (Counter) — increment when a file *completes* the stage:

| Name | Incremented after |
|------|-------------------|
| `stage_validated` | validation completes (success or failure) |
| `stage_hashed` | SHA256 computation completes |
| `stage_dedup_checked` | duplicate check completes |
| `stage_stored` | storage write completes (all roots) |
| `stage_db_inserted` | DB insert completes (all DBs) |

**Cumulative byte counters** (Counter) — total bytes that passed through each stage:

| Name | Incremented with |
|------|------------------|
| `stage_validated_bytes` | blob.size() after validation completes |
| `stage_hashed_bytes` | blob.size() after hash completes |
| `stage_stored_bytes` | already exists as `storage_bytes_written`, no new counter |
| `stage_db_inserted_bytes` | blob.size() after DB insert completes |

Note: `storage_bytes_written` already serves as the byte counter for the storage stage. `storage_bytes_read` already serves for reads. No duplication needed.

**In-flight gauges** (Gauge) — files and bytes currently *inside* each stage:

Each stage has two gauges: one for the number of files and one for the total bytes currently being processed at that stage. The byte gauge uses `add(blob.size())` on entry and `add(-blob.size())` on exit.

| Files gauge | Bytes gauge | Increment | Decrement |
|-------------|-------------|-----------|-----------|
| `inflight_validating` | `inflight_validating_bytes` | before validate coroutine | after validate completes |
| `inflight_hashing` | `inflight_hashing_bytes` | before hash coroutine | after hash completes |
| `inflight_waiting_mutex` | `inflight_waiting_mutex_bytes` | before `writeMutex.lock()` | after lock acquired |
| `inflight_dedup_checking` | `inflight_dedup_checking_bytes` | before `fileExists` | after it returns |
| `inflight_writing_storage` | `inflight_writing_storage_bytes` | before `writeFileAsync` | after it returns |
| `inflight_inserting_db` | `inflight_inserting_db_bytes` | before `dbs.addFile` | after it returns |

These gauges are updated using RAII guards to ensure correct decrement even on exceptions or early returns:

```cpp
struct GaugeGuard {
  Gauge& g;
  GaugeGuard(Gauge& g) : g(g) { g.increment(); }
  ~GaugeGuard() { g.decrement(); }
};

/// RAII guard for a paired file-count + byte-count gauge.
/// Increments both on construction, decrements both on destruction.
struct SizedGaugeGuard {
  Gauge& files;
  Gauge& bytes;
  int64_t size;
  SizedGaugeGuard(Gauge& f, Gauge& b, int64_t s) noexcept
    : files(f), bytes(b), size(s) { files.increment(); bytes.add(size); }
  ~SizedGaugeGuard() { files.decrement(); bytes.add(-size); }

  SizedGaugeGuard(const SizedGaugeGuard&) = delete;
  SizedGaugeGuard& operator=(const SizedGaugeGuard&) = delete;
};
```

#### Instrumentation in `Imager.cpp` — `addImage`

The instrumentation is added alongside the existing `Timer` measurements — same scope, minimal code:

```cpp
AddResult Imager::addImage(const Blob& blob, const std::string& filename) {
  metrics::Timer total(m_impl->metrics.addimage_total);

  // ... extension/validator checks ...

  const auto blobSize = static_cast<int64_t>(blob.size());

  if (validator) {
    // Parallel validate + hash — instrumentation inside coroutine lambdas:
    // validate lambda:
    {
      SizedGaugeGuard sg(m_impl->metrics.inflight_validating,
                         m_impl->metrics.inflight_validating_bytes, blobSize);
      metrics::Timer t(m_impl->metrics.validate);
      out = v->validate(b.data(), b.size());
    }
    m_impl->metrics.stage_validated.add(1);
    m_impl->metrics.stage_validated_bytes.add(blob.size());

    // hash lambda:
    {
      SizedGaugeGuard sg(m_impl->metrics.inflight_hashing,
                         m_impl->metrics.inflight_hashing_bytes, blobSize);
      metrics::Timer t(m_impl->metrics.hash);
      out = computeSha256(b);
    }
    m_impl->metrics.stage_hashed.add(1);
    m_impl->metrics.stage_hashed_bytes.add(blob.size());
  }

  // mutex wait:
  {
    SizedGaugeGuard sg(m_impl->metrics.inflight_waiting_mutex,
                       m_impl->metrics.inflight_waiting_mutex_bytes, blobSize);
    metrics::Timer t(m_impl->metrics.mutex_wait);
    m_impl->writeMutex.lock();
  }
  std::lock_guard lock(m_impl->writeMutex, std::adopt_lock);

  // dedup check:
  {
    SizedGaugeGuard sg(m_impl->metrics.inflight_dedup_checking,
                       m_impl->metrics.inflight_dedup_checking_bytes, blobSize);
    metrics::Timer t(m_impl->metrics.dedup_check);
    if (m_impl->dbs.fileExists(id)) { ... }
  }
  m_impl->metrics.stage_dedup_checked.add(1);

  // storage write:
  {
    SizedGaugeGuard sg(m_impl->metrics.inflight_writing_storage,
                       m_impl->metrics.inflight_writing_storage_bytes, blobSize);
    metrics::Timer t(m_impl->metrics.storage_write);
    coro::blockOn(m_impl->pool, m_impl->storage.writeFileAsync(id, ext, blob));
  }
  m_impl->metrics.stage_stored.add(1);
  // storage_bytes_written already incremented inside writeToRoot

  // db insert:
  {
    SizedGaugeGuard sg(m_impl->metrics.inflight_inserting_db,
                       m_impl->metrics.inflight_inserting_db_bytes, blobSize);
    metrics::Timer t(m_impl->metrics.db_insert);
    m_impl->dbs.addFile(id, bareName, blob.size(), ext);
  }
  m_impl->metrics.stage_db_inserted.add(1);
  m_impl->metrics.stage_db_inserted_bytes.add(blob.size());

  // ...
}
```

The validate and hash lambdas run as coroutines on the thread pool, so their gauges reflect true concurrency — if 8 files are hashing in parallel, `inflight_hashing` reads 8.

#### What these gauges reveal without changing the flow

With `imagestore --jobs 32` running 32 concurrent `addImage` calls:

```
inflight_validating:            4    (4 files being validated right now)
inflight_validating_bytes:   20 MB   (total size of those 4 files)
inflight_hashing:               5    (5 files being hashed)
inflight_hashing_bytes:      25 MB
inflight_waiting_mutex:        18    (18 files queued for the write mutex)  <- BOTTLENECK
inflight_waiting_mutex_bytes: 90 MB  (90 MB of data blocked on the mutex)
inflight_dedup_checking:        1
inflight_dedup_checking_bytes: 5 MB
inflight_writing_storage:       1
inflight_writing_storage_bytes: 5 MB
inflight_inserting_db:          1
inflight_inserting_db_bytes:   5 MB
```

This immediately shows the mutex is the serialization bottleneck — 18 of 32 in-flight files are blocked waiting for it, holding 90 MB of Blob memory. The byte gauges reveal memory pressure: if `inflight_waiting_mutex_bytes` is 500 MB, backpressure may be needed. The "queue" at each stage emerges naturally from the gauge values without any explicit queue data structure.

### Part B — `addFile` entry point with internal file reading

#### New method on `Imager`

```cpp
/// Read a file from disk and process it through the full addImage pipeline.
/// The file read happens inside the library, making it observable via metrics.
///
/// @param path     Absolute or relative path to the file on disk.
/// @param filename Display name for the file (used for extension detection
///                 and stored in the database). If empty, the path's
///                 filename component is used.
/// @return AddResult with the outcome.
AddResult addFile(const std::filesystem::path& path,
                  const std::string& filename = "");
```

#### Implementation

```cpp
AddResult Imager::addFile(const std::filesystem::path& path,
                          const std::string& filename) {
  std::string displayName = filename.empty()
    ? path.filename().string()
    : filename;

  // Stage 0: file read — tracked by metrics
  // Note: inflight_reading (file count) is incremented immediately.
  // inflight_reading_bytes is incremented after stat (once we know the size).
  Blob blob;
  {
    m_impl->metrics.inflight_reading.increment();

    std::error_code ec;
    auto fileSize = std::filesystem::file_size(path, ec);
    if (ec) {
      m_impl->metrics.inflight_reading.decrement();
      m_impl->metrics.images_failed.add(1);
      return {ErrorCode::FileNotFound, "",
              "Cannot stat: " + path.string() + ": " + ec.message()};
    }

    auto blobSz = static_cast<int64_t>(fileSize);
    m_impl->metrics.inflight_reading_bytes.add(blobSz);
    metrics::Timer t(m_impl->metrics.file_read);

    blob = Blob(fileSize);
    std::ifstream in(path, std::ios::binary);
    if (!in) {
      m_impl->metrics.inflight_reading.decrement();
      m_impl->metrics.inflight_reading_bytes.add(-blobSz);
      m_impl->metrics.images_failed.add(1);
      return {ErrorCode::FileNotFound, "",
              "Cannot open: " + path.string()};
    }
    if (fileSize > 0) {
      in.read(reinterpret_cast<char*>(blob.writableData()),
              static_cast<std::streamsize>(fileSize));
      if (in.fail() && !in.eof()) {
        m_impl->metrics.inflight_reading.decrement();
        m_impl->metrics.inflight_reading_bytes.add(-blobSz);
        m_impl->metrics.images_failed.add(1);
        return {ErrorCode::StorageError, "",
                "Read error: " + path.string()};
      }
    }
    blob.freeze();
    m_impl->metrics.inflight_reading.decrement();
    m_impl->metrics.inflight_reading_bytes.add(-blobSz);
  }
  m_impl->metrics.stage_read.add(1);
  m_impl->metrics.stage_read_bytes.add(blob.size());

  // Delegate to existing addImage
  return addImage(blob, displayName);
}
```

#### New metrics for the read stage

| Type | Name | Purpose |
|------|------|---------|
| Counter | `stage_read` | Files that completed disk read |
| Counter | `stage_read_bytes` | Total bytes read from disk via `addFile` |
| Gauge | `inflight_reading` | Files currently being read from disk |
| Gauge | `inflight_reading_bytes` | Bytes currently being read from disk |
| Histogram | `file_read` | Per-file read latency |

#### Impact on `imagestore`

`imagestore/main.cpp` currently does its own file reading (lines 291-319) and calls `addImage`. After this plan, it can optionally call `addFile(path)` instead, which:

1. Moves file reading inside the library, making it observable via metrics.
2. Simplifies `imagestore` — no more manual Blob construction.
3. Makes the read stage visible alongside all other stages in the metrics snapshot.

The `imagestore` change is optional — `addImage(blob, filename)` remains the primary API for callers that manage their own I/O. `addFile` is a convenience for the common "process a file from disk" case.

#### What the full pipeline looks like with `addFile`

```

inflight_reading:            3      inflight_reading_bytes:          15 MB
inflight_validating:         4      inflight_validating_bytes:       20 MB
inflight_hashing:            5      inflight_hashing_bytes:          25 MB
inflight_waiting_mutex:     15      inflight_waiting_mutex_bytes:    75 MB  <- memory pressure
inflight_dedup_checking:     1      inflight_dedup_checking_bytes:    5 MB
inflight_writing_storage:    2      inflight_writing_storage_bytes:  10 MB
inflight_inserting_db:       2      inflight_inserting_db_bytes:     10 MB

stage_read:          8421           stage_read_bytes:        42.1 GB
stage_validated:     8418           stage_validated_bytes:   42.1 GB
```

An application can compute queue depths from counter differences: `stage_read - stage_validated` = files that have been read but not yet validated. The byte gauges reveal memory pressure: 75 MB blocked on the mutex means 15 Blobs are alive just waiting their turn. Combined with the in-flight gauges, this gives a complete picture.

### GaugeGuard utility

A small RAII helper, placed in `metrics/Gauge.h` alongside the `Gauge` class:

```cpp
/// RAII guard: increments a Gauge on construction, decrements on destruction.
/// Ensures correct decrement even when exceptions unwind the stack.
struct GaugeGuard {
  Gauge& gauge;
  explicit GaugeGuard(Gauge& g) noexcept : gauge(g) { gauge.increment(); }
  ~GaugeGuard() { gauge.decrement(); }

  GaugeGuard(const GaugeGuard&) = delete;
  GaugeGuard& operator=(const GaugeGuard&) = delete;
};
```

No heap allocation, no virtual dispatch — a single `fetch_add(1)` on construction, `fetch_sub(1)` on destruction.

## Overhead analysis

| Operation | Cost per `addImage` call |
|-----------|--------------------------|
| 7 SizedGaugeGuard constructions | 7 x 2 `fetch_add` ~ 70 ns |
| 7 SizedGaugeGuard destructions | 7 x 2 `fetch_sub`/`fetch_add` ~ 70 ns |
| 5 stage file counter increments | 5 x `fetch_add(1)` ~ 25 ns |
| 5 stage byte counter increments | 5 x `fetch_add(size)` ~ 25 ns |
| **Total new overhead** | **~190 ns** |

Negligible compared to the ms-scale I/O in each stage. Combined with the existing ~360 ns from plan 0005, total instrumentation overhead is ~550 ns per `addImage` — still well under 1 microsecond.

## Future considerations (out of scope)

- **Batch `addFiles` method**: accept a vector of paths with bounded concurrency, return a vector of results. Would fully replace `imagestore`'s async loop.
- **Callback/observer interface**: let the caller register a progress callback instead of polling. Useful for GUI applications.
- **Per-format counters**: break down stage counters by file extension (e.g., "1200 JPEGs validated, 300 PNGs validated"). Would require a concurrent map instead of flat counters.
- **Rate computation**: expose files/sec and bytes/sec as derived metrics. Currently the caller must compute these from counter deltas over time.
