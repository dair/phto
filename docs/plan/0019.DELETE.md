# 0019 — File-Input Deletion in `libimager` and `imagestore`

## Revision Note

The prior draft of this plan proposed a separate `imagedelete` binary that accepted SHA256
**IDs** as input. That direction is **superseded**. The new requirement matches the
`imagestore` ingestion contract: callers give us a **file (path or bytes)**, we hash it
ourselves and delete whatever matches the resulting SHA256 — from all databases, all
storage roots, and all sidecars.

Rationale for the change:

- **Consistency with the existing tool.** `imagestore` already takes paths on stdin and
  runs them through `Imager::addFile`. A `--delete` mode that takes paths the same way is
  immediately intuitive; users do not need to learn a second input format.
- **Real workflow.** Operators typically have the source files at hand (camera card,
  export folder, "delete this batch I just noticed was garbage"), not their SHA256s. The
  ID-based CLI forced callers to run the file through a hasher first anyway.
- **One binary, one config, one progress pipeline.** Reusing `imagestore`'s stdin loop,
  bounded-concurrency semaphore, `SlotTracker`, `ResultLog`, and `ErrorFile` avoids
  duplicating ~500 lines of utility plumbing.

ID-based deletion remains reachable through the existing `Imager::deleteImage(id)` for
programmatic callers, and we keep the door open for a later `--by-id` mode on `imagestore`
if it turns out to be useful.

---

## Goal

1. Add two new public methods to `libimager` that accept a **file input** (path or blob),
   hash it **without validating**, and delete whatever matches:

   ```cpp
   imager::DeleteResult Imager::deleteBlob(const Blob& blob);
   imager::DeleteResult Imager::deleteFile(const std::filesystem::path& path,
                                           StageCallback onStage = nullptr);
   ```

2. Add a `--delete` / `-d` mode to `imagestore`: stdin becomes a list of file paths to
   *delete*, not to import. Concurrency, progress, error-file, quiet/verbose, and
   dry-run semantics carry over unchanged.

Out of scope: a separate `imagedelete` binary, bulk-delete-by-tag, HTTP API, interactive
confirmation.

---

## Library API Design

### New type: `DeleteResult`

`imager/types/DeleteResult.h`:

```cpp
#pragma once

#include <string>
#include "ErrorCode.h"

namespace imager {

struct DeleteResult {
  ErrorCode code{ErrorCode::Ok};
  std::string id;      ///< The SHA256 we computed (populated even when FileNotFound)
  std::string message; ///< Error detail on failure
};

} // namespace imager
```

Returning the computed id even on `FileNotFound` matters: the CLI layer wants to print
"MISS <id>" without re-hashing.

### New methods on `Imager`

Added to `imager/Imager.h` next to `deleteImage`:

```cpp
/// Compute SHA256 of `blob` (no validation, no extension check) and delete whatever
/// matches from all databases, all storage roots, and all sidecars.
/// Returns Ok + the computed id on success, FileNotFound + id if nothing matched,
/// DatabaseError / StorageError on failure.
DeleteResult deleteBlob(const Blob& blob);

/// Read `path` from disk, compute its SHA256 (streaming if over the size threshold),
/// and delete the matching record. No validation, no extension check.
/// The optional stage callback receives Reading -> Hashing -> WaitingMutex ->
/// DedupChecking (repurposed as "looking up id") -> (no WritingStorage/InsertingDb).
/// Returns Ok + id on success, FileNotFound + id if nothing matched.
DeleteResult deleteFile(const std::filesystem::path& path,
                        StageCallback onStage = nullptr);
```

Key properties:

- **No validation.** The file might be a broken JPEG, an unsupported format, or truncated;
  we still hash and delete whatever matches. Deletion is idempotent and
  format-independent.
- **Identity is pure SHA256.** The existing add pipeline stores by SHA256 of file bytes,
  so hashing the same bytes now yields the same id — even if the extension differs. This
  is the correct semantics: "delete this content."
- **Streaming for large files.** `deleteFile` must reuse the existing `kStreamingThreshold`
  (256 MB) split: use `StreamHasher` with 4 MB chunks for large files, single-shot
  `computeSha256` for small ones. This mirrors `addFile`/`addFileLarge`.
- **Internals reuse `deleteImage`.** Both new methods compute the id, then call the
  existing private path under `writeMutex` (the same one `deleteImage(const std::string&)`
  uses). We do **not** duplicate the cascade / sidecar / storage-cleanup logic.

### `ProcessingStage` additions

The existing stage enum already has `Reading`, `Hashing`, `WaitingMutex`, `DedupChecking`.
For delete we reuse them:

| Stage           | Meaning during delete                            |
|-----------------|--------------------------------------------------|
| `Reading`       | Streaming file bytes from disk                   |
| `Hashing`       | Feeding bytes into SHA256                        |
| `WaitingMutex`  | Blocked on `writeMutex`                          |
| `DedupChecking` | DB lookup for the id (reuses existing stage)     |

No new `ProcessingStage` values needed. `imagestore`'s slot display labels are fine as-is;
we add a "delete mode" hint in the header line so operators know what `DedupChecking`
means in this context.

## `imagestore` CLI Changes

### New flag

```
  -d, --delete         Delete mode: treat stdin paths as files to delete from the
                       collection (file is read, hashed, and the matching id is
                       removed from all databases and storage). No validation is
                       performed.
```

Interactions:

- `--delete` + `--dry-run` = compute the hash and look it up, print `DRY` / `DRY?`, do not
  delete.
- `--delete` + `--errors` = unchanged semantics: failing paths go into the error file and
  are skipped on re-run. (A path that hashes to a not-found id is **not** an error — same
  as `DUP` is not an error in import mode.)
- `--delete` + `--jobs N` = we still parallelize **reading and hashing**. Deletion itself
  serializes inside `libimager` on `writeMutex`, but that's fine; the hashing stage
  (which dominates for large files) runs in parallel.
- `--delete` + `--verbose` / `--quiet` = unchanged.
- `--delete` + `--memory-report` = unchanged.

### Output tokens in delete mode

`imagestore` today emits `OK`, `DUP`, `ERR`, `SKIP`. In delete mode we add:

```
DEL  <path>  <id-prefix>        Successfully deleted
MISS <path>  <id-prefix>        Hashed but no matching record (not an error)
ERR  <path>: <message>          I/O / DB / storage failure (counted as error)
DRY  <path>  <id-prefix>        --dry-run, would delete
DRY? <path>  <id-prefix>        --dry-run, no match found
SKIP <path> (in error list)     Unchanged skip behaviour
```

Summary line (non-quiet):

```
N deleted, M not found, K errors, S skipped in T.TTs
# or with --dry-run:
N would delete, M not found, K errors, S skipped in T.TTs  [dry run]
```

Exit codes: unchanged — `0` clean, `1` usage/config error, `2` one or more `ERR`.

### Pipeline changes

Only the per-file task body changes. The structural layout (stdin loop, semaphore,
`SlotTracker`, `ResultLog`, `ErrorFile`, `ProgressReporter`) is shared. Pseudocode for the
task:

```cpp
if (dryRun) {
  // Read + hash only; don't mutate storage or DB
  auto [code, id] = img.hashOnlyFile(path);          // see note below
  if (auto info = img.getImage(id); info) {
    resultLog.append("DRY  ...");
  } else {
    resultLog.append("DRY? ...");
  }
} else {
  auto res = img.deleteFile(path, onStage);
  switch (res.code) {
    case Ok:           resultLog.append("DEL  " + path + "  " + res.id.substr(0,12)); ...
    case FileNotFound: resultLog.append("MISS ..."); ...                  // not an error
    default:           resultLog.append("ERR  ..."); errorFile->record(...);
  }
}
```

**Dry-run helper.** We need a way to hash-without-deleting. Two options:

1. Add `Imager::hashOnlyFile(path) -> std::string` / `hashOnlyBlob(blob) -> std::string`
   and have the caller pair it with `getImage` for the existence check.
2. Add a `bool dryRun` argument to `deleteFile` / `deleteBlob`.

**Recommended:** option (1). It keeps the `deleteX` methods single-purpose, and
`hashOnly*` is plausibly useful elsewhere (dedup-check-before-copy, CLI `imagestore
--hash-only` future work). Cost is one extra public method pair; payoff is a cleaner API
boundary.

## Implementation Steps

1. **libimager — type and headers**
   - Add `imager/types/DeleteResult.h`.
   - Extend `imager/Types.h` to `#include "types/DeleteResult.h"`.
   - Add `deleteBlob`, `deleteFile`, `hashOnlyBlob`, `hashOnlyFile` declarations to
     `imager/Imager.h`.

2. **libimager — Imager.cpp**
   - Extract the existing `deleteImage(const std::string&)` body into a private
     `Impl::deleteByIdLocked(const std::string& id, const std::string& ext)` helper so
     `deleteBlob` / `deleteFile` can call it after hashing. The existing public
     `deleteImage` becomes a thin wrapper that hashes-not-applicable and goes straight to
     the helper.
   - Implement `hashOnlyBlob(blob)` = `computeSha256(blob)`.
   - Implement `hashOnlyFile(path)` mirroring the Reading + Hashing prologue of
     `addFile` / `addFileLarge`, respecting `kStreamingThreshold`. Extract the
     "read + hash" prologue into a shared private coroutine/helper to avoid copy-paste.
   - Implement `deleteBlob` = hash + lock `writeMutex` + lookup id + call helper.
   - Implement `deleteFile` = read + hash + lock + lookup + call helper.
   - Both return `DeleteResult{Ok/FileNotFound/..., id, message}`.

3. **imagestore — CLI plumbing**
   - Add `-d` / `--delete` to `getopt_long` in `imagestore/main.cpp`.
   - Update `printUsage`.
   - Branch the per-file task body on `deleteMode`: invoke `deleteFile` /
     `hashOnlyFile` + `getImage` instead of `addFile` / `validateOnly`.
   - Map result codes to `DEL` / `MISS` / `ERR` / `DRY` / `DRY?` tokens.
   - Update `Stats` to track `deleted`, `missing` counters in addition to the existing
     `processed`, `successful`, `duplicates`, `errors`, `skipped`. Reuse existing fields
     where semantically compatible: `successful` → `deleted`, `duplicates` → `missing`
     (reinterpretation is cheaper than adding fields; document it in the summary printer).
   - Summary line: switch wording based on `deleteMode`.

4. **ProgressReporter / ResultLog**
   - No structural change. `ProgressReporter` already renders whatever `Stats` holds; we
     only need to change the header line to include `[delete]` when `--delete` is active,
     and adjust labels. Small diff in `ProgressReporter.cpp`.

5. **Tests**
   - `imager/imager/test/ImagerTests.cpp`: add cases for `deleteFile`, `deleteBlob`,
     `hashOnlyFile`, `hashOnlyBlob`:
     - Round-trip: `addFile` an image, then `deleteFile` the same path → `Ok`; second
       `deleteFile` → `FileNotFound`.
     - Content-identity: add a file, copy its bytes to a different extension (e.g.
       rename `.jpg` to `.bin`), `deleteFile` the renamed copy → still deletes (same
       SHA256).
     - Sidecar cascade: add a JPEG + its AAE, then `deleteFile(jpeg)` → both gone.
     - Dry-run analogue: `hashOnlyFile(path)` + `getImage` returns the id and the stored
       record; no mutation.
     - Large-file path: fabricate a file > `kStreamingThreshold` (use a sparse file or
       skip in CI if too slow) to exercise `StreamHasher` in the delete pipeline.
   - `imagestore/test/test_cli.sh.in`: add delete-mode cases:
     - `--delete --help` (no such combo — `--help` wins; just verify delete flag shows in
       `--help` output).
     - `--delete` on missing path → `ERR`, exit 2.
     - `--delete` on unrecognised-content file → `MISS`, exit 0.
     - Import then `--delete` the same path → `DEL`, exit 0.
     - Second `--delete` of same path → `MISS`, exit 0 (idempotent).
     - `--delete --dry-run` on imported file → `DRY`, storage still intact (verify with
       `sqlite3` or a follow-up `--delete` that still succeeds).
     - `--delete` with `--errors` → `ERR` paths recorded, subsequent rerun skips them.
   - `imagestore/test/test_memcheck.sh.in`: mirror the basic import memcheck test in
     delete mode so valgrind catches leaks on the new code path.

6. **CLAUDE.md + docs**
   - Update `imager/CLAUDE.md` "Architecture highlights" to mention file-input delete.
   - Add a one-line entry for delete mode in `imagestore`'s `--help` and in any README
     section that enumerates the tool's modes.

## Risks and Mitigations

| Risk | Mitigation |
|------|------------|
| Hashing a giant file just to confirm it isn't in the collection is expensive. | `--dry-run` exists for cautious use; and by design the file is on disk anyway, so the I/O cost is inherent to the "delete by content" contract. |
| Users accidentally pass the *wrong* file with the right hash (collision unrealistic; rename-on-import risk real). | `--dry-run` prints the computed id prefix — operators can eyeball it. Log the full id at `--verbose`. |
| Streaming-threshold code is duplicated between add and delete paths. | Factor the "read + hash" prologue into a private helper (`Impl::readAndHash(path, StageCallback)`) returning `(Blob or empty) + id`; both pipelines call it. |
| `writeMutex` serialization kills parallelism for delete. | Acceptable — hashing dominates for large files and runs before the lock. Confirmed by code: `deleteImage` takes the mutex after lookup; we mirror that. |
| Sidecar-only files (orphan AAE) — what happens if user deletes the *parent file's* bytes but the parent was never imported? | `deleteFile(parent_path)` hashes parent bytes, looks up that id, finds nothing → `FileNotFound`. Orphan AAEs remain. This matches existing `deleteImage` semantics; a separate "delete by sidecar" story is out of scope. |
