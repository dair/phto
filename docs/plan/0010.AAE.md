# 0010 — Apple AAE Sidecar File Support

## Goal

Add support for Apple AAE (Apple Adjustment Expression) sidecar files so that `.aae` files are stored alongside their parent media file (JPG, HEIC, MOV, etc.) using the **parent file's content hash** as the filename, not the AAE's own hash. After this change, a set of input files `IMG_1234.JPG` + `IMG_1234.AAE` produces `<sha256-of-jpg>.jpg` + `<sha256-of-jpg>.aae` in storage — preserving the pairing relationship through the rename.

This is the first **sidecar** file type, establishing a pattern for non-independently-addressable companion files whose storage identity derives from a parent rather than from their own content.

## Background

### What is an AAE file?

AAE (Apple Adjustment Expression) files are XML-based plist files created by Apple's Photos app on iOS and macOS. They record non-destructive edits (crops, filters, adjustments) applied to a photo or video. Key properties:

- **Always paired**: an AAE file like `IMG_1234.AAE` corresponds to `IMG_1234.JPG`, `IMG_1234.HEIC`, `IMG_1234.MOV`, or another media file sharing the same base name.
- **Small**: typically 1–5 KB of XML/plist data.
- **Not media**: AAE files contain edit metadata, not image/video data. They should not be validated as media.
- **Idempotent edits**: the AAE describes the full edit state — replacing an AAE with a newer version is valid.

### The naming problem

The current system stores every file as `<root>/<first2hex>/<sha256>.<ext>`. Since the AAE's content differs from its parent JPG, they get different SHA256 hashes and end up with unrelated filenames in storage — destroying the pairing relationship.

The requirement is that both files share the same hash-based prefix on disk, so that a consumer of the storage can reconstruct the pair by matching filenames:

```
Storage root:
  a1/a1b2c3d4...f0.jpg    ← content hash of the JPG
  a1/a1b2c3d4...f0.aae    ← same prefix, NOT the AAE's own hash
```

### Current system behavior

- `addImage("IMG_1234.AAE", blob)` → `UnsupportedFormat` (no validator registered for `.aae`)
- The `file` table stores `name` (original filename, no directory), `id` (content SHA256), `size`, `ext`
- `FileStorage::filePath()` computes `<root>/<id[0:2]>/<id>.<ext>`
- No concept of file relationships or sidecar types exists
- The `addImage` API takes `filename` (just the name, e.g. `"photo.jpg"`) — no source path information is passed or stored

### Path-bearing filenames for disambiguation

The source set of files is expected to be relatively static — files and directories may be added or deleted, but rarely changed in place. Two cameras may produce identically-named files (`IMG_0001.JPG`) placed in different directories (`camera_a/IMG_0001.JPG` vs `camera_b/IMG_0001.JPG`). These are different files and their sidecars must pair correctly:

```
Source:
  vacation/IMG_0001.JPG  +  vacation/IMG_0001.AAE
  wedding/IMG_0001.JPG   +  wedding/IMG_0001.AAE

Must NOT cross-pair. Each AAE must find its own directory's JPG.
```

To support this, the existing `filename` parameter to `addImage()` is extended to accept a **path-bearing filename** (e.g., `"vacation/IMG_0001.JPG"` instead of just `"IMG_0001.JPG"`). The system extracts the directory portion and the base filename from this single string. The combination `(source_dir, base_name)` forms the pairing key — not just `base_name` alone. No new parameter is added; the existing `filename` simply carries more information when a path prefix is present.

## Design overview

### New concepts

1. **Sidecar file type**: a file whose storage path derives from a parent file's hash, not its own content hash.
2. **Source-qualified base name matching**: given `vacation/IMG_1234.AAE`, the pairing key `(vacation, IMG_1234)` — i.e., source directory + base name (no extension) — is used to find a parent file `vacation/IMG_1234.JPG` (or `.heic`, `.mov`, `.nef`, etc.) in the database. This prevents cross-pairing between identically-named files from different source directories.
3. **Original-name index**: a new database table mapping `(source_dir, base_name)` pairs to file IDs, enabling efficient parent lookup and deferred pairing when the parent arrives after the sidecar.

### Path-bearing `filename` parameter

The `addImage(blob, filename)` signature is unchanged — no new parameter is added. Instead, the `filename` parameter is now understood to accept an optional path prefix:

- `"IMG_1234.JPG"` — bare filename (legacy behavior, backwards compatible). The system extracts `source_dir = ""` and `base_name = "img_1234"`.
- `"vacation/IMG_1234.JPG"` — path-bearing filename. The system extracts `source_dir = "vacation"` and `base_name = "img_1234"`.
- `"/photos/vacation/IMG_1234.JPG"` — absolute path-bearing filename. The system extracts `source_dir = "/photos/vacation"` and `base_name = "img_1234"`.

The extension is detected from the final path component (the actual filename), and the `file.name` DB column stores only the bare filename (final component). The directory portion is extracted and stored in `original_name.source_dir`.

The `imagestore` batch utility (0006) naturally has the full path from stdin and will pass it directly as the `filename`. The sample CLI and tests can pass bare filenames.

All files (not just sidecars) record their source directory and base name in `original_name` at add time. This makes the index available for parent lookup regardless of insertion order.

### Core algorithm

Two scenarios must be handled:

**Scenario A — Parent exists when AAE is added** (common case):

1. Receive `addImage(blob, "vacation/IMG_1234.AAE")`
2. Split filename: `source_dir = "vacation"`, `bare_name = "IMG_1234.AAE"`, `ext = ".aae"`, `base_name = "img_1234"` (lowercased, no extension)
3. Validate AAE format (XML/plist structure check — lightweight)
4. Compute AAE's own content hash → `aae_hash` (for deduplication)
5. Query `original_name` table: find a non-sidecar file with `source_dir = 'vacation'` AND `base_name = 'img_1234'`
6. Found exactly one parent with `file_id = parent_hash` → proceed
   - If multiple parents found (e.g., `IMG_1234.JPG` and `IMG_1234.HEIC` in the same dir): see "Parent selection" below
   - If zero parents found: fall through to Scenario B (orphan)
7. Store AAE on disk as `<root>/<parent_hash[0:2]>/<parent_hash>.aae`
8. Insert into `file` table: `id = aae_hash`, `name = IMG_1234.AAE` (bare name only), `ext = .aae`
9. Insert into `original_name` table: `source_dir = 'vacation'`, `base_name = 'img_1234'`, `file_id = aae_hash`
10. Insert into `file_companion` table: `file_id = aae_hash`, `parent_id = parent_hash`, `storage_id = parent_hash`

**Scenario B — AAE is added before its parent** (less common, but must work):

1. Receive `addImage(blob, "vacation/IMG_1234.AAE")`
2. Split filename, validate, compute `aae_hash`, extract pairing key `("vacation", "img_1234")`
3. No parent found in `original_name` table for this `(source_dir, base_name)`
4. Store AAE with its own hash temporarily: `<root>/<aae_hash[0:2]>/<aae_hash>.aae`
5. Insert into `file` table: `id = aae_hash`, `name = IMG_1234.AAE` (bare name only), `ext = .aae`
6. Insert into `original_name` table: `source_dir = 'vacation'`, `base_name = 'img_1234'`, `file_id = aae_hash`
7. Insert into `file_companion` table: `file_id = aae_hash`, `parent_id = NULL`, `storage_id = aae_hash` (orphan)

**Scenario B continued — Parent arrives later**:

1. Receive `addImage(blob, "vacation/IMG_1234.JPG")`, validate, compute `parent_hash`
2. Normal addImage flow stores the JPG
3. Insert into `original_name` table: `source_dir = 'vacation'`, `base_name = 'img_1234'`, `file_id = parent_hash`
4. Check `file_companion` for orphan sidecars: query for entries where `parent_id IS NULL` and the sidecar's `(source_dir, base_name)` matches `('vacation', 'img_1234')`
5. Found orphan AAE with `file_id = aae_hash`
6. **Relocate** the AAE file on all storage roots: move from `<aae_hash[0:2]>/<aae_hash>.aae` to `<parent_hash[0:2]>/<parent_hash>.aae`
7. Update `file_companion`: set `parent_id = parent_hash`, `storage_id = parent_hash`

**Scenario C — Bare filename without path** (legacy / programmatic usage):

When `filename` has no directory component (e.g., `"IMG_1234.AAE"`), `source_dir` is stored as `""`. Pairing matches on `(source_dir = "", base_name)`. This means all files added without path prefixes share a single namespace — base name collisions are possible. This is acceptable for the simple case (single-camera imports) and is the backwards-compatible default.

### Why relocation is acceptable

The relocation step (moving a file between shard directories on disk) seems expensive, but:

- AAE files are tiny (1–5 KB) — the move is effectively instantaneous
- This only happens in Scenario B (AAE-before-parent), which is the uncommon ordering
- The move is within the same filesystem (same storage root), so `std::filesystem::rename` is atomic
- Multi-root: the move runs in parallel across all roots, matching the existing write/delete pattern

If rename fails (e.g., cross-device — which shouldn't happen since source and dest are under the same root), fall back to copy+delete.

## Schema changes

### New table: `original_name`

Maps the source-directory-qualified base name (without extension) to a file ID. The `(source_dir, base_name)` pair is the pairing key used to match sidecars to their parent files.

```sql
CREATE TABLE IF NOT EXISTS original_name (
    source_dir TEXT NOT NULL,   -- directory portion of original path (e.g., "vacation", "camera_a/2024")
    base_name  TEXT NOT NULL,   -- filename without extension, lowercased (e.g., "img_1234")
    file_id    TEXT NOT NULL REFERENCES file(id) ON DELETE CASCADE,
    PRIMARY KEY (source_dir, base_name, file_id)
);

CREATE INDEX IF NOT EXISTS idx_original_name_pairing
    ON original_name(source_dir, base_name);
```

Every file added to the system gets an entry here — not just sidecars. This makes parent lookup O(1) regardless of total file count.

**Why `source_dir` + `base_name`?** Two cameras may produce `IMG_0001.JPG` in different directories. Without the directory component, pairing would be ambiguous. The source directory is the natural scope boundary — files in the same directory are assumed to be from the same device/session.

**`source_dir` semantics**: the directory portion is extracted from the `filename` parameter passed to `addImage()`. For `"/photos/vacation/IMG_1234.JPG"`, `source_dir = "/photos/vacation"`. For relative paths like `"vacation/IMG_1234.JPG"`, `source_dir = "vacation"`. For bare filenames like `"IMG_1234.JPG"` (no path separator), `source_dir = ""`. The directory is stored as-is (after normalization to remove trailing slashes), case-preserved but compared case-insensitively (via `COLLATE NOCASE` or by lowercasing before storage — matching the `base_name` approach).

**Why a separate table instead of a column on `file`?** A single `(source_dir, base_name)` pair can map to multiple file IDs (e.g., `IMG_1234.JPG` and `IMG_1234.MOV` from a Live Photo) and a single file might be added with different original names across sessions. The many-to-many relationship warrants a join table.

### New table: `file_companion`

Tracks the sidecar-to-parent relationship.

```sql
CREATE TABLE IF NOT EXISTS file_companion (
    file_id   TEXT PRIMARY KEY NOT NULL REFERENCES file(id) ON DELETE CASCADE,
    parent_id TEXT REFERENCES file(id) ON DELETE SET NULL,
    storage_id TEXT NOT NULL
);
```

| Column | Purpose |
|--------|---------|
| `file_id` | The sidecar file's own content hash (its `file.id`) |
| `parent_id` | The parent file's content hash (`NULL` if orphan — parent not yet added) |
| `storage_id` | The hash used for the on-disk filename. Equals `parent_id` when parent is known, equals `file_id` when orphan. Updated on relocation |

The `storage_id` column is the key indirection: `FileStorage` uses `storage_id` (not `file_id`) to compute the disk path for sidecar files. This avoids ambiguity about where the file lives on disk, especially during the orphan→paired transition.

### No data migration needed

The schema changes are additive (new tables only). The existing `file` table is unchanged. The new tables are created with `CREATE TABLE IF NOT EXISTS` during initialization, matching the existing pattern. No existing data needs to be backfilled — the `original_name` and `file_companion` tables are populated going forward as files are added via the updated `addImage` API.

## AAE validation

AAE files are XML-based Apple plist files. Validation should be lightweight since they're not media:

### Validation steps

1. **Quick rejection** — check minimum size (64 bytes) and look for XML plist markers: `<?xml` near the start and `<plist` within the first 512 bytes. If absent → `WRONG`.
2. **Structure check** — parse as XML (using a lightweight parser or simple state machine). Verify it contains a `<dict>` root element with at least one key. If parsing fails → `INVALID`.
3. **AAE-specific keys** — optionally check for known AAE keys like `adjustmentFormatVersion`, `adjustmentBaseVersion`, or `adjustmentData`. This is a soft check — missing keys result in `VALID` with a warning, not `INVALID`, since Apple may change the format.

### Validation depth

Unlike media validators that decode pixel/frame data, AAE validation is essentially XML well-formedness plus a quick format sniff. This is intentional — AAE files are metadata, not media. Bit-level corruption would be caught by the XML parser.

### No external library needed

AAE files are simple XML. A hand-rolled check (scan for `<?xml` + `<plist>` markers, optionally verify XML well-formedness with a minimal SAX-style scan) avoids adding a dependency. If a proper XML parser is later wanted, tinyxml2 or expat could be bundled, but for this plan the quick-rejection + marker check is sufficient.

### Validator interface

```cpp
// validations/aae/aae_validator.h
#pragma once
#include <cstddef>

enum ValidationResult {
    INVALID = -1,
    VALID = 0,
    WRONG = 1,
};

ValidationResult validateAae(const void* data, size_t dataSize);
```

Follows the same pattern as all existing validators.

## Facade changes

### `Imager::addImage` modifications

The `addImage` method signature is unchanged — `filename` now accepts path-bearing filenames. A new code path handles sidecar files:

```
addImage(blob, "vacation/IMG_1234.AAE"):
  1. split filename: source_dir = "vacation", bare_name = "IMG_1234.AAE"
  2. ext = ".aae" → recognized as sidecar type
  3. validate AAE format
  4. compute content hash → aae_hash
  5. pairing key: source_dir = "vacation", base_name = "img_1234"
  6. lookup parent via original_name table WHERE source_dir AND base_name match
  7. if exactly one parent found:
       storage_id = parent_hash
       store as <parent_hash>.aae
       insert file record (id=aae_hash, name=bare_name)
       insert original_name (source_dir, base_name, file_id=aae_hash)
       insert file_companion (file_id=aae_hash, parent_id=parent_hash, storage_id=parent_hash)
  8. if zero parents found (orphan):
       storage_id = aae_hash
       store as <aae_hash>.aae
       insert file record (id=aae_hash, name=bare_name)
       insert original_name (source_dir, base_name, file_id=aae_hash)
       insert file_companion (file_id=aae_hash, parent_id=NULL, storage_id=aae_hash)
  9. if multiple parents found (ambiguous — e.g., same-dir JPG+HEIC):
       see "Parent selection" below
```

### `Imager::addImage` — parent arrival triggers orphan resolution

When a non-sidecar file is added, after the normal flow succeeds:

```
addImage(blob, "vacation/IMG_1234.JPG"):
  ... normal flow (split filename, validate, hash, store) ...
  9. extract pairing key from filename: source_dir = "vacation", base_name = "img_1234"
  10. insert original_name (source_dir, base_name, file_id=parent_hash)
  11. query file_companion for orphan sidecars with matching (source_dir, base_name):
      SELECT fc.file_id, fc.storage_id, f.ext
      FROM file_companion fc
      JOIN file f ON f.id = fc.file_id
      JOIN original_name on_ ON on_.file_id = fc.file_id
           AND on_.source_dir = ? AND on_.base_name = ?
      WHERE fc.parent_id IS NULL
  12. for each orphan:
        relocate file on disk: old_storage_id.ext → parent_hash.ext
        update file_companion: parent_id = parent_hash, storage_id = parent_hash
```

### `Imager::deleteImage` — cascade to sidecars

When a parent file is deleted, its sidecars should also be deleted (they're meaningless without the parent):

```
deleteImage(parent_hash):
  1. find all companions: SELECT file_id, storage_id, ext FROM file_companion WHERE parent_id = ?
  2. for each companion:
       delete file from storage using storage_id
       delete file record from DB (cascades file_companion, original_name via ON DELETE CASCADE)
  3. proceed with normal parent deletion
```

### `Imager::getImageData` — sidecar retrieval

When reading a sidecar file, `FileStorage` must use `storage_id` (from `file_companion`) instead of the file's own `id`:

```
getImageData(aae_hash):
  1. check file_companion for this file_id
  2. if found: use storage_id for disk path
  3. if not found: use file_id as usual (normal file)
```

### `FileStorage` changes

`FileStorage::filePath` currently takes `(root, id, ext)` and computes the path. No changes needed — the caller (Imager) will pass the correct `storage_id` instead of `file_id` for sidecar files.

However, a new method is needed for relocation:

```cpp
/// Move a file from one id-based path to another across all storage roots.
/// Used when an orphan sidecar's parent is discovered.
coro::Task<void> relocateFileAsync(
    const std::string& oldId, const std::string& newId, const std::string& ext);
```

This calls `std::filesystem::rename` per root in parallel (or copy+delete if rename fails).

## Database API additions

### `Database` class new methods

```cpp
// --- Original name tracking ---

/// Record that file `fileId` was originally at (sourceDir, baseName).
void addOriginalName(const std::string& sourceDir, const std::string& baseName,
                     const std::string& fileId);

/// Find all files with a given (sourceDir, baseName) pairing key.
/// Used to find parent candidates for a sidecar.
std::vector<File> getFilesBySourceAndBaseName(const std::string& sourceDir,
                                              const std::string& baseName);

// --- Companion tracking ---

struct CompanionInfo {
    std::string fileId;
    std::optional<std::string> parentId;
    std::string storageId;
};

/// Record a sidecar relationship.
void addCompanion(const std::string& fileId, const std::optional<std::string>& parentId,
                  const std::string& storageId);

/// Get the companion record for a sidecar file. Returns nullopt for normal files.
std::optional<CompanionInfo> getCompanion(const std::string& fileId);

/// Find orphan sidecars matching a (sourceDir, baseName) pairing key.
/// Used when a parent arrives and needs to resolve its orphan sidecars.
std::vector<CompanionInfo> getOrphanCompanionsBySourceAndBaseName(
    const std::string& sourceDir, const std::string& baseName);

/// Update a companion's parent and storage ID (used during orphan resolution).
void updateCompanionParent(const std::string& fileId, const std::string& parentId,
                           const std::string& storageId);

/// Get all companions of a parent file.
std::vector<CompanionInfo> getCompanionsForParent(const std::string& parentId);
```

### `MultiDatabase` wrappers

Each new `Database` method gets a corresponding `MultiDatabase` method — writes fan out to all DBs, reads go to `m_dbs[0]`. Same pattern as all existing operations.

## Facade integration

### `imager/AaeValidatorImpl.cpp`

```cpp
#include "Validators.h"
#include "aae_validator.h"

namespace {

class AaeValidator final: public validation::IValidator {
public:
  bool supportsExtension(const std::string& ext) const override {
    return ext == ".aae";
  }

  validation::ValidationResult validate(const uint8_t* data, size_t size) const override {
    switch (validateAae(data, size)) {
      case VALID:   return {true, ""};
      case INVALID: return {false, "AAE data is corrupted or malformed"};
      case WRONG:   return {false, "Data is not an AAE file"};
    }
    return {false, "Unknown validation result"};
  }
};

} // namespace

namespace imager {

std::unique_ptr<validation::IValidator> createAaeValidator() {
  return std::make_unique<AaeValidator>();
}

} // namespace imager
```

### `Validators.h` changes

Add `createAaeValidator()` and register it in `createDefaultValidators()`.

### Sidecar detection

A helper function in `Imager.cpp` identifies sidecar extensions:

```cpp
static bool isSidecarExtension(const std::string& ext) {
    return ext == ".aae";
    // Future: ".xmp" (Adobe sidecar) could be added here
}
```

This is checked early in `addImage` to route into the sidecar code path.

## Risk: base name collision across directories

The `(source_dir, base_name)` pairing key prevents cross-directory collisions. Two cameras producing `IMG_0001.JPG` in different directories (`camera_a/IMG_0001.JPG` and `camera_b/IMG_0001.JPG`) get distinct `source_dir` values, so their AAEs pair correctly.

**Within the same directory**, collision is still possible but unlikely — it would mean two files with the same base name and different media extensions in the same source folder (e.g., `IMG_0001.JPG` and `IMG_0001.HEIC`). This legitimately happens with Live Photos or format conversion. See "Parent selection" below for how this is handled.

### Parent selection (multiple parents in same source_dir)

When a sidecar's `(source_dir, base_name)` matches multiple parent files — e.g., `vacation/IMG_1234.JPG` and `vacation/IMG_1234.MOV` (Live Photo):

1. **Prefer image over video**: AAE edits almost always apply to the still image. If one match is an image extension (`.jpg`, `.jpeg`, `.heic`, `.heif`, `.nef`, `.png`) and another is a video (`.mov`, `.mp4`), prefer the image.
2. **If still ambiguous** (e.g., both `.jpg` and `.heic`): reject with error `"Ambiguous sidecar: multiple parent files match (source_dir, base_name) for 'IMG_1234.AAE'"`. The user must resolve by removing or renaming one of the conflicting files before re-import.
3. **This rejection is conservative** — it avoids silent mis-pairing and can be refined later if real-world usage shows it's too restrictive.

### Bare filenames (no path prefix)

Files added with bare filenames (no directory component, e.g. `"IMG_1234.JPG"`) all share `source_dir = ""`. In this namespace, base name collisions are possible. The same ambiguity rules apply: if multiple parents match `("", base_name)`, the pairing is rejected.

## AAE replacement

If the user re-edits a photo, a new `IMG_1234.AAE` is generated with different content. The content hash changes, so the system sees it as a new file. The old AAE is replaced: if a companion already exists for the same parent with the same extension, delete the old sidecar from storage and DB, then store the new one. An AAE represents the current edit state — keeping old versions is not useful.

## Risk: case sensitivity in base name matching

Apple filesystems (APFS) are case-insensitive by default. A file might arrive as `img_1234.JPG` and its sidecar as `IMG_1234.AAE`. Base name matching must be **case-insensitive**.

**Implementation**: normalize base names to lowercase before storing in `original_name` and before querying. This matches the existing `lowercaseExt()` pattern in `Imager.cpp`.

## Risk: Live Photos (JPG + MOV pairs)

Apple Live Photos consist of `IMG_1234.JPG` + `IMG_1234.MOV` sharing the same base name. These are NOT sidecars — both are independent media files with their own content hashes. The `original_name` table will have two entries for the same base name, which is correct and handled by the composite primary key.

An AAE for a Live Photo edit would apply to the JPG (still image edits) or the MOV (video trim). In practice, iOS creates the AAE for the JPG. The parent lookup finds both files but selects the one with a media extension matching the typical AAE→JPG pairing. If disambiguation is needed, prefer the image file over the video file.

## Comparison with existing patterns

| Aspect | Media files (JPG/HEIC/MOV/NEF) | Sidecar files (AAE) |
|--------|-------------------------------|---------------------|
| Validation | Deep (decode pixel/frame data) | Lightweight (XML structure check) |
| File identity (DB `id`) | Own content hash | Own content hash |
| Storage filename | Own content hash | Parent's content hash (or own hash if orphan) |
| Deduplication | By content hash | By content hash |
| Independent retrieval | Yes | Yes (via own `id`) |
| Deletion cascade | Independent | Deleted when parent is deleted |
| External dependency | Various (libjpeg, libheif, etc.) | None |
