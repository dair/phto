# 0005 — Monitoring Infrastructure for Bottleneck Analysis

## Goal

Add lightweight instrumentation to identify where time is spent when processing images at scale (10k+ concurrent operations). The monitoring must be:

- **Low overhead** — nanosecond-resolution timers, no heap allocation on the hot path, no locks on the recording path
- **Always-on capable** — cheap enough to leave enabled in production, not just debug builds
- **Aggregating** — at 10k images/sec, per-image log lines are noise; we need histograms, percentiles, throughput counters
- **Actionable** — the output should immediately show which stage is the bottleneck and whether it's CPU, I/O, or contention

## What to measure

### Per-image pipeline stages (the primary ask)

Each `addImage` call passes through distinct stages. Instrument each:

| Stage | What it measures | Where |
|-------|-----------------|-------|
| **validate** | Format validation (libjpeg / libpng decode check) | `Imager.cpp` coroutine lambda |
| **hash** | SHA256 computation (CPU-bound, OpenSSL EVP) | `Imager.cpp` coroutine lambda |
| **dedup_check** | `fileExists` query on first DB | `Imager.cpp` after mutex acquire |
| **storage_write** | Total wall time to write all roots in parallel | `Imager.cpp` around `writeFileAsync` blockOn |
| **storage_write_root** | Per-root write (create_directories + fstream write) | `FileStorage::writeToRoot` |
| **db_insert** | Total wall time to insert into all DBs in parallel | `Imager.cpp` around `dbs.addFile` |
| **db_insert_single** | Per-DB insert (SQLite INSERT + WAL commit) | `MultiDatabase::parallelWriteAll` per-DB lambda |
| **mutex_wait** | Time spent waiting for `writeMutex` | `Imager.cpp` before lock acquisition |
| **addimage_total** | End-to-end `addImage` wall time | `Imager.cpp` top/bottom |

Each measurement records: **duration** (nanoseconds) and **file size** (bytes, for throughput calculations).

### Thread pool health

| Metric | What it measures | Where |
|--------|-----------------|-------|
| **pool_queue_depth** | Number of coroutines waiting in the queue | `ThreadPool::enqueue` |
| **pool_schedule_latency** | Time between `enqueue` and `resume` (how long a coroutine waited for a thread) | `ThreadPool::schedule` awaiter |
| **pool_active_threads** | Number of threads currently executing (not blocked on condvar) | `ThreadPool::workerLoop` |

These reveal whether the pool is saturated. If `schedule_latency` is high while all threads are active, the pool is too small. If `queue_depth` is high but `active_threads` is low, threads are blocked on I/O or locks.

### Storage I/O patterns

| Metric | What it measures | Where |
|--------|-----------------|-------|
| **storage_bytes_written** | Total bytes written (counter) | `FileStorage::writeToRoot` |
| **storage_bytes_read** | Total bytes read (counter) | `FileStorage::readFile` |
| **storage_read_duration** | Per-file read latency | `FileStorage::readFile` |

Correlating `storage_bytes_written` with `storage_write_root` duration gives per-root write throughput (MB/s), which identifies slow disks.

### Database contention

| Metric | What it measures | Where |
|--------|-----------------|-------|
| **db_read_duration** | Duration of read queries (shared_lock section) | `Database.cpp` read methods |
| **db_write_duration** | Duration of write queries (unique_lock section) | `Database.cpp` write methods |

At 10k concurrent images, the single `writeMutex` in `Imager` serializes all writes. If `mutex_wait` dominates, the architecture needs to change (e.g., per-hash-prefix sharding of the mutex, or pipelining writes).

### Memory pressure

| Metric | What it measures | Where |
|--------|-----------------|-------|
| **blobs_alive** | Number of `Blob` instances currently alive (shared_ptr refcount > 0) | `Blob` constructor / destructor |
| **blob_bytes_alive** | Total bytes held by live Blobs | Same |

At 10k concurrent 5 MB images, that's 50 GB of Blob memory. This counter reveals whether Blobs are being freed promptly after `addImage` completes or accumulating.

## Architecture

### Core primitive: `Metrics` singleton

A single thread-safe metrics collector, accessed globally. All instrumentation calls go through it.

```
metrics/
├── CMakeLists.txt
└── include/metrics/
    ├── Metrics.h        # Singleton, histogram registry, counter registry
    ├── Histogram.h      # Lock-free histogram (HDR-style or fixed-bucket)
    ├── Counter.h        # Atomic monotonic counter
    ├── Gauge.h          # Atomic gauge (current value, can go up/down)
    ├── Timer.h          # RAII duration measurement → records into a Histogram
    └── Snapshot.h       # Point-in-time read of all metrics for reporting
```

### `Histogram` — fixed-bucket, lock-free

For latency measurements. Pre-defined log-scale buckets (e.g., 1us, 10us, 100us, 1ms, 10ms, 100ms, 1s, 10s). Each bucket is a `std::atomic<uint64_t>` count. Recording is a single `fetch_add` — no locks, no allocation.

```cpp
namespace metrics {

class Histogram {
public:
    explicit Histogram(std::string name);

    /// Record a duration sample. O(1), lock-free.
    void record(std::chrono::nanoseconds duration);

    /// Read current state without resetting.
    struct Snapshot {
        std::string name;
        uint64_t    count;
        uint64_t    sum_ns;       // for computing mean
        uint64_t    buckets[N];   // per-bucket counts
        // Derived: p50, p95, p99, max from bucket distribution
    };
    Snapshot snapshot() const;

private:
    std::string                          m_name;
    std::atomic<uint64_t>                m_count{0};
    std::atomic<uint64_t>                m_sum{0};
    std::array<std::atomic<uint64_t>, N> m_buckets{};

    static size_t bucketIndex(std::chrono::nanoseconds d);
};

} // namespace metrics
```

Bucket boundaries (23 buckets, covering 100ns to 30s):

```
100ns, 500ns, 1us, 5us, 10us, 50us, 100us, 500us,
1ms, 5ms, 10ms, 50ms, 100ms, 500ms,
1s, 2s, 5s, 10s, 30s, +Inf
```

This gives enough resolution to distinguish CPU-bound stages (microseconds) from I/O stages (milliseconds) from contention stalls (seconds).

### `Counter` — monotonic, lock-free

For throughput (bytes written, images processed).

```cpp
class Counter {
public:
    explicit Counter(std::string name);
    void     add(uint64_t delta);   // atomic fetch_add
    uint64_t value() const;         // atomic load
};
```

### `Gauge` — current value, lock-free

For point-in-time counts (queue depth, active threads, live blobs).

```cpp
class Gauge {
public:
    explicit Gauge(std::string name);
    void     increment();  // fetch_add(1)
    void     decrement();  // fetch_sub(1)
    void     set(int64_t v);
    int64_t  value() const;
};
```

### `Timer` — RAII measurement → Histogram

```cpp
class Timer {
public:
    explicit Timer(Histogram& target);
    ~Timer();  // records elapsed time into target histogram

    Timer(const Timer&) = delete;
    Timer& operator=(const Timer&) = delete;

    /// Manually stop and record (for cases where you want the duration value).
    std::chrono::nanoseconds stop();

private:
    Histogram*                                    m_target;
    std::chrono::steady_clock::time_point         m_start;
};
```

Usage at instrumentation sites:

```cpp
// In addImage:
metrics::Timer t(metrics::get().addimage_total);
// ... t destructor records duration when addImage returns

// In a coroutine:
{
    metrics::Timer t(metrics::get().validate);
    result = validator->validate(blob.data(), blob.size());
}  // t records
```

### `Metrics` — the singleton registry

```cpp
class Metrics {
public:
    static Metrics& get();  // Meyer's singleton

    // --- Per-image pipeline ---
    Histogram addimage_total{"addimage_total"};
    Histogram validate{"validate"};
    Histogram hash{"hash"};
    Histogram dedup_check{"dedup_check"};
    Histogram storage_write{"storage_write"};
    Histogram storage_write_root{"storage_write_root"};
    Histogram db_insert{"db_insert"};
    Histogram db_insert_single{"db_insert_single"};
    Histogram mutex_wait{"mutex_wait"};

    // --- Thread pool ---
    Histogram pool_schedule_latency{"pool_schedule_latency"};
    Gauge     pool_queue_depth{"pool_queue_depth"};
    Gauge     pool_active_threads{"pool_active_threads"};

    // --- Storage I/O ---
    Counter   storage_bytes_written{"storage_bytes_written"};
    Counter   storage_bytes_read{"storage_bytes_read"};
    Histogram storage_read_duration{"storage_read_duration"};

    // --- Database ---
    Histogram db_read_duration{"db_read_duration"};
    Histogram db_write_duration{"db_write_duration"};

    // --- Memory ---
    Gauge     blobs_alive{"blobs_alive"};
    Gauge     blob_bytes_alive{"blob_bytes_alive"};

    // --- Throughput ---
    Counter   images_added{"images_added"};
    Counter   images_failed{"images_failed"};

    /// Take a consistent snapshot of all metrics.
    struct FullSnapshot { /* all histogram/counter/gauge snapshots */ };
    FullSnapshot snapshot() const;

    /// Reset all counters/histograms to zero (for periodic reporting).
    void reset();
};
```

Meyer's singleton (`static Metrics& get()`) avoids initialization-order issues and is thread-safe in C++11+.

### No external dependencies

The metrics library uses only `<atomic>`, `<chrono>`, `<array>`, `<string>`, `<cstdint>`. No third-party libraries. This keeps with the project's minimal-dependency philosophy.

### Reporting / export

The metrics are in-memory. How they get consumed is pluggable:

**Phase 1 (this plan)**: A `Metrics::snapshot()` method returns a `FullSnapshot` struct. The sample CLI (`imager_cli`) can dump it to stderr on exit, or a future HTTP endpoint can serialize it as JSON.

**Future phases** (out of scope):
- Prometheus `/metrics` endpoint (text exposition format)
- OpenTelemetry span export
- Periodic background dump to a log file

## Instrumentation points

### `Imager.cpp` — `addImage`

```cpp
AddResult Imager::addImage(const Blob& blob, const std::string& filename) {
    metrics::Timer total(metrics::get().addimage_total);

    // ... extension/validator checks ...

    if (!validator) {
        metrics::Timer t(metrics::get().hash);
        id = computeSha256(blob);
    } else {
        // parallel validate + hash: instrument inside the coroutine lambdas
        // validate lambda:
        //   metrics::Timer t(metrics::get().validate);
        //   out = v2->validate(b2.data(), b2.size());
        // hash lambda:
        //   metrics::Timer t(metrics::get().hash);
        //   out = computeSha256(b2);
    }

    // mutex_wait: measure time to acquire
    {
        metrics::Timer t(metrics::get().mutex_wait);
        m_impl->writeMutex.lock();
    }
    std::lock_guard<std::mutex> lock(m_impl->writeMutex, std::adopt_lock);

    // dedup_check
    {
        metrics::Timer t(metrics::get().dedup_check);
        if (m_impl->dbs.fileExists(id)) ...
    }

    // storage_write (total across all roots)
    {
        metrics::Timer t(metrics::get().storage_write);
        coro::blockOn(m_impl->pool, m_impl->storage.writeFileAsync(id, ext, blob));
    }

    // db_insert (total across all DBs)
    {
        metrics::Timer t(metrics::get().db_insert);
        m_impl->dbs.addFile(id, filename, blob.size(), ext);
    }

    metrics::get().images_added.add(1);
    return {ErrorCode::Ok, id, ""};
}
```

### `MultiDatabase.cpp` — per-DB insert timing

```cpp
    }

```

### `ThreadPool` — schedule latency and pool health

```cpp
auto schedule() {
    struct Awaiter {
        ThreadPool& pool;
        std::chrono::steady_clock::time_point enqueueTime;

        bool await_ready() const noexcept { return false; }
        void await_suspend(std::coroutine_handle<> h) {
            enqueueTime = std::chrono::steady_clock::now();
            metrics::get().pool_queue_depth.increment();
            pool.enqueue(h);
        }
        void await_resume() noexcept {
            metrics::get().pool_queue_depth.decrement();
            auto elapsed = std::chrono::steady_clock::now() - enqueueTime;
            metrics::get().pool_schedule_latency.record(elapsed);
        }
    };
    return Awaiter{*this, {}};
}
```

`await_resume` runs on the worker thread after the coroutine is resumed, so the elapsed time accurately measures queue wait.

For `active_threads`, increment in `workerLoop` before `h.resume()`, decrement after:

```cpp
void workerLoop() {
    while (true) {
        // ... dequeue h ...
        metrics::get().pool_active_threads.increment();
        h.resume();
        metrics::get().pool_active_threads.decrement();
    }
}
```

### `Blob` — memory tracking

In `Blob` constructors, increment `blobs_alive` and `blob_bytes_alive`. In destructor (or when shared_ptr deleter runs), decrement. Since Blob uses `shared_ptr`, the tracking must happen at the shared_ptr level, not the Blob copy level. Use a custom deleter:

```cpp
explicit Blob(size_t size)
    : m_data(size > 0
        ? std::shared_ptr<uint8_t[]>(new uint8_t[size],
            [size](uint8_t* p) {
                metrics::get().blobs_alive.decrement();
                metrics::get().blob_bytes_alive.set(
                    metrics::get().blob_bytes_alive.value() - static_cast<int64_t>(size));
                delete[] p;
            })
        : nullptr)
    , m_size(size)
{
    if (size > 0) {
        metrics::get().blobs_alive.increment();
        metrics::get().blob_bytes_alive.set(
            metrics::get().blob_bytes_alive.value() + static_cast<int64_t>(size));
    }
}
```

This correctly counts unique buffers (not Blob copies), since the deleter runs once when the last shared_ptr reference drops.

## Overhead analysis

| Operation | Cost | Acceptable? |
|-----------|------|-------------|
| `Timer` construction | `steady_clock::now()` — ~20 ns on Linux | Yes |
| `Timer` destruction | `steady_clock::now()` + `Histogram::record` (~one `fetch_add`) — ~25 ns | Yes |
| `Histogram::record` | One comparison chain (find bucket) + one `fetch_add` — ~5 ns | Yes |
| `Counter::add` | One `fetch_add` — ~5 ns | Yes |
| `Gauge::increment/decrement` | One `fetch_add` / `fetch_sub` — ~5 ns | Yes |
| Total per addImage | ~8 Timer sites × 45 ns = ~360 ns | Yes (negligible vs ms-scale I/O) |

No heap allocations, no locks, no syscalls on the recording path. The overhead is dominated by `steady_clock::now()` calls, which are VDSO-accelerated on Linux.

## Compile-time disable

For builds where even 360 ns per image matters, provide a `IMAGER_METRICS_ENABLED` CMake option (default ON). When OFF:

- `Timer` becomes an empty struct with no-op constructor/destructor
- `Counter::add`, `Gauge::increment/decrement`, `Histogram::record` become no-ops
- The compiler eliminates all measurement code

```cmake
option(IMAGER_METRICS_ENABLED "Enable built-in metrics collection" ON)
if(IMAGER_METRICS_ENABLED)
    target_compile_definitions(metrics_lib PUBLIC IMAGER_METRICS_ENABLED)
endif()
```

```cpp
#ifdef IMAGER_METRICS_ENABLED
    // real implementation
#else
    struct Timer { explicit Timer(Histogram&) {} };
    // etc.
#endif
```

`Metrics::snapshot()` returns a `FullSnapshot` that can be formatted as human-readable text:

```

  validate          count=8921   mean=1.8ms  p50=1.2ms  p95=5.3ms   p99=11.2ms
  hash              count=12847  mean=0.9ms  p50=0.7ms  p95=2.1ms   p99=4.8ms
  dedup_check       count=12847  mean=0.02ms p50=0.01ms p95=0.05ms  p99=0.1ms
  storage_write     count=12847  mean=1.1ms  p50=0.8ms  p95=3.2ms   p99=8.1ms
  storage_write_root count=25694 mean=0.9ms  p50=0.7ms  p95=2.8ms   p99=7.2ms
  db_insert         count=12847  mean=0.3ms  p50=0.2ms  p95=0.8ms   p99=1.5ms
  db_insert_single  count=25694  mean=0.2ms  p50=0.15ms p95=0.6ms   p99=1.2ms
  mutex_wait        count=12847  mean=0.05ms p50=0.001ms p95=0.2ms  p99=12.4ms  ← CONTENTION

Thread pool:
  schedule_latency  count=89421  mean=0.1ms  p50=0.02ms p95=0.5ms   p99=2.1ms
  queue_depth       current=3
  active_threads    current=8/8                                       ← SATURATED

Storage I/O:
  bytes_written     52.3 GB
  bytes_read        0.0 GB
  write throughput  ~124 MB/s per root

Memory:
  blobs_alive       current=47
  blob_bytes_alive  current=235 MB

Throughput:
  images_added      12847
  images_failed     0
```

From this output, an operator can immediately see:
- `mutex_wait` p99 of 12.4ms → the global `writeMutex` is a contention hotspot
- `active_threads` 8/8 → pool is fully utilized, consider increasing pool size
- `validate` is the slowest per-image stage at p95 → consider validation-level optimization or skipping for trusted sources
- `storage_write` p99 at 8.1ms but `storage_write_root` p99 at 7.2ms → nearly all time is in the single-root write; the parallel fan-out adds little overhead

## Beyond this plan: optimization opportunities the metrics will reveal

The metrics infrastructure is diagnostic — it tells you *where* time is spent. Here are the likely findings and their fixes (future work, not part of this plan):

| Likely finding | Fix |
|---------------|-----|
| `mutex_wait` dominates at high concurrency | Replace global `writeMutex` with per-hash-prefix sharding (256 mutexes) or lock-free duplicate check |
| `pool_schedule_latency` high, all threads active | Increase pool size; make pool size configurable in TOML |
| `validate` is slowest stage for JPEG | Profile libjpeg — consider partial decode (header-only validation) |
| `storage_write_root` varies by root | One disk is slower; balance or prioritize fast disks |
| `blob_bytes_alive` grows unboundedly | Backpressure needed — limit concurrent `addImage` calls or Blob memory budget |
| `hash` CPU-bound at high throughput | Use hardware-accelerated SHA256 (SHA-NI instructions); increase chunk size |
| `db_insert_single` high p99 | SQLite WAL checkpoint stalls; tune `wal_autocheckpoint` or batch inserts |
