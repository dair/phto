# 0008 — NEF (Nikon RAW) Image Format Support via LibRaw

## Goal

Add NEF validation so that `.nef` files from Nikon cameras are accepted, validated, and stored like JPEG, PNG, and HEIC images are today. LibRaw is a system-installed library (like libheif), following the pattern established by `0007.HEIC`.

## Background

NEF (Nikon Electronic Format) is the RAW image format used by Nikon digital cameras. NEF files contain minimally processed sensor data, allowing photographers full control over post-processing. They are based on the TIFF/EP standard and use Nikon-proprietary compression and metadata structures.

**LibRaw** is the standard open-source library for reading camera RAW files. It supports over 1000 camera models across all major manufacturers. The `libraw-dev` Debian package provides headers at `/usr/include/libraw/` and a shared library. LibRaw exposes both a C++ class (`LibRaw`) and a C API (`libraw_*` functions). This validator will use the **C API** for consistency with the HEIC validator pattern and to keep the translation unit self-contained.

### Key differences from HEIC validator

| Aspect | HEIC (0007) | NEF (this plan) |
|--------|-------------|-----------------|
| Library | libheif (system) | LibRaw (system) |
| CMake integration | `find_package(libheif REQUIRED)` | `pkg_check_modules(LibRaw REQUIRED IMPORTED_TARGET libraw)` |
| File extensions | `.heic`, `.heif` | `.nef` |
| Magic bytes | ISOBMFF ftyp box at offset 4 | TIFF header: `II\x2A\x00` (little-endian) or `MM\x00\x2A` (big-endian) |
| Validation depth | Container parse + full pixel decode | RAW parse + unpack (no demosaic needed) |
| Scope | HEIF container family | Nikon NEF only (LibRaw supports many RAW formats, but we restrict to `.nef`) |

### Why only `.nef` and not all RAW formats?

LibRaw supports hundreds of RAW formats (CR2, CR3, ARW, ORF, RAF, DNG, etc.). Adding them all at once would be a large scope change. This plan adds NEF as the first RAW format, establishing the pattern. Additional RAW formats can be added later either by:
1. Extending this validator to accept more extensions (simple — just add extensions to `supportsExtension`), or
2. Creating per-manufacturer validators if different behavior is needed.

The validator implementation itself is format-agnostic — LibRaw handles all RAW formats through the same API. The extension restriction is purely at the facade adapter level.

## Validation strategy

Validation must confirm that the data is a structurally valid NEF file that LibRaw can parse and that contains decodable RAW sensor data. Unlike JPEG/PNG/HEIC where a full pixel decode is performed, for RAW files we unpack the sensor data but skip demosaicing (`dcraw_process`), which is computationally expensive and unnecessary for validation — unpacking already exercises the format parser and decompressor.

### Validation steps

1. **Quick rejection** — check minimum size (8 bytes) and verify TIFF header magic bytes at offset 0. NEF files are TIFF-based, so they start with either `II\x2A\x00` (little-endian, Intel byte order) or `MM\x00\x2A` (big-endian, Motorola byte order). If absent, return `WRONG`.
2. **Open from memory** — create a `libraw_data_t` via `libraw_init(0)`, then call `libraw_open_buffer()` to parse the RAW file structure from the in-memory buffer. This reads the TIFF/IFD structure, Nikon MakerNote, and image metadata. If this fails, classify the error (see below).
3. **Unpack RAW data** — call `libraw_unpack()` to decompress the actual sensor data. This exercises the Nikon-specific decompression codecs (lossy/lossless compressed NEF, uncompressed NEF) and catches data-level corruption. Failure → `INVALID`.
4. **Cleanup** — call `libraw_close()` to free all resources. Return `VALID`.

Using `libraw_open_buffer()` reads from the provided memory buffer without copying it. The buffer must remain valid for the lifetime of the `libraw_data_t`, which is satisfied since the processor is created and destroyed within the validation function.

### Why not `libraw_dcraw_process()`?

`libraw_dcraw_process()` performs demosaicing, white balance, color space conversion, and other post-processing. This is:
- **Computationally expensive** — orders of magnitude slower than unpack alone for large NEF files (24–50 MP sensors produce 50–100 MB RAW data)
- **Unnecessary for validation** — `libraw_unpack()` already fully decompresses the sensor data and would catch any structural or data corruption
- **Not what we're validating** — we care about file integrity, not post-processing correctness

The JPEG and PNG validators do full decode because those formats interleave structure and pixel data. RAW formats separate metadata/structure (parsed by `open_buffer`) from sensor data (decompressed by `unpack`), so unpacking is sufficient.

### RAII considerations

The LibRaw C API uses manual resource management (`libraw_init` / `libraw_close`). A `std::unique_ptr` with a custom deleter (matching the HEIC pattern) ensures cleanup on all paths:

```cpp
struct LibRawDeleter {
  void operator()(libraw_data_t* p) const noexcept {
    libraw_close(p);
  }
};
using LibRawPtr = std::unique_ptr<libraw_data_t, LibRawDeleter>;
```

`libraw_close()` handles full cleanup including any data allocated by `open_buffer` and `unpack`, so no intermediate `libraw_recycle()` call is needed when using the single-use pattern.

### Error classification

| LibRaw return code | Validator result | Rationale |
|---|---|---|
| `LIBRAW_SUCCESS` (0) | `VALID` | File parsed and unpacked successfully |
| `LIBRAW_FILE_UNSUPPORTED` (-2) | `WRONG` | Not a recognized RAW format |
| `LIBRAW_DATA_ERROR` (-100008) | `INVALID` | RAW data is corrupt |
| `LIBRAW_IO_ERROR` (-100009) | `INVALID` | I/O error during buffer read |
| `LIBRAW_UNSUFFICIENT_MEMORY` (-100007) | `INVALID` | Cannot allocate enough memory to unpack |
| `LIBRAW_REQUEST_FOR_NONEXISTENT_IMAGE` (-3) | `INVALID` | Container parsed but no image found |
| All other negative codes | `INVALID` | Treat any unexpected error as invalid |

For `libraw_open_buffer()` specifically: `LIBRAW_FILE_UNSUPPORTED` means the TIFF structure was parsed but the camera/format is not recognized — this maps to `WRONG` since the quick rejection already passed the TIFF check but the file is not actually a supported RAW.

## Public interface

### `nef_validator.h`

```cpp
#pragma once

#include <cstddef>

enum ValidationResult {
  INVALID = -1, // the input is NEF data that is actually broken
  VALID = 0,    // the input is valid NEF data
  WRONG = 1,    // the input is not NEF data at all
};

ValidationResult validateNef(const void* data, size_t dataSize);
```

This follows the exact same pattern as `heic_validator.h`, `jpeg_validator.h`, and `validate_png.h`: a single free function returning the same `ValidationResult` enum. The enum is defined locally per TU to avoid cross-validator conflicts.

## Facade integration

### `imager/NefValidatorImpl.cpp` (new file)

A new translation unit implementing the `validation::IValidator` adapter, exactly mirroring `HeicValidatorImpl.cpp`:

```cpp
#include "Validators.h"
#include "nef_validator.h"

namespace {

class NefValidator final: public validation::IValidator {
public:
  bool supportsExtension(const std::string& ext) const override {
    return ext == ".nef";
  }

  validation::ValidationResult validate(const uint8_t* data, size_t size) const override {
    switch (validateNef(data, size)) {
      case VALID:
        return {true, ""};
      case INVALID:
        return {false, "NEF data is corrupted or incomplete"};
      case WRONG:
        return {false, "Data is not a NEF file"};
    }
    return {false, "Unknown validation result"};
  }
};

} // namespace

namespace imager {

std::unique_ptr<validation::IValidator> createNefValidator() {
  return std::make_unique<NefValidator>();
}

} // namespace imager
```

## Validation implementation detail

### `nef_validator.cpp`

```cpp
#include "nef_validator.h"
#include <libraw/libraw.h>

#include <cstdint>
#include <cstring>
#include <memory>

namespace {

struct LibRawDeleter {
  void operator()(libraw_data_t* p) const noexcept {
    libraw_close(p);
  }
};

using LibRawPtr = std::unique_ptr<libraw_data_t, LibRawDeleter>;

} // namespace

ValidationResult validateNef(const void* data, size_t dataSize) {
    // Step 1: Quick rejection — check TIFF header magic
    if (!data || dataSize < 8) return WRONG;
    const auto* bytes = static_cast<const uint8_t*>(data);

    // TIFF little-endian: 49 49 2A 00
    // TIFF big-endian:    4D 4D 00 2A
    bool littleEndian = (bytes[0] == 0x49 && bytes[1] == 0x49 &&
                         bytes[2] == 0x2A && bytes[3] == 0x00);
    bool bigEndian    = (bytes[0] == 0x4D && bytes[1] == 0x4D &&
                         bytes[2] == 0x00 && bytes[3] == 0x2A);
    if (!littleEndian && !bigEndian) return WRONG;

    // Step 2: Create LibRaw processor and open from memory
    LibRawPtr raw{libraw_init(0)};
    if (!raw) return INVALID;

    int err = libraw_open_buffer(raw.get(), data, dataSize);
    if (err != LIBRAW_SUCCESS) {
        return (err == LIBRAW_FILE_UNSUPPORTED) ? WRONG : INVALID;
    }

    // Step 3: Unpack RAW sensor data
    err = libraw_unpack(raw.get());
    if (err != LIBRAW_SUCCESS) {
        return INVALID;
    }

    return VALID;
}
```

The TIFF magic check is intentionally broad — it passes any TIFF-based file through to LibRaw for format-specific identification. This means a regular TIFF or a Canon CR2 (also TIFF-based) would pass the quick check but then be classified by LibRaw. Since the extension gate at the facade level restricts input to `.nef` files, this broad check is safe and avoids duplicating format-specific magic byte parsing that LibRaw already handles.

## Risk: NEF file size for test fixtures

NEF files from real cameras are large (20–100 MB for modern Nikon bodies). A minimal test fixture is needed. Options:

1. **Use a public-domain sample** — several freely-licensed NEF samples exist online (e.g., from raw.pixls.us). A low-resolution sample from an older camera (e.g., Nikon D50, 6 MP) would be ~3–5 MB. This is larger than ideal for a test fixture but manageable.
2. **Craft a synthetic TIFF-based file** — construct a minimal TIFF/IFD structure that LibRaw can parse. This is fragile and may not exercise real NEF code paths.
3. **Use LibRaw's test infrastructure** — if LibRaw ships any minimal test files, reuse one.

**Recommended**: option 1 — find a small, freely-licensed NEF sample (ideally from a low-resolution camera) and commit it. Even at 3–5 MB this is acceptable for a test fixture. The truncated/corrupted variants are derived programmatically. If even this is too large, the test can be configured to look for a NEF file at a path specified by an environment variable, skipping gracefully if absent.

## Risk: LibRaw's broad format support

LibRaw will happily parse Canon CR2, Sony ARW, and many other TIFF-based RAW formats — not just NEF. The quick rejection step (TIFF magic check) deliberately does not distinguish between TIFF-based formats. This is safe because:

1. The facade extension gate restricts input to `.nef` files only — a CR2 file named `photo.cr2` would hit `UnsupportedFormat` before reaching this validator.
2. If a non-NEF RAW file were somehow fed to `validateNef` directly (bypassing the facade), LibRaw would still parse and unpack it correctly — it would just validate the wrong format, which is harmless for data integrity.
3. Adding more RAW format support later is trivial: add extensions to `supportsExtension` in the facade adapter, or create new adapter TUs.

## Comparison with HEIC system-library pattern

This follows the `0007.HEIC` pattern closely:

| Aspect | HEIC (0007) | NEF (this plan) |
|--------|-------------|-----------------|
| System library | `libheif-dev` | `libraw-dev` |
| CMake discovery | `find_package(libheif REQUIRED)` | `pkg_check_modules(LibRaw REQUIRED libraw)` |
| C API pattern | `heif_context_alloc` / `heif_context_free` | `libraw_init` / `libraw_close` |
| RAII wrapper | `unique_ptr` + custom deleter | `unique_ptr` + custom deleter |
| Validation depth | Container parse + full decode | RAW parse + unpack (no demosaic) |
| Extension scope | `.heic`, `.heif` | `.nef` |

The only structural difference is CMake discovery: libheif ships CMake config files, while LibRaw uses pkg-config. Both are standard CMake patterns for system libraries.

## Future: extending to other RAW formats

Once this plan is implemented, adding support for other RAW formats (CR2, CR3, ARW, ORF, RAF, DNG, etc.) becomes trivial because the validator implementation is format-agnostic. Two approaches:

1. **Extend this validator** — rename to `raw_validator`, add extensions to the facade adapter. Simplest approach if all RAW formats should share the same validation behavior.
2. **Per-format adapters** — keep `nef_validator` as-is, create `cr2_validator` etc. that all link to the same `raw_validator` static lib. More flexible if different formats need different behavior.

The choice can be deferred until the next RAW format is requested.
