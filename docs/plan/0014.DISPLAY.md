# 0014 — `imagestore` Progress Metrics Display

## Goal

Extend the `imagestore` batch import CLI to display progress metrics during file processing.
Concretely:

1. **Default mode** — print a rolling one-line progress report to stderr at regular intervals (every N files or every T seconds), showing throughput metrics drawn from the `libimager` metrics layer.
2. **`-q` / `--quiet` flag** — suppress all per-run progress and the final summary from stderr (fatal config/arg errors still print).
3. **`--graph` flag** — replace the plain-text periodic report with an animated, in-place pseudo-graph rendered in the terminal using ASCII/Unicode block characters, updating on the same cadence.

All metrics are already collected inside `libimager` via the `metrics::Metrics` object owned by `Imager`. The CLI accesses them through `img.metrics()`, which returns a `const metrics::Metrics&`. No library-side changes are needed.

---

## Current State Analysis

### How `imagestore` works today

`imagestore/main.cpp` is a single-file CLI (~400 lines, C++23):

1. **Arg parsing** — `getopt_long`, flags: `-c/--config`, `-e/--errors`, `-j/--jobs`, `-n/--dry-run`, `-v/--verbose`, `-h/--help`.
2. **Stdin reader** — reads paths line-by-line; skips empty lines and `#` comments; resolves to absolute paths; checks the skip-set from `ErrorFile`.
3. **Bounded concurrency** — a `std::counting_semaphore<256>` caps files in-flight at `--jobs` (default: `nproc`).
4. **Worker lambdas** — launched via `std::async`; each reads the file into a `Blob`, then calls either `img.addImage(blob, filename)` (normal) or `img.validateOnly(blob, filename)` (dry-run); updates atomic `Stats` counters.
5. **Verbose progress** — `ProgressTracker::maybeReport()` prints a `[progress] N/? processed …` line every 1000 files or every 5 seconds, but only when `--verbose` is active.
6. **Final summary** — always printed to stderr after all futures complete.

### The `Stats` struct (in-process)

```cpp
struct Stats {
  std::atomic<uint64_t> processed{0};
  std::atomic<uint64_t> added{0};
  std::atomic<uint64_t> duplicates{0};
  std::atomic<uint64_t> errors{0};
  std::atomic<uint64_t> skipped{0};
  std::atomic<uint64_t> totalBytes{0};
};
```

These capture the CLI-level outcome view (added/dup/error/skipped). They are complementary to — not a replacement for — the `libimager` metrics, which track pipeline-stage details.

### The `metrics::Metrics` object (library-owned)

Accessible via `img.metrics()` (const ref). Contains:

- `images_added`, `images_failed` — cumulative outcome counters
- `stage_read`, `stage_validated`, `stage_hashed`, `stage_dedup_checked`, `stage_stored`, `stage_db_inserted` — per-stage completion counters
- `stage_read_bytes`, `stage_validated_bytes`, `stage_hashed_bytes`, `stage_db_inserted_bytes`, `storage_bytes_written` — per-stage byte counters
- `inflight_reading`, `inflight_validating`, `inflight_hashing`, `inflight_waiting_mutex`, `inflight_dedup_checking`, `inflight_writing_storage`, `inflight_inserting_db` — live in-flight gauges
- All corresponding `_bytes` gauge variants
- `pool_queue_depth`, `pool_active_threads` — thread-pool health gauges

The `metrics::Metrics::snapshot()` method returns a `FullSnapshot` containing consistent point-in-time copies of all counters, gauges, and histograms.

### `ProgressTracker` today

`ProgressTracker::maybeReport()` uses only the local `Stats` struct and computes MB/s from wall-clock time. It is only called from worker lambdas when `--verbose` is set. There is no background thread; progress fires only when a file completes.

## Architecture Design

### Design principle: a dedicated progress-reporter background thread

The current approach (progress fires only from worker lambdas) is fundamentally event-driven and unsuitable for two reasons with the new requirements:

1. The default mode must show progress even without `--verbose` — i.e., always.
2. The `--graph` mode needs smooth animation; updates must come at wall-clock intervals, not only when a file completes.

The solution is a **dedicated background progress thread** that:
- starts just before the stdin reader loop begins
- polls `img.metrics()` + `Stats` at a fixed interval (e.g., 200 ms for smooth animation, or 1 s for plain text)
- renders to stderr
- stops (via a `std::stop_token` or `std::atomic<bool>`) after all futures are joined

This is the standard pattern for terminal progress indicators and has no ordering hazards — all data it reads is already atomic.

### Display mode selection

Three mutually exclusive output modes (a `DisplayMode` enum):

```
enum class DisplayMode { Normal, Quiet, Graph };
```

| Flag combination | Mode |
|-----------------|------|
| (neither) | Normal |
| `-q` | Quiet |
| `--graph` | Graph |
| `-q --graph` | Error or Quiet takes precedence (decide: error or quiet wins) |

**Decision needed**: if both `-q` and `--graph` are supplied, treat it as a usage error (they are contradictory) and exit with code 1.

### Normal mode

- Background thread fires every **1 second** (same cadence as the existing 5-second periodic report, but shortened for always-on use).
- Prints a single line to stderr, not in-place (no ANSI escape codes; safe for non-TTY / piped stderr):

  ```
  [progress] 4832 processed, 12 errors, 3 duplicates, 47.2 MB/s, 5 in-flight
  ```

- On completion, the final summary line replaces the last-printed value (it is always printed unless `-q`).
- The `--verbose` flag (existing) continues to print per-file `OK`/`DUP`/`ERR` lines in addition to the periodic summary. This is orthogonal to the progress reporter.

### Quiet mode (`-q`)

- No progress thread is launched.
- The final summary is suppressed.
- Fatal errors (config failure, arg error) still go to stderr.
- Exit code semantics unchanged (`0`, `1`, `2`).

### Graph mode (`--graph`)

- Background thread fires every **200 ms** (smooth animation).
- Uses ANSI escape sequences to clear and redraw a multi-line block in place:
  - Save cursor position at the start of the block (`\033[s` or `\033[<N>A` to move up after initial draw).
  - Overwrite lines on each tick.
- The graph block shows:
  1. A header line: elapsed time, overall files/s, MB/s.
  2. A pipeline stage table with a bar for each stage showing in-flight count relative to `--jobs`:

     ```
     Pipeline stages (in-flight / --jobs):
       read         [####            ]   4 /32   42 GB read
       validate     [#######         ]   8 /32   42 GB validated
       hash         [########        ]   9 /32   41 GB hashed
       mutex wait   [################]  18 /32   ← bottleneck
       dedup check  [                ]   0 /32
       storage      [##              ]   3 /32   41 GB stored
       db insert    [##              ]   2 /32   41 GB inserted
     ```
  3. A throughput line: `Throughput: 548 files/s, 2.3 GB/s`
  4. A thread-pool line: `Thread pool: 8/8 active, queue depth 3`

- Block height is fixed (known ahead of time — 4 + 7 pipeline rows = ~12 lines). The cursor is moved up by that many lines on each redraw.
- **TTY guard**: `--graph` is only meaningful on a real terminal. At startup, check `isatty(STDERR_FILENO)`. If stderr is not a TTY, fall back to Normal mode automatically (print a one-time warning: `--graph: stderr is not a TTY, falling back to normal progress`).
- **Terminal width**: read via `ioctl(STDOUT_FILENO, TIOCGWINSZ, ...)` at startup. Default to 80 columns if unavailable. The bar width = `terminal_width - 40` chars, clamped to `[10, 60]`.
- On exit, print a newline after the graph block so the shell prompt appears cleanly below.

### Bar rendering

The in-flight count for a stage (a `Gauge`) divided by `--jobs` gives the fill fraction. Use Unicode block elements for sub-character resolution:

```
Full:  █  (U+2588)
3/4:   ▊  (U+258A) — or keep binary (full/empty) for simplicity
Half:  ▌  (U+258C)
1/4:   ▎  (U+258E)
Empty: (space)
```

For simplicity in the initial implementation, binary full/empty (only `█` and space) is sufficient. Sub-character resolution can be added later.

Bar formula:
```
filled_chars = (inflight / jobs) * bar_width   (integer division)
```

### `ProgressReporter` class

Extract the display logic into a small class to keep `main.cpp` clean. Ownership model: constructed before the processing loop, destroyed (or `stop()`-ed) after all futures are joined.

```cpp
class ProgressReporter {
public:
  ProgressReporter(DisplayMode mode,
                   const imager::Imager& img,
                   const Stats& stats,
                   unsigned int jobs,
                   bool dryRun);
  ~ProgressReporter();     // calls stop() if not already stopped

  void stop();             // signals thread to exit, joins it
  void printFinalSummary(double elapsedSeconds) const;

private:
  void loop();             // thread entry point
  void renderNormal() const;
  void renderGraph();      // mutates m_graphLines (line count tracking)

  DisplayMode                 m_mode;
  const imager::Imager&       m_img;
  const Stats&                m_stats;
  unsigned int                m_jobs;
  bool                        m_dryRun;
  bool                        m_graphInitialized{false};
  int                         m_barWidth{40};
  std::atomic<bool>           m_stop{false};
  std::thread                 m_thread;
};
```

The thread is launched in the constructor (or via an explicit `start()` method — explicit start is slightly cleaner since it avoids the object being in an unusual state if construction throws).

### Interaction with existing `ProgressTracker`

`ProgressTracker` and `maybeReport()` are called only when `--verbose` is true. With the new `ProgressReporter` handling the normal/graph progress display, `maybeReport()` remains for the verbose per-1000-file report. There is no conflict:

- `ProgressReporter` renders the periodic line/graph to stderr from its background thread.
- `maybeReport()` (with `--verbose`) prints per-file status lines from worker threads.
- All stderr writes share `g_outputMutex` — **the graph mode must also take this mutex before writing escape sequences**, otherwise interleaving with verbose `OK`/`ERR` lines would corrupt the display.

**Implication for graph mode with `--verbose`**: `--graph --verbose` is a valid combination but the interleaving of per-file lines with in-place graph redraws will corrupt the terminal. Two options:

1. **Disallow**: treat `--graph --verbose` as a usage error.
2. **Allow with degraded output**: document that verbose lines intersperse; redraw re-synchronizes on the next tick.

**Recommendation**: disallow the combination (exit code 1). Verbose mode is for debugging; graph mode is for production monitoring. They serve different audiences.

### ANSI escape sequences needed for `--graph`

| Purpose | Sequence |
|---------|----------|
| Move cursor up N lines | `\033[NA` |
| Move cursor to column 1 | `\r` |
| Clear to end of line | `\033[K` |
| Hide cursor during animation | `\033[?25l` |
| Show cursor on exit | `\033[?25h` |

Hide/show cursor on entry/exit avoids cursor flicker during redraws. Use a RAII guard to ensure show-cursor is called even on signal/exception exit. To handle `SIGINT` cleanly: register a signal handler that sets `m_stop` and allows the destructor to show the cursor before exiting.

## Metrics Data to Display

### Normal mode line

All values from `Stats` (atomic) + wall-clock elapsed + byte counter from metrics:

```
[progress] 4832 processed, 12 errors, 3 duplicates, 47.2 MB/s, 5 in-flight
```

- `processed` = `stats.processed.load()`
- `errors` = `stats.errors.load()`
- `duplicates` = `stats.duplicates.load()`
- `MB/s` = `stats.totalBytes.load() / elapsed_seconds / (1024*1024)`
- `in-flight` = sum of all `inflight_*` file gauges from `img.metrics()`, OR simply `jobs - sem_available` (the semaphore does not expose its count directly; use metrics)

For in-flight count, the simplest source is the sum of the 7 `inflight_*` file gauges. This can momentarily exceed `--jobs` due to the non-atomic snapshot, but for display purposes the approximation is fine.

### Graph mode block

```
Elapsed: 23.4s   Files: 548/s   Throughput: 2.3 GB/s
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Pipeline stages   [  in-flight / jobs  ]  completed   bytes
  read            [████████            ]   8 / 32      42.1 GB
  validate        [███████████         ]  11 / 32      42.0 GB
  hash            [████████████        ]  12 / 32      41.9 GB
  mutex wait      [████████████████████]  20 / 32      (serialized)
  dedup check     [                    ]   0 / 32      41.8 GB
  storage write   [██                  ]   2 / 32      41.7 GB  2.3 GB written
  db insert       [██                  ]   2 / 32      41.7 GB
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Thread pool: 8/8 active  queue depth: 3
```

Data sources per row:

| Row | In-flight gauge | Completed counter | Bytes counter |
|-----|-----------------|-------------------|---------------|
| read | `inflight_reading` | `stage_read` | `stage_read_bytes` |
| validate | `inflight_validating` | `stage_validated` | `stage_validated_bytes` |
| hash | `inflight_hashing` | `stage_hashed` | `stage_hashed_bytes` |
| mutex wait | `inflight_waiting_mutex` | — | — |
| dedup check | `inflight_dedup_checking` | `stage_dedup_checked` | — |
| storage write | `inflight_writing_storage` | `stage_stored` | `storage_bytes_written` |
| db insert | `inflight_inserting_db` | `stage_db_inserted` | `stage_db_inserted_bytes` |

Header line metrics:
- Elapsed: wall clock from `startTime`
- Files/s: `stats.processed.load() / elapsed`
- Throughput (GB/s or MB/s): `stats.totalBytes.load() / elapsed`

Thread pool line:
- `pool_active_threads` (Gauge)
- `pool_queue_depth` (Gauge)
- Pool size is not directly exposed by `Metrics`; it can be stored separately (pass `jobs` to the reporter, or read the number of hardware threads). **Note**: `pool_active_threads` is the libimager coroutine thread pool size, which is independent of `--jobs`. For the display, show it as `N active` without a denominator unless the pool size is passed separately.

**Decision**: the libimager thread pool size is not exposed by `Imager`. For the graph, just show `pool_active_threads current` and `pool_queue_depth` without a denominator.

#### `ProgressReporter.h`

Declares:

- `class ProgressReporter` with the interface described in Architecture Design above.

#### `ProgressReporter.cpp`

Implements `renderNormal()`, `renderGraph()`, `loop()`.

**`renderNormal()`**: takes `g_outputMutex`, formats and prints one line to `std::cerr`.

**`renderGraph()`**:
- On first call, initialize `m_graphInitialized = true`, print the full block and record line count `m_blockLines`.
- On subsequent calls, emit `\033[<m_blockLines>A\r` to return to the top of the block, then redraw each line with `\033[K` suffix.
- Takes `g_outputMutex` for the entire redraw (prevents interleaving with worker `stderrLine()` calls).

**`loop()`**:
- Interval: 1000 ms for Normal, 200 ms for Graph.
- Exits when `m_stop.load()`.
- Uses `std::this_thread::sleep_for` in a loop (not `sleep_until`; the simplest correct approach).

**Bar rendering helper** (`renderBar(int filled, int total, int width)`):
```
int filledChars = (total > 0) ? (filled * width) / total : 0;
filledChars = std::min(filledChars, width);
std::string bar(filledChars, '\xE2\x96\x88');  // U+2588 FULL BLOCK
bar += std::string(width - filledChars, ' ');
```

Note: `█` is a 3-byte UTF-8 sequence. The `std::string(N, '\xE2\x96\x88')` approach will produce garbled output — use a proper UTF-8 string literal or write the bytes explicitly:
```cpp
static const char FULL_BLOCK[] = "\xe2\x96\x88"; // UTF-8 for U+2588
```
Alternatively, use plain `#` characters for ASCII-only operation (simpler, no encoding issues). The plan recommends starting with ASCII `#` and upgrading to Unicode block elements as a follow-on.

**TTY check** (in constructor, when mode == Graph):
```cpp
#include <unistd.h>
if (!isatty(STDERR_FILENO)) {
  std::cerr << "--graph: stderr is not a TTY, falling back to normal progress\n";
  m_mode = DisplayMode::Normal;
}
```

**Terminal width** (in constructor, when mode == Graph and TTY confirmed):
```cpp
#include <sys/ioctl.h>
struct winsize ws{};
if (ioctl(STDERR_FILENO, TIOCGWINSZ, &ws) == 0 && ws.ws_col > 0) {
  m_termWidth = ws.ws_col;
} else {
  m_termWidth = 80;
}
m_barWidth = std::clamp(m_termWidth - 44, 10, 60);
```

**Cursor hide/show** (graph mode only):
- Constructor: emit `\033[?25l` to stderr.
- Destructor (or `stop()`): emit `\033[?25h` to stderr.
- `SIGINT` handling: in `main()`, install a signal handler that sets a global `std::atomic<bool> g_interrupted{false}`. The `ProgressReporter` destructor always runs through normal control flow — no special signal handling needed in `ProgressReporter` itself, as long as the destructor is not bypassed. Use `std::signal` or `sigaction` with a flag-set-only handler; the main thread checks the flag and calls `progress.stop()` before exiting.

## Design Trade-offs and Decisions

### Decision 1: Background thread vs event-driven

**Chosen**: background thread. Event-driven (from worker lambdas) cannot provide smooth animation for `--graph` mode and cannot display progress when no files are completing (e.g., all files blocked at storage write).

### Decision 2: Snapshot via `img.metrics()` directly vs `FullSnapshot`

**Chosen**: read individual metric values directly (`.value()` on each Counter/Gauge), not via `Metrics::snapshot()`. Reason: `snapshot()` allocates vectors and formats strings — too expensive to call at 200 ms intervals for a terminal display. Direct `.value()` reads are single atomic loads, negligible cost.

### Decision 3: Mutex strategy for graph redraw

**Chosen**: take `g_outputMutex` for the entire graph redraw. This briefly serializes worker verbose output against the graph redraw. At 200 ms intervals, this lock hold time is microseconds and has no measurable impact.

**Alternative**: use a separate mutex for stderr writes; would require more refactoring and is not worth it.

### Decision 4: `--graph --verbose` and `--quiet --graph`

**Chosen**: both combinations are usage errors (exit code 1). Rationale: the combinations produce meaningless or contradictory output. Detecting them early gives clearer user feedback.

### Decision 5: Unicode vs ASCII for the bar

**Chosen**: ASCII `#` characters for the initial implementation. The bar rendering helper should be structured to make a later upgrade to Unicode block characters trivial (a single constant change).

**Future**: `█` (U+2588) with sub-character half-blocks for fractional fill.

### Decision 6: Normal mode always-on vs only with `--verbose`

**Chosen**: Normal mode progress is active by default (no flag required). This changes the existing behavior where progress only showed with `--verbose`. The `--verbose` flag now means "also print per-file OK/DUP/ERR lines" — it no longer controls whether progress is shown at all. The `-q` flag disables everything for quiet pipelines.

**Risk**: users who were piping stderr (`2>/dev/null`) will not notice the change. Users who were relying on no-progress-by-default may be surprised. Document clearly in usage.

### Decision 7: Progress reporter and `ProgressTracker` coexistence

**Chosen**: remove `ProgressTracker` entirely. The `ProgressReporter` background thread subsumes its functionality. There is no value in keeping both.

### Decision 8: `addFile` vs `addImage` in `main.cpp`

The current `main.cpp` calls `img.addImage(blob, filename)` after reading the file itself. Plan 0013 introduced `img.addFile(path)` which internalizes file reading into the library (making the `inflight_reading` gauge meaningful). This plan does not require migrating to `addFile`, but it is a natural follow-on that would make the `read` stage row in `--graph` show real data instead of zeros.

**Recommendation**: migrate `main.cpp` to `img.addFile(capturedPath)` as part of this implementation. The simplification is significant (removes ~30 lines of file-reading boilerplate per worker lambda) and makes `inflight_reading`/`stage_read`/`stage_read_bytes` display real values. This is included as an optional sub-step in Step 4.

## Potential Blockers

1. **`g_outputMutex` is `static` in `main.cpp`** — `ProgressReporter.cpp` needs access to it. Options:
   - Make it a member of `ProgressReporter` passed in via constructor (breaks the existing `stderrLine` function which is also in `main.cpp`).
   - Move `g_outputMutex` and `stderrLine` to a shared `Output.h` / `Output.cpp` helper.
   - Declare `g_outputMutex` in `main.cpp` and `extern` it in `ProgressReporter.cpp`.

   **Recommended**: move `g_outputMutex` and `stderrLine` to `imagestore/Output.h` (inline or separate `.cpp`). This is a clean separation. The mutex and helper are then included by both `main.cpp` and `ProgressReporter.cpp`.

2. **ANSI escape sequence support** — On some terminals or terminal emulators, `\033[NA` may not behave as expected. The TTY check (`isatty`) guards against non-TTY stderr. For terminals that don't support ANSI, graph mode may produce garbage. This is acceptable for a developer tool; add a note in usage.

3. **Signal handling for cursor restoration** — if the user presses `Ctrl+C` during graph mode, the cursor may remain hidden. A `SIGINT` handler that shows the cursor and exits cleanly is important for usability. This requires registering a `sigaction` or `std::signal` handler in `main()` that:
   - Sets `g_interrupted = true`
   - Calls `progress.stop()` (or the reporter's destructor handles it)
   - Breaks the stdin reading loop

4. **`--dry-run` with `--graph`** — dry-run mode does not call `addImage`, so `inflight_writing_storage` and `inflight_inserting_db` will always be 0. This is expected and visually correct (the graph will show a pipeline that stops at the hash stage). No special handling needed.

5. **`inflight_reading` always zero unless `addFile` is used** — see Decision 8 above. If `addImage` is retained, the `read` row in the graph will always show 0 in-flight. This is cosmetically undesirable but functionally correct.

## Overhead Analysis

| Operation | Cost | Notes |
|-----------|------|-------|
| Background thread at rest | ~0 CPU | `sleep_for(200ms)` — thread is blocked |
| `renderNormal()` lock + write | ~50 µs | Single `cerr` write, rare (1/s) |
| `renderGraph()` lock + write | ~200 µs | ~12 lines to stderr at 5/s max |
| Gauge `.value()` reads (14x) | ~70 ns | 14 atomic loads per render |
| Counter `.value()` reads (8x) | ~40 ns | 8 atomic loads per render |
| **Total reporter overhead** | **negligible** | Background thread sleeps 99.9% of the time |

The metrics reads are already atomic. There is no additional synchronization cost beyond what the processing loop already pays.
