# Plan 0022 — Backend Service: HTTP(S) REST API

## 1. Requirement

Turn the offline `libimager` core into a network-accessible daemon (Phase 2 in
[README](README.md)). The daemon exposes a REST API over HTTP(S) for an
**intranet** deployment with a **small, fixed set of users** and a large media
library.

Mandatory characteristics:

- **HTTP(S)** transport — Crow handles requests; native TLS optional, reverse
  proxy supported (§10).
- **Authentication, no third party.** No public/self-service registration. An
  **admin CLI tool** provisions and removes users. Auth is self-hosted: password
  login → Bearer JWT (`Authorization: Bearer <token>`), verified statelessly via
  `jwt-cpp`. Both libraries are already sanctioned for Phase 2 in
  [README §PHASE 2](README.md).
- **Users** are identified by `login`, carry a `full_name`, authenticate by
  `password`, and have an `is_admin` flag. The schema is built to admit
  additional auth methods later (§5.1) without a breaking migration.

Endpoints requested (PUT item, list items by tags incl. untagged, get item, get
tags for item, set/update tags) plus a fuller surface derived from the existing
facade (§6).

> **Status:** Proposal — design only. No code is written by this document.

## 2. Design constraints inherited from the project

| Constraint | Source | Consequence for the server |
|---|---|---|
| Public facade API is **synchronous**, thread-safe | `imager/Imager.h`, CLAUDE.md | Crow worker threads call `Imager` directly; one shared `Imager` instance. |
| `Database` uses `shared_mutex` + WAL, `SQLITE_THREADSAFE=1` | `database/CLAUDE.md` | Concurrent reads scale; writes serialize. No extra locking in handlers. |
| No new libraries without discussion | CLAUDE.md | Only **Crow** + **jwt-cpp** are added — both pre-approved. Password hashing reuses **OpenSSL** (already a dep); JSON uses **crow::json** (bundled). No nlohmann/argon2/bcrypt. |
| One library per top-level dir, no `include/`/`src/` | CODING.md | New libs `auth/`, `server/`, tool `imageradmin/` follow the flat layout. |
| Config read once at startup | CLAUDE.md | `[server]` and `[auth]` sections parsed at boot; no hot reload. |
| File identity = SHA256 hex (64 chars) | CLAUDE.md | Item ids in URLs are validated against `^[0-9a-f]{64}$` before any DB hit. |

## 3. New dependencies

| Library | Purpose | Integration | Notes |
|---|---|---|---|
| **Crow** | HTTP(S) server, routing, middleware, `crow::json` | FetchContent (`CrowCpp/Crow`, pinned tag) | Header-only. Requires **ASIO** — fetch `standalone-asio` (or `chriskohlhoff/asio`) via FetchContent and build Crow with `CROW_USE_BOOST=OFF`. |
| **jwt-cpp** | Issue/verify JWT (HS256) | FetchContent (`Thalhammer/jwt-cpp`, pinned tag) | Header-only. Uses OpenSSL (present) for HMAC; bundles picojson as its JSON traits. |

No password-hashing dependency: **PBKDF2-HMAC-SHA256 via OpenSSL
`PKCS5_PBKDF2_HMAC`** (§5.2). Argon2/bcrypt would each be a new dependency and
are intentionally declined for now; the stored algorithm tag (§5.1) lets us swap
later.

Both new deps are added in the top-level `CMakeLists.txt` next to the existing
`tomlplusplus` FetchContent block, pinned to explicit tags (mirroring `v3.4.0`).

```
  CMakeLists.txt

  App.h           .cpp     # wires routes + middleware onto a crow::App
  AuthMiddleware.h .cpp    # Crow middleware: extract/verify Bearer, set request context
```

`server/` depends on `imager`, `auth`, `config`, Crow, jwt-cpp.

in isolation. `imageradmin` depends on `auth` + `config` only — it never imports
Crow, so user provisioning works without the daemon running.

Top-level `CMakeLists.txt` gains: `add_subdirectory(auth)`,
`add_subdirectory(server)`, `add_subdirectory(imageradmin)`.

## 5. Authentication design

### 5.1 User store (`auth/UserStore`)

A dedicated SQLite database, **separate from the per-target image DBs** (those
are replicated and image-only). Path from `[auth].database`. Built in the
`database/` style: prepared statements, RAII handles, `shared_mutex`, WAL,
`busy_timeout`.

```sql
CREATE TABLE IF NOT EXISTS user (
    login         TEXT PRIMARY KEY NOT NULL,
    full_name     TEXT NOT NULL,
    pw_algo       TEXT NOT NULL,            -- "pbkdf2-sha256" (future: "argon2id", ...)
    pw_iterations INTEGER NOT NULL,
    pw_salt       BLOB NOT NULL,            -- 16 random bytes
    pw_hash       BLOB NOT NULL,            -- 32 bytes (SHA-256 output length)
    is_admin      INTEGER NOT NULL DEFAULT 0,
    enabled       INTEGER NOT NULL DEFAULT 1,
    created_at    INTEGER NOT NULL,         -- unix epoch seconds
    updated_at    INTEGER NOT NULL
);
```

`pw_algo`/`pw_iterations` are stored per-row so a future hash upgrade can run
lazily (re-hash on next successful login). `enabled=0` disables login without
deleting history. Additional auth methods (e.g. an API-key table, TOTP secret)
slot in as new columns/tables without touching this one.

`UserStore` API sketch:

```cpp
namespace auth {
struct User { std::string login, fullName; bool isAdmin, enabled;
              uint64_t createdAt, updatedAt; };

class UserStore {
public:
  explicit UserStore(const std::filesystem::path& dbPath);
  void create(const std::string& login, const std::string& fullName,
              const PasswordRecord& pw, bool isAdmin);
  void remove(const std::string& login);                 // throws NotFound
  void setPassword(const std::string& login, const PasswordRecord& pw);
  void setEnabled(const std::string& login, bool enabled);
  void setAdmin(const std::string& login, bool isAdmin);
  std::optional<User> get(const std::string& login);
  std::optional<PasswordRecord> getPassword(const std::string& login); // for verify
  std::vector<User> list(std::optional<db::Pagination> = std::nullopt);
  uint64_t count();
};
}
```

### 5.2 Password hashing (`auth/PasswordHash`)

PBKDF2-HMAC-SHA256 via OpenSSL — **no new dependency**.

- Salt: 16 bytes from `RAND_bytes`.
- Iterations: from `[auth].pbkdf2_iterations`, default **310000** (OWASP 2023
  guidance for PBKDF2-HMAC-SHA256).
- Output: 32 bytes via `PKCS5_PBKDF2_HMAC(..., EVP_sha256(), 32, out)`.
- Verify: re-derive with the stored salt/iterations, compare with
  `CRYPTO_memcmp` (constant-time). Never log or echo the password.

```cpp
namespace auth {
struct PasswordRecord { std::string algo; uint32_t iterations;
                        std::vector<uint8_t> salt, hash; };

PasswordRecord hashPassword(std::string_view password, uint32_t iterations);
bool verifyPassword(std::string_view password, const PasswordRecord& rec); // constant-time
}
```

### 5.3 Token service (`auth/TokenService`)

`jwt-cpp`, **HS256** with a server secret loaded once at boot from
`[auth].jwt_secret_file` (preferred) or `[auth].jwt_secret`. The secret must be
≥ 32 bytes; the daemon **refuses to start** if it is missing/short/world-readable.

Claims: `iss` (issuer from config), `sub` (login), `name` (full name),
`role` (`"admin"` | `"user"`), `iat`, `exp` (`iat + token_ttl_seconds`),
`jti` (random id, reserved for optional revocation, §13).

```cpp
namespace auth {
class TokenService {
public:
  TokenService(std::string secret, std::string issuer, uint32_t ttlSeconds);
  std::string issue(const User& u);                       // returns signed JWT
  struct Claims { std::string login, fullName; bool isAdmin; };
  std::optional<Claims> verify(std::string_view bearerToken); // checks sig+exp+iss
};
}
```

Verification is stateless (no DB hit) — the standard JWT tradeoff. A disabled or
deleted user keeps a valid token until expiry; with the default 12 h TTL this is
acceptable for an intranet. Immediate revocation is the optional `jti` blocklist
in §13.

### 5.4 Admin CLI (`imageradmin`)

Operates directly on the auth DB (no daemon required), mirroring the `dbcli`/
`imagestore` CLI conventions (exit codes `0`/`1`/`2`).

```
imageradmin <config.toml> <command> [args]
  user add    <login> <full name> [--admin]   # prompts for password (no echo) or --password-stdin
  user del    <login>
  user passwd <login>                          # prompts / --password-stdin
  user enable <login> | user disable <login>
  user promote <login> | user demote <login>
  user list   [--offset N] [--limit N]
```

Passwords are read from a no-echo TTY prompt or `--password-stdin`; never passed
as an argv argument (argv is visible in `ps`). First-run bootstrap: if the user
table is empty, `user add --admin` is allowed; otherwise normal rules apply.

## 6. REST API surface

Base path `/api/v1`. Request/response bodies are JSON (`crow::json`) except item
**content** upload/download, which is raw bytes. All endpoints except
`GET /health` and `POST /auth/login` require a valid Bearer token.

### 6.1 Auth

| Method | Path | Body | Returns |
|---|---|---|---|
| POST | `/auth/login` | `{ "login", "password" }` | `200 { token, expiresAt, login, fullName, isAdmin }` / `401` |
| GET  | `/auth/me` | — | `200 { login, fullName, isAdmin }` |
| POST | `/auth/password` | `{ "oldPassword", "newPassword" }` | `204` (self password change) |

### 6.2 Items

| Method | Path | Body / params | Returns |
|---|---|---|---|
| **PUT** | `/items` | raw bytes; `X-Filename` header (or `?filename=`) | `201 { id, duplicate:false }` new · `200 { id, duplicate:true }` existing · errors §7 |
| GET | `/items` | `?tags=a,b` (AND) · `?untagged=true` · none = all · `?offset`/`?limit` | `200 { items:[ImageInfo…], offset, limit }` |
| GET | `/items/{id}` | — | `200 ImageInfo` (incl. `tags`) / `404` |
| GET | `/items/{id}/content` | `Accept` / `?format=` (see [0023](0023.TRANSCODING.md)) | `200`/`206` bytes in a client-playable format (original or transcoded), `Content-Type` negotiated, `ETag`, `Cache-Control: immutable`, Range supported |
| DELETE | `/items/{id}` | — | `204` / `404` |

`PUT /items` rationale: identity is content-derived (SHA256), so re-uploading the
same bytes is **idempotent** — the defining property of PUT. The response
distinguishes a freshly stored item (`201`) from an existing duplicate (`200`,
`duplicate:true`) rather than treating a duplicate as an error.

### 6.3 Tags of an item

| Method | Path | Body | Returns |
|---|---|---|---|
| GET | `/items/{id}/tags` | — | `200 { tags:[...] }` |
| **PUT** | `/items/{id}/tags` | `{ "tags":[...] }` | `200 { tags:[...] }` — **replace** full set (UPDATE semantics) |
| POST | `/items/{id}/tags` | `{ "tags":[...] }` or `{ "tag":"x" }` | `200 { tags:[...] }` — **add** to set |
| DELETE | `/items/{id}/tags/{tag}` | — | `204` — remove one |

The requested "POST (or UPDATE?) tags" is resolved as: **PUT = replace the whole
set**, **POST = add**. Replace is the common edit-UI operation and must be
**atomic** — see the `setImageTags` facade addition in §8. Unknown tags in the
body are auto-created (`createTag`) before binding, matching CLI behavior.

### 6.4 Tags (global)

| Method | Path | Body | Returns |
|---|---|---|---|
| GET | `/tags` | `?offset`/`?limit` | `200 { tags:[...] }` |
| POST | `/tags` | `{ "name" }` | `201` / `409` if exists |
| DELETE | `/tags/{name}` | — | `204` (unbinds from all items) |

### 6.5 Users (admin only — `403` for non-admins)

| Method | Path | Body | Returns |
|---|---|---|---|
| GET | `/users` | `?offset`/`?limit` | `200 { users:[...] }` |
| POST | `/users` | `{ login, fullName, password, isAdmin }` | `201` / `409` |
| GET | `/users/{login}` | — | `200 User` / `404` |
| PATCH | `/users/{login}` | any of `{ fullName, password, isAdmin, enabled }` | `204` |
| DELETE | `/users/{login}` | — | `204` (guard: cannot delete last admin) |

### 6.6 Meta

| Method | Path | Auth | Returns |
|---|---|---|---|
| GET | `/health` | none | `200 { status:"ok" }` — liveness, no DB hit |
| GET | `/stats` | yes | `200 { imageCount, tagCount }` |

## 7. Error model & status mapping

Uniform JSON envelope on every error:

```json
{ "error": { "code": "BrokenFile", "message": "JPEG validation failed" } }
```

`code` is the stringified facade `imager::ErrorCode` (or an auth/transport code).
Mapping to HTTP:

| Facade / cause | HTTP | Notes |
|---|---|---|
| `Ok` (new) | 201 | PUT item created |
| `Ok` (existing) / duplicate | 200 | PUT item, `duplicate:true` |
| `DuplicateFile` (tag/user create) | 409 | resource already exists |
| `BrokenFile` | 422 | validation failed |
| `UnsupportedFormat` | 415 | extension not recognized |
| `TooLarge` | 413 | exceeds per-format limit / `max_upload` |
| `FileNotFound` | 404 | id/tag/user absent |
| `AmbiguousSidecar` | 409 | sidecar matches multiple parents |
| `StorageError` / `DatabaseError` / `ConfigError` | 500 | server fault; log detail, return generic message |
| missing/invalid/expired token | 401 | `WWW-Authenticate: Bearer` |
| authenticated but not admin | 403 | |
| malformed body / bad `id` format / bad pagination | 400 | reject before touching the facade |

`ErrorCode → (HTTP, string)` lives in one table in `server/Json.cpp` so the
mapping is single-sourced.

## 8. Required facade / DB additions

The server needs a few small additions to `libimager` / `database` to serve the
requested endpoints cleanly and efficiently:

1. **Untagged listing** (`GET /items?untagged=true`). The current
   `getImagesByTags` is AND-over-tags; it cannot express "items with *no* tags".
   Add:
   - `db::Database::getUntaggedFiles(std::optional<Pagination>)` — `SELECT … FROM
     file WHERE id NOT IN (SELECT file_id FROM file_tag)`.
   - `imager::Imager::getUntaggedImages(uint32_t offset, uint32_t limit)`.

2. **Atomic tag replace** (`PUT /items/{id}/tags`). Doing untag-all + tag-each in
   the handler is non-atomic and racy. Add:
   - `imager::Imager::setImageTags(const std::string& id,
     const std::vector<std::string>& tags)` — replaces the binding set in one DB
     transaction (auto-creating missing tags), kept consistent across all
     per-target DBs via the existing `MultiDatabase` all-or-nothing path.

3. **Zero-copy download** (`GET /items/{id}/content`). `getImageData` reads the
   whole file into a `Blob` — fine for images, heavy for multi-GB videos. Add:
   - `std::optional<std::filesystem::path> imager::Imager::getImagePath(const
     std::string& id)` — returns the on-disk path in the first available storage
     root, so Crow can stream the file (`crow::response` from file / sendfile)
     without buffering it in memory. `getImageData` remains for callers that want
     bytes. (Also consumed by the transcoding subsystem in
     [0023](0023.TRANSCODING.md), which adds format negotiation + a derivative
     cache on top of this endpoint; §6.2's raw-bytes behavior is the
     no-transcode baseline.)

These are additive (no breaking changes) and each ships with CPPUnit coverage in
`imager/test` / `database/test`.

## 9. Large uploads & memory

**Known constraint:** Crow buffers the full request body into `req.body`
(`std::string`) before the handler runs — there is no chunked/streaming request
body in the version we target. For a library with single-GB videos this matters.

Mitigation in this iteration:

- Enforce a hard cap: `[server].max_upload_mb` → reject oversized bodies with
  `413` (also short-circuits before the facade's per-format `TooLarge`).
- On `PUT /items`, **spool the received body to a temp file** and call
  `Imager::addFile(tempPath, filename)` rather than `addImage(blob)`. This routes
  large files through the existing streaming validate+hash path (`addFile`
  streams above the 256 MB threshold) and keeps only one in-flight copy, not two.
  The temp file is `unlink`ed after the call (success or failure).
- **Downloads** are already solved by `getImagePath` + file streaming (§8.3).

True streaming *uploads* (no full-body buffering) are deferred (§13). For very
large media the documented production recommendation is to terminate at a reverse
proxy that spools request bodies to disk (nginx `client_body_in_file_only`), or
to add a future chunked-upload endpoint.

## 10. TLS

Two supported deployments, selected by `[server].tls`:

- **Native TLS** (`tls = true`): build Crow with `CROW_ENABLE_SSL` and point it
  at `[server].tls_cert` / `[server].tls_key` (PEM). Crow uses OpenSSL (already a
  dependency).
- **Reverse-proxy TLS** (`tls = false`): the daemon serves plain HTTP on
  `127.0.0.1:<port>`; nginx/Caddy terminates TLS and forwards. Recommended for
  intranet ops (cert rotation, HTTP/2, request buffering for large uploads).

The plan implements native TLS and **documents** the proxy option; either
satisfies the HTTP(S) requirement.

## 11. Config additions (`config::AppConfig`)

Extend `config/Config.h` and the TOML parser:

```cpp
namespace config {
struct ServerConfig {
  std::string  bind          = "0.0.0.0";
  uint16_t     port          = 8443;
  bool         tls           = false;
  std::filesystem::path tlsCert, tlsKey;
  uint32_t     threads       = 0;          // 0 = hardware_concurrency
  uint64_t     maxUploadBytes = 4ull*1024*1024*1024;
};
struct AuthConfig {
  std::filesystem::path database;           // users DB (required for the daemon)
  std::string  jwtSecret;                   // inline (discouraged)
  std::filesystem::path jwtSecretFile;      // preferred
  uint32_t     tokenTtlSeconds  = 43200;    // 12 h
  std::string  issuer           = "phto";
  uint32_t     pbkdf2Iterations = 310000;
};
struct AppConfig {                          // existing fields kept
  std::vector<TargetConfig> targets;
  std::unordered_map<std::string,uint64_t> fileSizeLimits;
  ServerConfig server;                      // NEW
  AuthConfig   auth;                        // NEW

}
```

```toml
[server]
bind = "0.0.0.0"
port = 8443
tls  = true
tls_cert = "/etc/phto/tls/fullchain.pem"
```

## 12. Concurrency, lifecycle, observability

- **Single shared `Imager`** and single `auth::UserStore`/`TokenService`,
  constructed in `main.cpp` and referenced by all handlers (thread-safe APIs).
- Crow worker count = `[server].threads` (`0` → `hardware_concurrency`).
- **Graceful shutdown** on `SIGINT`/`SIGTERM`: stop accepting, drain in-flight,
  then destroy `Imager` (flushes/closes DBs).
- **Metrics:** the daemon already owns `Imager::metrics()`. Expose it read-only
  at `GET /stats` (and optionally a future `/metrics` Prometheus endpoint). Add
  request-level counters/histograms (per route, per status class) using the
  existing `metrics::` library — no new dependency.
- **Logging:** structured access log (method, path, status, bytes, latency,
  login) and an error log. Never log tokens, passwords, or full Authorization
  headers.

## 13. Security considerations

- **Transport:** TLS on (native or proxy). Bind to localhost when proxied.
- **Secrets:** JWT secret from a `0600` file outside the repo; refuse to start if
  missing/short/world-readable. Never in argv, logs, or git.
- **Passwords:** PBKDF2-HMAC-SHA256, per-user salt, constant-time verify; cost
  configurable. No password in argv (CLI prompts).
- **Brute force:** per-`login` + per-IP throttle/lockout on `/auth/login`
  (e.g. exponential backoff after N failures within a window). Implemented in the
  middleware with an in-memory counter (acceptable for a single-node intranet
  daemon).
- **Input validation:** ids must match `^[0-9a-f]{64}$`; tag/user names length-
  and charset-checked; pagination bounded (`limit ≤ 500`); body size capped
  before parsing.
- **AuthZ:** `requireAuth` on all data routes; `requireAdmin` on `/users`;
  "cannot delete/demote the last admin" guard.
- **Token revocation (optional / §future):** a `revoked_jti` table checked in
  `verify` gives immediate logout/disable at the cost of one indexed lookup per
  request. Ship stateless first; add if operationally needed.
- **CORS:** off by default (same-origin intranet UI). A `[server].cors_origins`
  allow-list can be added if a separate-origin frontend is introduced.
- **Security headers:** `X-Content-Type-Options: nosniff`, `Cache-Control:
  no-store` on JSON responses (immutable cache only on `/content`).

## 14. Testing strategy

### 14.1 Unit (CPPUnit, temp DBs, cleaned in `tearDown`)

- `auth/test/PasswordHashTest` — derive determinism, salt uniqueness, correct
  verify, wrong-password reject, tamper reject, constant-time path exercised.
- `auth/test/TokenServiceTest` — issue→verify round-trip, expired token rejected,
  wrong-secret/tampered signature rejected, wrong-issuer rejected, claims parsed.
- `auth/test/UserStoreTest` — CRUD, duplicate login → constraint, not-found,
  enable/disable, admin flag, pagination, concurrent access.
- `imager/test` / `database/test` — new `getUntaggedImages`/`getUntaggedFiles`,
  `setImageTags` (atomic replace, multi-target consistency), `getImagePath`.

### 14.2 Handler/integration (CPPUnit)

Construct the `crow::App` against temp image + auth DBs and drive routes via
Crow's in-process test handler (`app.handle(req)`), asserting status + JSON for:
login success/failure, missing/expired/tampered token → 401, non-admin → 403,
PUT new vs duplicate, unsupported/broken/oversized upload, get/list/by-tags/
untagged, tag PUT-replace vs POST-add vs DELETE-one, user CRUD + last-admin guard.

### 14.3 End-to-end shell test

`server/test/test_api.sh.in` (mirrors `imagestore/test/test_cli.sh.in`): start
`imagerd` on an ephemeral port with a temp config, `imageradmin user add` an
admin, then exercise the full flow with `curl` — login, PUT a fixture image, GET
it back (compare bytes), tag/list/untagged, 401/403 paths, shut down. Reuse
existing fixtures (e.g. `validations/*/test/fixtures`).

## 16. Implementation steps — small resumable checkpoints

The work is split into **session-sized checkpoints**. Each one is sized so it can
be completed comfortably within a single working session, and — critically — each
ends at a **clean, committable boundary**:

> **Checkpoint invariant.** Every step below leaves the tree **building**
> (`cmake --build --preset default`) and **green** (`ctest --preset default`), and
> is a **single commit inside `imager/`** (then a superproject pin bump). If a
> session ends after step *N*, nothing is half-done: the next session starts
> fresh at step *N+1*. No checkpoint depends on uncommitted scratch state.

Steps are grouped into milestones. Within a milestone, steps are ordered; across
milestones, only the listed dependencies matter — **M-D (facade/DB) and M-A/M-B
(config/auth) are independent of each other** and can be done in either order or
interleaved across sessions. The server milestones (M-E…M-I) need M-A done, and
each route step needs its facade dependency from M-D.

### 16.1 Minimal first-usable slices

If you want a runnable artifact as early as possible (to de-risk before investing
in the full surface), these are the natural "it works" milestones — each is a
strict prefix of the table above:

- **After A1–A2 + B1–B3 + C1:** user provisioning works (`imageradmin`) with no
  server yet — independently useful and fully testable.
- **After +E1–E2 + F1:** a running, authenticating daemon (`/health`, `/auth/login`,
  `/auth/me`) — the smallest end-to-end "log in" demo.
- **After +G1 + G3:** upload and download items with auth — the core media loop.
- Everything after that (G2, H, I, J) is additive surface on a working base.
