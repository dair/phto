# 0016 — Verbose Output Redesign: Real-Time File Status Display

## Goal

Redesign `imagestore`'s output behavior to provide two clearly distinct modes:

1. **Verbose mode (`-v`, TTY-only)**: A real-time, in-place terminal display showing which files are currently being processed, what pipeline stage each is at, aggregate statistics, and a scrolling result log at the bottom.
2. **Normal mode (default)**: Only result log lines (OK/DUP/ERR/SKIP), no runtime status. Silent during processing; final summary at end.

Additionally, the existing `--graph` mode is removed entirely as part of this redesign. The new verbose mode subsumes its purpose (real-time pipeline visibility) with a superior per-file view.

This replaces the current behavior where `-v` prints interleaved per-file lines to stderr and Normal mode prints periodic `[progress]` lines.

---

## Current State

### What exists today

| Mode | Behavior |
|------|----------|
| Normal (default) | Background thread prints `[progress] N processed, ...` every 1s to stderr |
| `-v` (verbose) | Per-file `OK`/`DUP`/`ERR`/`SKIP` lines printed inline from worker threads |
| `-q` (quiet) | No output at all (no progress, no summary) |
| `--graph` | Animated ASCII pipeline graph (TTY required, mutually exclusive with `-v`) — **removed in this plan** |

### Problems with current design

1. **Normal mode is noisy**: Periodic `[progress]` lines pollute stderr when piping. Users who want clean machine-parseable output get unwanted progress lines.
2. **Verbose mode is unstructured**: Per-file lines interleave unpredictably from concurrent workers. No indication of *what's happening now* — only what *completed*.
3. **No visibility into in-flight work**: There's no way to see which files are currently being read, validated, hashed, or written without `--graph` (which only shows aggregate counts, not filenames).
4. **`--graph` mode is over-engineered for its value**: It provides a detailed pipeline stage view but only shows aggregate in-flight counts — not which files are where. The new verbose mode provides strictly more useful information (per-file stage tracking + result log + statistics), making `--graph` redundant.

### Key components

- **`Output.h`**: `g_outputMutex` (inline global mutex) + `stderrLine()` helper
- **`ProgressReporter`**: Background thread, renders Normal or Graph mode — graph rendering code to be removed
- **`DisplayMode` enum**: `Normal`, `Quiet`, `Graph` — `Graph` to be removed
- **`Stats` struct**: Atomic counters (processed/added/duplicates/errors/skipped/totalBytes)
- **`metrics::Metrics`**: Rich pipeline-stage gauges and counters from libimager
- **TTY detection**: Already in `ProgressReporter.cpp` via `isatty(STDERR_FILENO)` + `ioctl` for terminal size

## Requirements

### Verbose Mode (`-v`)

When stderr is a TTY and `-v` is passed:

```
 [validating]      00h:01m:24s  photo_001.jpg        
 [hashing]         00h:00m:20s  photo_002.jpg        
 [reading]         00h:01m:12s  vacation/IMG_3041.cr2 
 [writing storage] 00h:02m:43s  photo_003.png 
 [inserting db]    00h:00m:5s   photo_004.heic       
 [idle]            00h:10m:31s
 [idle]            00h:11m:42s
 [idle]            00h:12m:34s
 
─────────────────────────────────────────────────────────
 Processed: 1,847  Written: 1,201  Skipped: 12  Errors: 3  DUP: 631
 Throughput: 124 files/s  287.3 MB/s  Elapsed: 14.9s
─────────────────────────────────────────────────────────
 OK   photo_000.jpg -> a1b2c3d4e5f610928347012984370198.jpg
 DUP  vacation/IMG_3038.jpg == a2893746298734bf29384798237498.jpg
 ERR  path/to/broken_file.jpg: JPEG validation failed: truncated
 OK   path/to/another/photo_0001.heic -> f7e8d9c0b1a22139182736481276349871.heic
 OK   vacation/IMG_3039.jpg -> 1092837409182743012fba2324.jpg
```

**Top section** — "Slot display": One line per in-flight file (up to `--jobs` slots). Each line shows the filename (truncated to fit, skipping the front side to fit), the time elapsed in this stage and its current pipeline stage in brackets. Idle slots are showin with [idle] line with elapsed time for this slot to remain idle. This section is redrawn in-place every 200ms.

**Middle section** — "Statistics bar": Two lines showing aggregate counters and throughput. Updated in-place on each refresh.

**Bottom section** — "Result log": Scrolling log of completed file outcomes. New lines are appended as files complete. This section scrolls naturally (not redrawn in-place). Limited to the remaining terminal height below the fixed sections. Shows full name for source files, only hash+extension for result files

**Layout strategy**: The top section (slots + stats) occupies a fixed number of lines at the top of the display. The result log occupies everything below. On each refresh tick, the top section is redrawn in-place using ANSI cursor movement. Result log lines are appended below.

When stderr is **not** a TTY and `-v` is passed: fall back to the current per-file line behavior (no in-place rendering). Print a one-time notice: `verbose: stderr is not a TTY, using line-based output`.

### Normal Mode (default)

- **No periodic progress lines**. Stderr is clean during processing.
- Per-file result lines (OK/DUP/ERR/SKIP) are printed just like in the verbose mode.
- The final summary line is printed at completion.
- This makes Normal mode safe for piping (`2>errors.log`) and non-TTY contexts.

### Unchanged Modes

- **`-q` (quiet)**: No output at all. No change.

### Removed Modes

- **`--graph`**: The animated ASCII pipeline graph mode is removed entirely. Its purpose (real-time pipeline visibility) is subsumed by the new verbose mode, which provides per-file stage tracking rather than just aggregate in-flight counts. See the "Graph Mode Removal" section below for details.

### New Components

#### 1. `SlotTracker` — Per-File Stage Tracking

Tracks which files are currently in-flight and what pipeline stage each is at. This is the **new** component that doesn't exist today.

```cpp
// imagestore/SlotTracker.h
#pragma once

#include <array>
#include <mutex>
#include <string>
#include <vector>

namespace imagestore {

enum class PipelineStage : uint8_t {
  Reading,
  Validating,
  Hashing,
  WaitingMutex,
  DedupChecking,
  WritingStorage,
  InsertingDb,
  Idle,
};

const char* stageName(PipelineStage stage);

struct SlotInfo {
  std::string filename;
  PipelineStage stage{PipelineStage::Idle};
};

/// Thread-safe tracker for per-file pipeline stage.
/// Each in-flight file gets a "slot" (0..jobs-1).
/// Workers acquire a slot on entry, update its stage as they
/// progress, and release it on completion.
class SlotTracker {
public:
  explicit SlotTracker(unsigned int maxSlots);

  /// Acquire a slot for the given filename. Returns slot index.
  /// Called by the worker thread when it starts processing a file.
  unsigned int acquire(const std::string& filename);

  /// Update the stage for a slot. Called as the file moves through
  /// the pipeline.
  void setStage(unsigned int slot, PipelineStage stage);

  /// Release a slot. Called when file processing completes.
  void release(unsigned int slot);

  /// Take a snapshot of all slots for rendering. Lock-free for
  /// the reader if we use a double-buffer approach, but a simple
  /// mutex snapshot is fine at 200ms intervals.
  std::vector<SlotInfo> snapshot() const;

  /// Number of active (non-idle) slots.
  unsigned int activeCount() const;

private:
  mutable std::mutex m_mutex;
  std::vector<SlotInfo> m_slots;
  unsigned int m_maxSlots;
};

} // namespace imagestore
```

**Thread safety**: Protected by a single mutex. At 200ms render intervals and sub-microsecond lock hold times, contention is negligible. Workers call `acquire`/`setStage`/`release` from their threads; the render thread calls `snapshot()`.

**Stage tracking mechanism**: The worker thread in `main.cpp` currently calls `img.addFile(path)` which is a single synchronous call. The library doesn't provide stage-change callbacks. Two approaches:

**Approach A — Callback-based (requires libimager change)**:
Add a `StageCallback` parameter to `addFile` that the library calls as the file transitions between stages. This is the cleanest approach but requires a library API change.

**Approach B — Metrics polling (no library change)**:
The render thread polls `inflight_*` gauges and maps them to stages. However, this only gives aggregate counts, not per-file stage information. To get per-file stages, we'd need to track which files entered/exited each stage.

**Approach C — Wrapper with per-stage calls (no library change)**:
Instead of calling `img.addFile(path)`, break the pipeline into explicit steps in the worker: read file, call `img.addImage(blob, filename)`. Since `addImage` is synchronous, we can't observe internal stages. But we can at least track "reading" vs "processing" stages.

**Recommended: Approach A** — Add a lightweight callback interface to `Imager::addFile`. This is a small, backward-compatible change (callback defaults to `nullptr`) and gives the cleanest result. The alternative (Approach C) only gives two stages (reading/processing), which is too coarse for the slot display.

#### 2. `StageCallback` — Library-Side Stage Notification

```cpp
// imager/Types.h (or a new imager/StageCallback.h)

namespace imager {

enum class ProcessingStage : uint8_t {
  Reading,
  Validating,
  Hashing,
  WaitingMutex,
  DedupChecking,
  WritingStorage,
  InsertingDb,
};

/// Optional callback invoked when a file transitions to a new pipeline stage.
/// Must be thread-safe — multiple files call this concurrently.
/// Implementations must be fast (no blocking, no allocation).
using StageCallback = std::function<void(ProcessingStage stage)>;

} // namespace imager
```

Updated `addFile` signature:

```cpp
AddResult addFile(const std::filesystem::path& path,
                  const std::string& filename = "",
                  StageCallback onStage = nullptr);
```

Inside `Imager::addFile` and `Imager::addImage`, the callback is invoked at each stage transition. The callback is cheap: a single virtual call or `std::function` invocation. The worker thread in `main.cpp` captures its slot index and calls `slotTracker.setStage(slot, ...)` in the callback.

#### 3. Updated `ProgressReporter` — Rendering Engine

The existing `ProgressReporter` is extended with a new render method for verbose mode. The `DisplayMode` enum gains a new value:

```cpp
enum class DisplayMode {
  Normal,   // final summary only (changed from current behavior)
  Verbose,  // real-time slot display + result log (new)
  Quiet,    // no output
};
```

Note: `Graph` is removed from the enum as part of this plan (see "Graph Mode Removal" section).

**Verbose rendering** (`renderVerbose()`):

The display is split into two regions:

1. **Fixed region** (top): Redrawn in-place every 200ms. Contains:
   - Slot lines (one per active file + idle count)
   - Separator
   - Statistics lines
   - Separator

2. **Scrolling region** (bottom): Result log lines appended as files complete. Uses ANSI scrolling region (`\033[<top>;<bottom>r`) to confine scrolling to the bottom portion, keeping the top fixed.

**ANSI terminal regions**:
```
\033[<top>;<bottom>r    Set scrolling region (rows top..bottom)
\033[<row>;<col>H       Move cursor to absolute position
\033[K                   Clear to end of line
\033[?25l / \033[?25h    Hide/show cursor
```

On startup (verbose TTY mode):
1. Query terminal height via `ioctl(STDERR_FILENO, TIOCGWINSZ, ...)`
2. Calculate fixed region height: `min(jobs, 20) + 4` lines (slots + separators + stats)
3. Set scrolling region to bottom portion: `\033[<fixed+1>;<term_height>r`
4. Position cursor at top for initial draw

On each 200ms tick:
1. Save cursor position
2. Move cursor to row 1, column 1
3. Redraw all slot lines + stats (with `\033[K` to clear trailing chars)
4. Restore cursor position (back to scrolling region)

When a file completes (from worker thread):
1. Take `g_outputMutex`
2. Save cursor, move to scrolling region
3. Print result line (OK/DUP/ERR)
4. Restore cursor

**Fixed region height cap**: Even with `--jobs 256`, displaying 256 slot lines is impractical. Cap the slot display at `min(jobs, maxDisplaySlots)` where `maxDisplaySlots = min(20, termHeight - 10)`. Show remaining active slots as `(+N more in-flight)`.

#### 4. `ResultLog` — Thread-Safe Result Buffer

Result log lines from worker threads need to be buffered and rendered in the correct terminal region. In non-TTY verbose mode, they go directly to stderr. In TTY verbose mode, they must be written into the scrolling region.

```cpp
// imagestore/ResultLog.h
#pragma once

#include <mutex>
#include <string>
#include <vector>

namespace imagestore {

class ResultLog {
public:
  /// Append a result line. Thread-safe.
  /// In TTY mode, writes to the scrolling region.
  /// In non-TTY mode, writes directly to stderr.
  void append(const std::string& line);

  /// Set TTY mode. When true, result lines are written using
  /// ANSI escape sequences to position in the scrolling region.
  void setTtyMode(bool tty, int scrollTop = 0);

private:
  std::mutex m_mutex;
  bool m_tty{false};
  int m_scrollTop{0};
};

} // namespace imagestore
```

In TTY mode, `append()` acquires `g_outputMutex`, saves cursor position, moves cursor to the scrolling region's current write position, prints the line, and restores cursor. The scrolling region's `\033[<top>;<bottom>r` setting means any print in that region auto-scrolls older lines up.

### Data Flow

```
Worker thread                    SlotTracker              ProgressReporter        ResultLog
     │                               │                         │                     │
     │ acquire(filename) ───────────►│                         │                     │
     │                               │                         │                     │
     │ img.addFile(path, "",         │                         │                     │
     │   [slot](stage) {             │                         │                     │
     │     tracker.setStage(         │                         │                     │
     │       slot, stage) ──────────►│                         │                     │
     │   })                          │                         │                     │
     │                               │   snapshot() ◄─────────│ (every 200ms)       │
     │                               │──────────────────────►  │                     │
     │                               │                         │ renderVerbose()     │
     │                               │                         │                     │
     │ (file completes)              │                         │                     │
     │ release(slot) ───────────────►│                         │                     │
     │                               │                         │                     │
     │ resultLog.append("OK ...") ──────────────────────────────────────────────────►│
     │                               │                         │                     │ (write to
     │                               │                         │                     │  scroll region)
```

### Normal Mode Changes

Normal mode becomes **silent during processing**:

- The background thread in `ProgressReporter` does NOT call `renderNormal()` anymore.
- No `[progress]` lines are printed.
- Per-file result lines are NOT printed (no `OK`/`DUP`/`ERR` lines).
- Only the final summary is printed at the end.

This is a behavioral change from the current Normal mode. The rationale: Normal mode should be clean for piping and non-interactive use. Users who want visibility use `-v` (verbose).

### Verbose Non-TTY Fallback

When `-v` is passed but stderr is not a TTY:

- No in-place rendering (no ANSI escapes)
- Per-file result lines are printed directly to stderr as they complete (current `-v` behavior)
- No slot display, no statistics bar
- Final summary is printed at end

This preserves the current behavior for `imagestore -v 2>log.txt`.

## Detailed Rendering Specification

### Slot Line Format

```
 Processing: <filename>        [<stage>]
```

- Filename is right-truncated with `...` to fit: `max_filename_len = termWidth - 20` (20 chars for ` Processing: ` prefix + ` [<stage>]` suffix)
- Stage names: `reading`, `validating`, `hashing`, `waiting`, `dedup check`, `writing`, `db insert`
- Idle slots collapsed: `(N idle slots)` on a single line

### Statistics Bar Format

```
 Processed: 1,847  Written: 1,201  Skipped: 12  Errors: 3  DUP: 631
 Throughput: 124 files/s  287.3 MB/s  Elapsed: 14.9s
```

Numbers use comma-separated thousands for readability. "Written" = `stats.added`, corresponds to files that were actually new and stored. "DUP" = `stats.duplicates`.

### Result Log Line Format

```
 OK   <hash-prefix>... <filename>
 DUP  <filename>
 ERR  <filename>: <error message>
 SKIP <filename> (in error list)
```

Hash prefix is first 12 chars of the SHA256 hex for OK results.

### Separator

```
─────────────────────────────────────────────────────────
```

Single-line dash separator, width = `termWidth - 2`. ASCII dash (`-`) for compatibility; Unicode box-drawing (`─`, U+2500) if UTF-8 locale is detected. Start with ASCII.

## Library-Side Changes

### `Imager::addFile` — Stage Callback Parameter

Add an optional `StageCallback` parameter to `addFile`:

```cpp
// imager/Types.h
namespace imager {

enum class ProcessingStage : uint8_t {
  Reading,
  Validating,
  Hashing,
  WaitingMutex,
  DedupChecking,
  WritingStorage,
  InsertingDb,
};

using StageCallback = std::function<void(ProcessingStage stage)>;

} // namespace imager
```

```cpp
// imager/Imager.h
AddResult addFile(const std::filesystem::path& path,
                  const std::string& filename = "",
                  StageCallback onStage = nullptr);
```

**Implementation change in `Imager.cpp`**: At each existing gauge guard point (where `SizedGaugeGuard` is constructed), invoke the callback if non-null:

```cpp
// Inside addImage (called by addFile):
if (onStage) onStage(ProcessingStage::Validating);
{
  SizedGaugeGuard sg(...);
  // validate
}

if (onStage) onStage(ProcessingStage::Hashing);
{
  SizedGaugeGuard sg(...);
  // hash
}
// ... etc for each stage
```

The `addFile` method invokes `onStage(ProcessingStage::Reading)` before the file read, then passes the callback through to `addImage` (or a new internal overload that accepts the callback).

**Backward compatibility**: The default `nullptr` callback means zero overhead for existing callers. The `std::function` is only invoked if non-null.

### Internal `addImage` overload

To thread the callback through, add a private overload:

```cpp
// Private in Imager (or in Impl)
AddResult addImageImpl(const Blob& blob, const std::string& filename,
                       StageCallback onStage);
```

The public `addImage` calls `addImageImpl` with `nullptr`. The public `addFile` calls `addImageImpl` with the provided callback.

## Graph Mode Removal

The `--graph` mode (plan 0014) is removed entirely as part of this redesign. The new verbose mode provides strictly superior functionality.

### Rationale

`--graph` displays an animated ASCII pipeline graph with aggregate in-flight counts per stage (e.g., "8 validating, 5 hashing"). The new verbose mode replaces this with:

- **Per-file visibility**: See exactly which files are at which stage, not just counts.
- **Result log**: See outcomes as they happen, not just at the end.
- **Statistics bar**: Same aggregate throughput data that `--graph` provided.

The two modes serve the same audience (interactive monitoring) and cannot coexist on the same terminal. Rather than maintaining two complex TTY rendering codepaths, we consolidate into one.

### What is removed

| Component | Location | Action |
|-----------|----------|--------|
| `DisplayMode::Graph` | `imagestore/DisplayMode.h` | Remove enum value |
| `--graph` CLI flag | `imagestore/main.cpp` | Remove from `longOpts[]`, remove `bool graphMode`, remove from `printUsage()` |
| Graph mutual-exclusion checks | `imagestore/main.cpp` | Remove `quiet && graphMode` and `graphMode && verbose` checks |
| `DisplayMode::Graph` resolution | `imagestore/main.cpp` | Remove `else if (graphMode)` branch |
| `renderGraph()` method | `imagestore/ProgressReporter.h/.cpp` | Remove declaration and implementation |
| Graph-specific members | `imagestore/ProgressReporter.h` | Remove `m_graphInitialized`, graph-specific `m_barWidth`, `m_termWidth` |
| Graph rendering helpers | `imagestore/ProgressReporter.cpp` | Remove `BAR_CHAR`, `renderBar()`, `fmtBytes()` (or retain `fmtBytes` if reused by verbose stats) |
| Graph TTY detection | `imagestore/ProgressReporter.cpp` | Remove graph-specific `isatty`/`ioctl` in constructor (will be replaced by verbose TTY setup) |
| Graph cursor management | `imagestore/ProgressReporter.cpp` | Remove cursor hide in constructor (`\033[?25l`) and cursor show in `stop()` (`\033[?25h`) for graph mode (will be replaced by verbose equivalents) |
| Graph interval | `imagestore/ProgressReporter.cpp` | Remove `200ms` graph interval in `loop()` (verbose mode will add its own 200ms interval) |
| `renderNormal()` periodic call | `imagestore/ProgressReporter.cpp` | Remove — Normal mode becomes silent (no background thread output) |

### What is retained

- `fmtBytes()` helper — reused by verbose statistics bar (move to a shared utility if needed)
- TTY detection pattern (`isatty` + `ioctl`) — reused by verbose mode with different setup logic
- `g_outputMutex` and `stderrLine()` — unchanged, still used by verbose non-TTY fallback and result logging
- `ProgressReporter` class structure — retained and extended for verbose mode

## Design Decisions

### Decision 1: Per-File Stage Tracking (SlotTracker) vs Aggregate Gauges

**Chosen**: Per-file tracking via `SlotTracker` with library-side stage callbacks.

**Alternative**: Poll aggregate `inflight_*` gauges and display only counts (e.g., "3 reading, 5 validating"). This requires no library change but provides no filename visibility — the core value proposition of verbose mode.

**Trade-off**: Requires a small library API change (`StageCallback` parameter on `addFile`). This is backward-compatible and minimal.

### Decision 2: Normal Mode — Silent vs Periodic Progress

**Chosen**: Normal mode is silent during processing (final summary only).

**Alternative**: Keep the current periodic `[progress]` line.

**Rationale**: The periodic line is noise for scripts and pipelines. Users who want runtime visibility should use `-v` (interactive). Clean default output is more valuable than unsolicited progress.

### Decision 3: ANSI Scrolling Region vs Manual Cursor Management

**Chosen**: Use ANSI scrolling regions (`\033[<top>;<bottom>r`) to split the terminal into a fixed top and scrolling bottom.

**Alternative**: Manual cursor management — track the exact row for each result line, move cursor explicitly for every write.

**Trade-off**: Scrolling regions are simpler and work correctly when result log lines exceed the visible area (they auto-scroll within the region). Manual tracking would require maintaining a line counter and handling scroll-back, which is error-prone.

### Decision 4: Slot Display Cap

**Chosen**: Cap at `min(jobs, 20, termHeight - 10)` displayed slots.

**Rationale**: With `--jobs 256`, displaying 256 lines leaves no room for the result log. A cap of 20 gives useful visibility while reserving space for results and stats.

### Decision 5: Verbose Non-TTY Fallback

**Chosen**: Fall back to current per-file line output (no ANSI). Print a one-time notice.

**Alternative**: Refuse to run verbose mode without a TTY.

**Rationale**: Per-file lines are still useful in log files. The notice informs the user that the full experience requires a TTY.

### Decision 6: StageCallback via std::function vs Virtual Interface

**Chosen**: `std::function<void(ProcessingStage)>`.

**Alternative**: A `class IStageObserver` with a virtual `onStage()` method.

**Rationale**: `std::function` is simpler for a single callback. The overhead of `std::function` invocation (~10-20ns) is negligible compared to the I/O in each pipeline stage. No need for a full observer pattern.

### Decision 7: Remove `--graph` rather than keep both modes

**Chosen**: Remove `--graph` entirely.

**Alternative**: Keep `--graph` alongside `-v` verbose mode.

**Rationale**: Both modes serve the same audience (interactive terminal monitoring) and compete for the same screen space. The new verbose mode provides strictly more information (per-file stages vs aggregate counts, plus a result log). Maintaining two complex TTY rendering codepaths increases code surface and testing burden for no user benefit. Clean removal simplifies the codebase.

### Decision 8: Where to invoke the callback in the library

**Chosen**: At the same points where `SizedGaugeGuard` is constructed — these are the natural stage boundaries.

**Rationale**: The gauge guards already mark exact stage transitions. Adding a callback invocation adjacent to each guard is minimal, co-located code.

## Terminal Rendering Details

### Initialization Sequence (Verbose TTY)

```
1. Query terminal dimensions: ioctl(STDERR_FILENO, TIOCGWINSZ, &ws)
2. Calculate fixedHeight = min(jobs, maxDisplaySlots) + 4
3. Print fixedHeight blank lines to "claim" the space
4. Move cursor back to row 1
5. Set scrolling region: \033[<fixedHeight+1>;<termHeight>r
6. Hide cursor: \033[?25l
7. Begin render loop
```

### Refresh Tick (every 200ms)

```
1. Save cursor: \033[s (or \0337)
2. Move to row 1, col 1: \033[1;1H
3. For each displayed slot:
     Print slot line + \033[K (clear to EOL)
4. Print idle count line + \033[K
5. Print separator + \033[K
6. Print stats line 1 + \033[K
7. Print stats line 2 + \033[K
8. Print separator + \033[K
9. Restore cursor: \033[u (or \0338)
```

### Result Line Emission (from worker thread)

```
1. Acquire g_outputMutex
2. Save cursor: \033[s
3. Move cursor to scrolling region (bottom): \033[<termHeight>;1H
4. Print result line (natural scroll within region)
5. Restore cursor: \033[u
6. Release g_outputMutex
```

Actually, with scrolling regions set, we simply need to position the cursor anywhere in the scrolling region and print. The terminal handles scrolling automatically. The key insight: after the scrolling region is set, newlines in the scrolling region cause that region to scroll independently.

Simpler approach for result lines:
```
1. Acquire g_outputMutex
2. Save cursor: \033[s
3. Move cursor to last row of scrolling region: \033[<termHeight>;1H
4. Scroll up one line within region: \n
5. Print result line (overwrites the new blank line at bottom)
   Actually, just printing at the bottom with \n triggers auto-scroll
6. Restore cursor: \033[u
7. Release g_outputMutex
```

Even simpler: just move cursor to the scroll region and write normally. The terminal scrolls that region.

### Cleanup (on stop)

```
1. Reset scrolling region: \033[r (full screen)
2. Show cursor: \033[?25h
3. Move cursor below the last written content
4. Print final summary
```

## Worker Lambda Changes

The worker lambda in `main.cpp` currently handles file processing and result logging inline. With the new design:

```cpp
// Acquire a slot
unsigned int slot = slotTracker.acquire(filename);

// Build the stage callback
imager::StageCallback onStage = nullptr;
if (mode == imagestore::DisplayMode::Verbose) {
  onStage = [&slotTracker, slot](imager::ProcessingStage stage) {
    slotTracker.setStage(slot, toPipelineStage(stage));
  };
}

// Process (non-dry-run path)
auto result = img.addFile(capturedPath, "", onStage);

// Release slot
slotTracker.release(slot);

// Log result
stats.processed.fetch_add(1, std::memory_order_relaxed);
switch (result.code) {
  case imager::ErrorCode::Ok:
    stats.added.fetch_add(1, std::memory_order_relaxed);
    if (mode == imagestore::DisplayMode::Verbose) {
      resultLog.append("OK   " + result.id.substr(0, 12) + "... " + filename);
    }
    break;
  // ... DUP, ERR cases similarly
}
```

For dry-run mode, the worker still reads the file itself and calls `img.validateOnly(blob, filename)`. The stage callback doesn't apply to `validateOnly` (which has no storage/db stages). Instead, the worker manually updates the slot:

```cpp
slotTracker.setStage(slot, PipelineStage::Reading);
// ... read file ...
slotTracker.setStage(slot, PipelineStage::Validating);
auto result = img.validateOnly(blob, filename);
```

## Overhead Analysis

| Operation | Cost | Notes |
|-----------|------|-------|
| `StageCallback` invocation | ~15 ns | `std::function` call, 7x per file |
| `SlotTracker::setStage` | ~50 ns | Mutex lock + string-free update |
| `SlotTracker::snapshot` | ~1 µs | Mutex lock + vector copy, 5x/s |
| `ResultLog::append` | ~5 µs | Mutex lock + ANSI write, per file |
| `renderVerbose()` total | ~500 µs | Full redraw, 5x/s |
| **Total new overhead per file** | **~120 ns** | Callback + stage updates |
| **Total render overhead** | **~2.5 ms/s** | 5 redraws/s, negligible |

The callback overhead (~120 ns/file) is negligible compared to the ms-scale I/O per file. The render overhead (~2.5 ms/s) is invisible.

## Edge Cases

1. **Very long filenames**: Truncated with `...` to fit terminal width.
2. **Terminal resize during operation**: Re-read terminal dimensions on `SIGWINCH`. Update scrolling region and slot cap. (Phase 2 — initially, dimensions are read once at startup.)
3. **Rapid file completion (small files)**: Result log may scroll faster than readable. This is expected and acceptable — the statistics bar provides the aggregate view.
4. **Zero files on stdin**: Stats show 0 processed. Final summary still prints. No slot display shown.
5. **Single file**: One slot active briefly, result log shows one line. Works correctly.
6. **`--dry-run` with `-v`**: Slot display shows reading/validating/hashing stages only (no writing/db). Statistics bar shows "valid" instead of "written". Works correctly.
7. **Ctrl+C during verbose mode**: Signal handler must reset scrolling region and show cursor before exit. Use `atexit` or signal handler.
