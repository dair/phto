# 0018 — Memory Growth Investigation and Instrumentation

## Goal

Diagnose long-run memory growth in `imager` / `imagestore` where:

- Valgrind leak checks report no definite leaks
- RSS still rises over time during large imports
- The process becomes unusable after many thousands of files

The objective is not only to ask "is memory leaked?" but to answer the more important operational question:

**Which subsystem owns or retains the memory that makes RSS grow during a long import?**

This plan defines:

1. A precise investigation process
2. The hypotheses to test
3. The observability needed in the application
4. The acceptance criteria for identifying the problem

---

## Why Valgrind Was Not Enough

Valgrind leak checking answers a narrow question:

- Was memory definitely or indirectly lost at process exit?

It does **not** fully answer:

- Is RSS rising because live objects remain referenced for too long?
- Is memory retained by the allocator after free?
- Are thread-local arenas or codec-library caches growing?
- Is a container intentionally accumulating entries over time?
- Is third-party native code allocating through paths not visible to the existing tracing hooks?

In this codebase, those distinctions matter.

---

## Current Code Reality

### Application-level dispatch

`imagestore` reads stdin, resolves paths, and launches one `std::async(std::launch::async, ...)` task per file while bounding concurrency with a semaphore.

Relevant file:

- [imagestore/main.cpp](/home/vibe/imager/imager/imagestore/main.cpp)

Important consequence:

- Concurrent work is bounded
- Thread creation/reuse behavior is still implementation-defined at the `std::async` layer
- Repeated task creation can amplify allocator arena growth and thread-local caching effects

### Library-owned file buffers

`Blob` is the main explicit file-buffer owner in the library. It already tracks:

- `blobs_alive`
- `blob_bytes_alive`

Relevant file:

- [blob/Blob.h](/home/vibe/imager/imager/blob/Blob.h)

This is the most important existing signal because it lets us distinguish:

- memory growth caused by our own live file buffers
- memory growth caused somewhere else

### Heavy validator backends

Several validators do substantial native-library work:

- HEIC: full decode via libheif
- NEF: unpack via LibRaw
- MOV/MP4: container parse + trial decode via FFmpeg

Relevant files:

- [validations/heic/heic_validator.cpp](/home/vibe/imager/imager/validations/heic/heic_validator.cpp)
- [validations/nef/nef_validator.cpp](/home/vibe/imager/imager/validations/nef/nef_validator.cpp)
- [validations/mov/mov_validator.cpp](/home/vibe/imager/imager/validations/mov/mov_validator.cpp)

These are strong suspects for RSS growth without a classic leak.

### Error-file accumulation

When `--errors` is used, the application keeps an in-memory `std::unordered_set<std::string>` of all known failed paths.

Relevant file:

- [imagestore/ErrorFile.h](/home/vibe/imager/imager/imagestore/ErrorFile.h)

This is not a bug by itself, but it is one of the few intentionally unbounded containers in the app.

### Existing memory tracer limitations

The current tracing feature hooks global `new` / `delete`.

Relevant file:

- [imagestore/MemoryTrace.cpp](/home/vibe/imager/imager/imagestore/MemoryTrace.cpp)

That helps for some C++ allocations, but it does **not** comprehensively explain RSS growth because:

- many libraries use `malloc` directly
- FFmpeg uses `av_malloc`
- codec libraries may retain pools/caches internally
- allocator arena retention is visible in RSS even after logical frees

## Hypotheses

The investigation must separate these cases explicitly.

### H1 — Live `Blob` memory is growing

Symptoms:

- `blob_bytes_alive` trends upward with RSS
- `blobs_alive` remains elevated
- in-flight bytes stay high or never settle

Meaning:

- application/library-owned file buffers are not being released fast enough
- or concurrency/backpressure is insufficient for the workload shape

### H2 — RSS grows while `Blob` memory stays flat

Symptoms:

- RSS trends upward
- `blob_bytes_alive` stays low or oscillates around a steady value

Meaning:

- growth is outside the primary `Blob` ownership path
- likely allocator retention, thread arenas, third-party decoder caches, or another long-lived structure

### H3 — Growth is format-specific

Symptoms:

- JPEG imports stable
- HEIC, NEF, or MOV imports show sustained RSS growth

Meaning:

- the responsible subsystem is likely format backend specific

### H4 — Growth scales with concurrency

Symptoms:

- `--jobs 1` is stable or nearly stable
- higher `--jobs` values grow substantially

Meaning:

- thread-local allocators, per-thread codec state, or native backend working sets are involved

### H5 — Growth tracks failures only

Symptoms:

- memory rises only in runs with many bad files
- growth correlates with the error-file skip set

Meaning:

- intentional retention in `ErrorFile` or error-specific paths is a contributor

## Investigation Process

The process is intentionally staged. Do not jump directly to external profilers before the built-in signals are collected.

### Phase 1 — Add runtime observability

Instrument `imagestore` to emit periodic memory samples during long imports.

Each sample must include:

- process RSS
- process peak RSS / high-water mark
- `blobs_alive`
- `blob_bytes_alive`
- thread-pool queue depth and active threads
- total in-flight file count
- total in-flight bytes
- processed / added / duplicate / error / skipped counters

Rationale:

- these signals let us separate library-owned live memory from process RSS
- they also show whether work is backing up in the pipeline

### Phase 2 — Baseline runs

Run the same import workload under:

1. `--jobs 1`
2. a normal production-like `--jobs`
3. with and without `--errors`

Record the periodic samples and compare:

- steady-state RSS
- slope of RSS over time
- relation between RSS and `blob_bytes_alive`

### Phase 3 — Format isolation

Run separate long imports for:

1. JPEG only
2. PNG only
3. HEIC only
4. NEF only
5. MOV/MP4 only

Goal:

- determine whether growth is general infrastructure or backend specific

### Phase 4 — Interpretation

Use the observations to classify the issue.

#### Case A — RSS and `blob_bytes_alive` rise together

Focus on:

- lifetime of `Blob` copies across async/coroutine boundaries
- storage fan-out holding buffers longer than expected
- queue/backpressure imbalance

#### Case B — RSS rises but `blob_bytes_alive` is flat

Focus on:

- allocator retention
- `std::async` threading behavior
- native decoder/library caches
- glibc arenas
- FFmpeg/libheif/LibRaw working-set retention

#### Case C — only one format grows

Focus on that validator/backend first.

#### Case D — only failure-heavy runs grow

Focus on:

- `ErrorFile`
- retained error-path strings or bookkeeping

### Phase 5 — External profiler only after narrowing

After the internal metrics identify the class of growth, use a profiler appropriate to the narrowed hypothesis:

- `heaptrack` or Massif for retained heap growth over time
- allocator-specific diagnostics for arena retention
- format/backend-specific stress runs for decoder libraries

Do not treat external profiling as the first step. Its output is far easier to interpret once the workload and growth pattern are narrowed.

## Instrumentation Design

### Requirements

The instrumentation must be:

- opt-in
- lightweight enough for long imports
- safe in both normal and verbose output modes
- useful without post-processing

### Output mechanism

Periodic memory samples should be written through `ResultLog`, not directly with ad-hoc `stderr` writes.

Reason:

- normal mode already writes result lines there
- verbose TTY mode routes `ResultLog` into the scrolling region cleanly
- this avoids corrupting the fixed top section of the verbose display

### Sampling interval

Default: 5 seconds

Configurable at runtime because:

- shorter intervals help reproduce fast growth
- longer intervals reduce noise for multi-hour imports

### Linux process memory source

Use `/proc/self/status`:

- `VmRSS` for current resident set size
- `VmHWM` for peak resident size

This is Linux-specific but appropriate for the current target environment and much more useful than allocation counts alone.

---

## Implemented Runtime Interface

The investigation instrumentation should be exposed in `imagestore` as:

- `--memory-report`
- `--memory-interval N`

Behavior:

- when enabled, emit a periodic line with current memory/process state
- emit one final sample at shutdown

Example shape:

```text
MEM  rss=512 MiB hwm=640 MiB blobs=2/96 MiB inflight=4/180 MiB pool=q1,a8 proc=12000 add=11910 dup=70 err=20 skip=0
MEMF rss=410 MiB hwm=640 MiB blobs=0/0 KiB inflight=0/0 KiB pool=q0,a0 proc=12500 add=12405 dup=72 err=23 skip=0
```

Interpretation:

- `rss` shows current process footprint
- `hwm` shows peak footprint
- `blobs=` shows library-owned file buffers
- `inflight=` shows pipeline pressure
- `pool=` shows queue depth and active worker count

## Acceptance Criteria

The plan is successful when one of the following statements can be made with evidence from a real long-running import:

1. RSS growth is caused by live `Blob` retention in our pipeline
2. RSS growth is not caused by `Blob` retention and instead points to allocator or third-party backend behavior
3. RSS growth is isolated to one or more specific formats
4. RSS growth is primarily caused by the error skip set or another intentional in-memory structure

The plan is **not** complete merely because tracing exists. It is complete only when the instrumentation makes the growth class identifiable.

---

## Follow-up Actions After Classification

### If `Blob` retention is the cause

Possible fixes:

- tighter backpressure
- eliminate unnecessary `Blob` copies in async fan-out
- reduce parallelism for large in-memory paths

### If allocator / thread arenas are the cause

Possible fixes:

- replace `std::async` with a fixed worker pool in `imagestore`
- test allocator tuning
- keep long-lived worker threads stable instead of repeated launch semantics

### If a native backend is the cause

Possible fixes:

- isolate the backend with a dedicated reproducer
- change validation depth
- force backend cleanup boundaries if the API supports them
- consider moving the heaviest validator path to streaming/file-backed-only operation where possible

### If the error skip set is the cause

Possible fixes:

- make skip retention optional
- store only a hashed representation
- spill to disk rather than keeping all paths resident
