# 0017 — Large File Handling: True Streaming Processing

## Goal

Enable `imagestore` and `libimager` to process files of arbitrary size without ever loading the entire file into memory. The current design requires the complete file contents in a contiguous `Blob` allocation, which fails for files exceeding available RAM and causes excessive memory pressure for multi-GB videos processed in parallel.

The solution introduces a **true streaming pipeline** where every stage — reading, validation, hashing, and storage writing — operates on fixed-size chunks. Peak per-file memory is bounded at `O(chunkSize)` regardless of file size.

---

## Current State

### How files are loaded today

Two entry points:

1. **`Imager::addFile(path)`**: Reads the entire file into a `Blob` via `std::ifstream::read()` in one call, then passes to `addImageImpl`.
2. **`Imager::addImage(blob, filename)`**: Receives an already-loaded `Blob` from the caller.

Both require the **entire file in a contiguous memory buffer** before any processing begins.

### The `Blob` type

`blob::Blob` (`blob/Blob.h`) — shared-ownership binary buffer backed by `std::shared_ptr<uint8_t[]>`:
- Single contiguous allocation: `new uint8_t[size]`
- Shared ownership for safe passing into coroutines
- Two-phase: `Blob(size)` → `writableData()` → `freeze()` → immutable

### Pipeline flow

```
addFile(path):
  1. Blob blob(fileSize)              ← full allocation
  2. ifstream.read(blob, fileSize)    ← full read into RAM
  3. addImageImpl(blob):
     a. validate(blob.data(), blob.size())  ← full buffer required
     b. computeSha256(blob)                 ← iterates in 64KB chunks internally
     c. dedup_check(hash)
     d. storage.writeFileAsync(blob)        ← writes from blob memory
     e. dbs.addFile(...)
```

### Validator interface

```cpp
class IValidator {
  virtual ValidationResult validate(const uint8_t* data, size_t size) const = 0;
};
```

Requires a contiguous buffer of the full file. This is the primary blocker for streaming.

### Validator internals — streaming capability analysis

| Validator | Library | Current API | Native streaming support |
|-----------|---------|-------------|-------------------------|
| **JPEG** | libjpeg | `jpeg_mem_src(data, size)` | **Yes** — `jpeg_stdio_src(FILE*)` reads from file; can also use custom source manager with `fill_input_buffer` callback for chunked reads |
| **PNG** | libpng | `png_set_read_fn()` with memory callback | **Yes** — already uses a callback-based read (`pngReadCallback`). Swapping to a file/stream-backed callback is trivial |
| **HEIC** | libheif | `heif_context_read_from_memory_without_copy(data, size)` | **Partial** — `heif_context_read_from_reader()` accepts a `heif_reader` struct with `read`, `seek`, `get_position`, `get_length` callbacks. Requires seekable source but not contiguous memory |
| **MOV** | libavformat | Custom `AVIOContext` with `readPacket`/`seekBuffer` callbacks | **Yes** — already uses callback-based I/O. Swapping the backing from memory buffer to file descriptor is straightforward |
| **NEF** | LibRaw | `libraw_open_buffer(data, size)` | **Partial** — `libraw_open_file(path)` reads from disk directly. No chunk callback, but file-based entry point exists |
| **AAE** | Pure C++ | Scans for XML markers in memory | **Yes** — simple string searches can be adapted to stream through chunks |

**Key finding**: Every validator either has a native file/stream-based API or uses a callback mechanism that can be backed by a file descriptor instead of memory. True streaming validation is achievable for all formats.

### Memory pressure analysis

| Scenario | Per-file | Jobs | Peak RAM |
|----------|----------|------|----------|
| 5 MB photos | 5 MB | 32 | 160 MB |
| 50 MB RAW photos | 50 MB | 32 | 1.6 GB |
| 500 MB video | 500 MB | 32 | 16 GB |
| 2 GB video | 2 GB | 32 | 64 GB |

## Problem Statement

1. **Allocation failure**: Files exceeding available contiguous RAM cannot be allocated as a `Blob`.
2. **Excessive peak memory**: N concurrent large files consume `N × fileSize` bytes.
3. **Validator interface**: `IValidator::validate(const uint8_t*, size_t)` mandates full-buffer.
4. **Hash requires full read before storage write**: SHA256 identity determines the storage path — must complete before writing.

---

## Requirements

### Functional

1. Process files of any size up to filesystem limits (for formats that allow it).
2. Maintain SHA256-based deduplication.
3. Maintain format validation for all supported types.
4. Maintain multi-root redundant storage with rollback.
5. Maintain all-or-nothing database writes.
6. **No stage ever holds the full file in memory.** Chunk buffers only.
7. **Per-format file size limits** — reject files exceeding their format's maximum before any processing.
8. Default limits per format covering 99%+ of real-world files.
9. Configurable size limits per extension via config file.

### Non-Functional

1. **Bounded memory**: Peak per-file memory is `O(chunkSize)`, not `O(fileSize)`.
2. **No regression for small files**: Files below threshold use the existing fast `Blob` path.
3. **Backward compatibility**: `addImage(blob, filename)` API unchanged.
4. **No new external dependencies**.

---

## Design Approach

### Per-Format File Size Limits

Each file format has a **maximum acceptable size**. Files exceeding their format's limit are **rejected immediately** without any processing — no validation, no hashing, no storage write. This catches obviously corrupt or misnamed files (a 5 GB "JPEG" is not a real photo) and avoids wasting resources on files that cannot reasonably be what they claim to be.

#### Default Limits

| Format | Extensions | Default max size | Rationale |
|--------|-----------|-----------------|-----------|
| **JPEG** | `.jpg`, `.jpeg` | 250 MB | A 100 MP camera produces ~50 MB JPEGs. 250 MB gives 5× headroom. |
| **PNG** | `.png` | 500 MB | Lossless — larger than JPEG for same content. 500 MB covers extreme cases. |
| **HEIC** | `.heic`, `.heif` | 250 MB | Similar to JPEG (lossy compressed photos). |
| **NEF** | `.nef` | 500 MB | RAW sensor data, 50 MP NEFs are ~50-80 MB. 500 MB gives generous headroom. |
| **AAE** | `.aae` | 1 MB | Tiny XML sidecar files, typically < 10 KB. 1 MB is already very generous. |
| **MOV/MP4** | `.mov`, `.mp4` | 100 GB | Video can legitimately be very large. 100 GB covers long 4K/8K recordings. |

These defaults cover 99%+ of real-world media files. A file exceeding its format limit is almost certainly not a valid instance of that format.

#### Configuration

Size limits are configurable via the config file and are **per-extension**:

1. **Config file** (`~/.imagestore.toml`): New `[file_size_limits]` section:
   ```toml
   [file_size_limits]
   jpg = "250MB"
   jpeg = "250MB"
   png = "500MB"
   heic = "250MB"
   heif = "250MB"
   nef = "500MB"
   aae = "1MB"
   mov = "100GB"
   mp4 = "100GB"
   ```
   Accepts human-readable size strings: `"250MB"`, `"1GB"`, `"512KB"`, etc. Only extensions explicitly listed are overridden — omitted extensions keep their compiled defaults.

2. **Library API**: `Imager` receives size limits as part of `AppConfig`:

```cpp
// config/Config.h — addition to AppConfig
struct AppConfig {
  std::vector<TargetConfig> targets;

  /// Per-extension maximum file size. Files exceeding their format's
  /// limit are rejected without processing.
  /// Key: lowercase extension without dot (e.g., "jpg", "mov").
  /// Value: maximum size in bytes.
  std::unordered_map<std::string, uint64_t> fileSizeLimits;  // populated with defaults + config overrides
};
```

The defaults are compiled into the config parser and merged with user overrides:

```cpp
// config/Config.cpp — default limits

static const uint64_t kMegabyte = 1024 * 1024;
static const uint64_t kDefaultLossyImageSizeLimit = 250ULL * kMegabyte;
static const uint64_t kDefaultLosslessImageSizeLimit = 500ULL * kMegabyte;
static const uint64_t kDefaultVideoSizeLimit = 100ULL * 1024 * kMegabyte;

static const std::unordered_map<std::string, uint64_t> kDefaultSizeLimits = {
  {"jpg",  kDefaultLossyImageSizeLimit},
  {"jpeg", kDefaultLossyImageSizeLimit},
  {"png",  kDefaultLosslessImageSizeLimit},
  {"heic", kDefaultLossyImageSizeLimit},
  {"heif", kDefaultLossyImageSizeLimit},
  {"nef",  kDefaultLosslessImageSizeLimit},
  {"aae",    1ULL * kMegabyte},
  {"mov",  kDefaultVideoSizeLimit},
  {"mp4",  kDefaultVideoSizeLimit},
};
```

No CLI flag for individual format limits — the config file is the right place for this level of detail. A `--max-file-size SIZE` CLI flag overrides **all** limits to a single value (useful for testing or one-off runs with unusual files).

### Streaming Threshold

Separately from rejection limits, files that pass the size check but are **large enough to cause memory pressure** use the streaming path instead of the `Blob` path.

**Streaming threshold**: 256 MB (hardcoded). Rationale: below this, `Blob` works well with concurrent jobs; above this, loading into contiguous memory becomes wasteful. This only affects files that passed their format's size limit — in practice, only MOV/MP4 will regularly exceed 256 MB and need streaming.

```cpp
// imager/Imager.cpp
static constexpr uint64_t kStreamingThreshold = 256ULL * kMegabyte;  // 256 MB
```

This is intentionally not user-configurable. It's a memory management detail, not a semantic knob. The per-format size limits are the user-facing configuration.

### Decision Flow

```
addFile(path):
  1. stat(path) → fileSize, ext
  2. Look up fileSizeLimits[ext]
  3. if (fileSize > limit):
       → REJECT immediately (result = TOO_LARGE error, no processing)
  4. if (fileSize > kStreamingThreshold):
       → streaming path (addFileLarge)
  5. else:
       → existing Blob path (unchanged)
```

**Implication**: Since static image formats cap at 250-500 MB and the streaming threshold is 256 MB, most image formats will never hit the streaming path — they're either small enough for `Blob` or too large and get rejected. The streaming path primarily serves MOV/MP4, which can legitimately range from a few MB to tens of GB.

### Core Architecture: Single-Pass Streaming Pipeline

Unlike the previous mmap-based design, this approach processes the file in a **single streaming pass** where hash, validation, and (for the write pass) storage all operate on chunks without the full file ever being in memory.

However, there is a fundamental ordering constraint: **the SHA256 hash determines the storage path**, so the hash must be known before storage writing can begin. This means we need two passes through the file data:

**Pass 1 — Validate + Hash** (single read, streamed):
- Open file once
- Stream chunks through both the validator and the hasher simultaneously
- Validator uses a file-backed or stream-backed interface (not memory buffer)
- Hasher uses incremental `StreamHasher`
- Peak memory: one chunk buffer (~4 MB) + validator working memory (one scanline/frame)

**Pass 2 — Storage Write** (streamed):
- Hash is now known → storage path is determined
- Re-open file, stream chunks to each storage root in parallel
- Peak memory: one chunk buffer per root (~4 MB × numRoots)

**Why two passes are unavoidable**: The hash is the filename on disk (`<root>/<hash[0:2]>/<hash>.<ext>`). We cannot write to storage until we know the hash. We cannot know the hash until we've read the entire file. Therefore, reading for write must be a separate pass from reading for hash.

**Why this is still true streaming**: Neither pass loads the full file into memory. Pass 1 streams through the file computing the hash and validating. Pass 2 streams through the file again writing to storage. The second read is fast — the file is likely hot in the OS page cache from Pass 1.

### Chunk Size

**4 MB** — balances syscall overhead against memory footprint.

| Chunk size | Chunks per 2 GB | Buffer memory (32 jobs) |
|------------|-----------------|-------------------------|
| 64 KB | 32,768 | 2 MB |
| 1 MB | 2,048 | 32 MB |
| **4 MB** | **512** | **128 MB** |
| 16 MB | 128 | 512 MB |

## Streaming Validator Interface

### New Interface: `IStreamValidator`

Add a new abstract base class alongside the existing `IValidator`:

```cpp
// imager/ImageValidator.h — additions

namespace validation {

/// Stream-based validator for large files.
/// Validators that support streaming implement this interface.
/// The file is opened and managed by the caller; the validator
/// reads from it via the provided source.
class IStreamValidator {
public:
  virtual ~IStreamValidator() = default;

  /// Returns true if this validator handles the given extension.
  virtual bool supportsExtension(const std::string& ext) const = 0;

  /// Validate a file by reading from the given path.
  /// The implementation opens the file itself and reads as needed.
  /// Must not hold the entire file in memory.
  ///
  /// This is the simplest interface: validators that have native
  /// file-based APIs (LibRaw, libjpeg stdio, libavformat) just
  /// open the file. Validators with callback APIs (libpng, libheif)
  /// use a small buffered reader internally.
  virtual ValidationResult validateFile(const std::filesystem::path& path) const = 0;
};

} // namespace validation
```

**Design rationale — `validateFile(path)` over chunk callbacks**:

The underlying libraries have very different streaming models:
- libjpeg: `jpeg_stdio_src(FILE*)` — wants a `FILE*`
- libpng: callback `pngReadCallback(png, buf, count)` — pull-based
- libheif: `heif_reader` with read/seek/tell callbacks — pull-based, seekable
- libavformat: `AVIOContext` with read/seek callbacks — pull-based, seekable
- LibRaw: `libraw_open_file(path)` — opens file itself
- AAE: simple string scanning — trivially adaptable

A chunk-push model (`begin()/update(chunk)/finalize()`) would force each library into an unnatural pattern (they all want to *pull* data). Instead, `validateFile(path)` lets each validator open and read the file in whatever pattern its library prefers. The validator manages its own I/O buffering — none of them need to hold the full file.

### Per-Validator Streaming Adaptation

#### JPEG — `JpegStreamValidator`

**Current**: `jpeg_mem_src(&cinfo, bytes, dataSize)` — memory source.

**Streaming**: `jpeg_stdio_src(&cinfo, file)` — libjpeg's built-in stdio source reads from a `FILE*` in small internal buffers (~4 KB). The decompression loop (`jpeg_read_scanlines`) already processes one scanline at a time — inherently streaming.

```cpp
ValidationResult JpegStreamValidator::validateFile(const std::filesystem::path& path) const {
  FILE* f = fopen(path.c_str(), "rb");
  if (!f) return WRONG;
  // ... setup cinfo, error manager ...
  jpeg_stdio_src(&cinfo, f);   // libjpeg reads file in ~4KB chunks
  jpeg_read_header(&cinfo, TRUE);
  jpeg_start_decompress(&cinfo);
  // read scanlines one at a time (same as current)
  while (cinfo.output_scanline < cinfo.output_height) {
    jpeg_read_scanlines(&cinfo, buf, 1);
  }
  jpeg_finish_decompress(&cinfo);
  fclose(f);
  return VALID;
}
```

**Peak memory**: One scanline buffer (`width × components` bytes, typically < 100 KB) + libjpeg's internal buffers (~64 KB). Total: < 200 KB regardless of file size.

#### PNG — `PngStreamValidator`

**Current**: `pngReadCallback` reads from a memory-backed `PngReadState`.

**Streaming**: Replace `PngReadState` with a file-backed version. The callback reads from a `FILE*` instead of a `(data, pos)` pair. The rest of the code is identical — libpng already reads row-by-row.

```cpp
struct PngFileState {
  FILE* f;
};

void pngFileReadCallback(png_structp png_ptr, png_bytep out, png_size_t count) {
  auto* s = static_cast<PngFileState*>(png_get_io_ptr(png_ptr));
  if (fread(out, 1, count, s->f) != count) {
    png_error(png_ptr, "read error");
  }
}
```

**Peak memory**: One row buffer (`rowbytes`, typically < 100 KB for most images) + libpng internals. Total: < 200 KB.

#### HEIC — `HeicStreamValidator`

**Current**: `heif_context_read_from_memory_without_copy(data, size)`.

**Streaming**: libheif provides `heif_context_read_from_reader()` which accepts a `heif_reader` struct:

```c
struct heif_reader {
  int reader_api_version;  // = 1
  int64_t (*get_position)(void* userdata);
  int (*read)(void* data, size_t size, void* userdata);
  int (*seek)(int64_t position, void* userdata);
  enum heif_reader_grow_status (*wait_for_file_size)(int64_t target_size, void* userdata);
};
```

We implement these callbacks backed by a `FILE*`:

```cpp
static int heifRead(void* data, size_t size, void* userdata) {
  auto* f = static_cast<FILE*>(userdata);
  return (fread(data, 1, size, f) == size) ? 0 : -1;
}
static int heifSeek(int64_t position, void* userdata) {
  auto* f = static_cast<FILE*>(userdata);
  return fseeko(f, position, SEEK_SET) == 0 ? 0 : -1;
}
// ... get_position, wait_for_file_size similarly
```

**Peak memory**: libheif's internal decode buffers. For HEIC images, libheif decodes tile-by-tile; peak memory depends on tile size (typically 512×512 pixels = ~768 KB per tile in RGB). For a 50 MP image: a few MB of decode buffers — much less than the full compressed file.

**Note**: libheif's decode step (`heif_decode_image`) does allocate the full decoded image in memory (width × height × 3 bytes). For very large images (e.g., 100 MP = 300 MB decoded), this could be significant. However, HEIC files are typically photos (< 50 MB compressed, < 150 MB decoded), not the multi-GB files this plan targets. If needed, we can skip the full decode for oversized HEIC and just verify the container + metadata (a partial validation).

#### MOV — `MovStreamValidator`

**Current**: Custom `AVIOContext` with `readPacket`/`seekBuffer` callbacks backed by in-memory `BufferState`.

**Streaming**: Replace `BufferState` with a file-descriptor-backed version. The `AVIOContext` callbacks read from the file instead of memory:

```cpp
struct FileState {
  FILE* f;
  int64_t size;
};

int readPacketFile(void* opaque, uint8_t* buf, int buf_size) {
  auto* s = static_cast<FileState*>(opaque);
  size_t n = fread(buf, 1, buf_size, s->f);
  return (n == 0) ? AVERROR_EOF : static_cast<int>(n);
}

int64_t seekFile(void* opaque, int64_t offset, int whence) {
  auto* s = static_cast<FileState*>(opaque);
  if (whence == AVSEEK_SIZE) return s->size;
  fseeko(s->f, offset, whence);
  return ftello(s->f);
}
```

The rest of the validation is identical — `avformat_open_input`, `avformat_find_stream_info`, trial decode of up to 8 packets. libavformat reads in its own 32 KB I/O buffer.

**Peak memory**: AVIOContext buffer (32 KB) + one decoded video frame (~width × height × 1.5 bytes for YUV420, e.g., 4K = ~12 MB). This is the same as current — no change. And crucially, far less than holding a 2 GB MOV file in memory.

#### NEF — `NefStreamValidator`

**Current**: `libraw_open_buffer(data, size)` — memory buffer.

**Streaming**: LibRaw provides `libraw_open_file(path)` which opens and reads from disk directly. LibRaw manages its own I/O internally.

```cpp
ValidationResult NefStreamValidator::validateFile(const std::filesystem::path& path) const {
  LibRawPtr raw{libraw_init(0)};
  if (!raw) return INVALID;

  int err = libraw_open_file(raw.get(), path.c_str());
  if (err != LIBRAW_SUCCESS) {
    return (err == LIBRAW_FILE_UNSUPPORTED) ? WRONG : INVALID;
  }

  err = libraw_unpack(raw.get());
  return (err == LIBRAW_SUCCESS) ? VALID : INVALID;
}
```

**Peak memory**: LibRaw allocates buffers for the RAW sensor data during `libraw_unpack()`. For a 50 MP NEF (~25 MB compressed), the unpacked sensor data is ~100 MB. This is the same as the current approach (LibRaw allocates internally regardless of input source). NEF files are typically < 100 MB compressed, so this is not a concern for the multi-GB file use case.

#### AAE — `AaeStreamValidator`

**Current**: Scans memory buffer for XML markers (`<?xml`, `<plist`, `<dict>`, `<key>`).

**Streaming**: Read the file in chunks, scanning each chunk (with overlap at boundaries for cross-chunk matches):

```cpp
ValidationResult AaeStreamValidator::validateFile(const std::filesystem::path& path) const {
  FILE* f = fopen(path.c_str(), "rb");
  if (!f) return WRONG;

  // AAE files are tiny (<100 KB). Read up to 64 KB and scan.
  // If file > 64 KB, it's not a valid AAE.
  char buf[65536];
  size_t n = fread(buf, 1, sizeof(buf), f);
  fclose(f);

  return validateAae(buf, n);  // reuse existing memory-based validator
}
```

AAE files are always tiny (< 10 KB typically). The streaming validator can just read the first 64 KB and delegate to the existing memory-based function. No special chunking needed.

### Validator Discovery and Dispatch

`Imager::Impl` currently stores a `std::vector<std::unique_ptr<validation::IValidator>>`. For streaming support, add a parallel vector:

```cpp
struct Imager::Impl {
  std::vector<std::unique_ptr<validation::IValidator>> validators;
  std::vector<std::unique_ptr<validation::IStreamValidator>> streamValidators;
  // ...

  const validation::IStreamValidator* findStreamValidator(const std::string& ext) const {
    for (const auto& v : streamValidators) {
      if (v->supportsExtension(ext)) return v.get();
    }
    return nullptr;
  }
};
```

When `addFile` dispatches to the streaming path, it uses `findStreamValidator()`. If no stream validator is available for the format, it falls back to the `Blob`-based path with a warning — this ensures forward compatibility if a new format is added without a stream validator.

## Streaming Hash

### `StreamHasher` — Incremental SHA256

Wraps OpenSSL's EVP digest API in an init/update/finalize pattern:

```cpp
// imager/StreamHasher.h

namespace imager {

class StreamHasher {
public:
  StreamHasher();
  ~StreamHasher();

  StreamHasher(const StreamHasher&) = delete;
  StreamHasher& operator=(const StreamHasher&) = delete;

  /// Feed a chunk of data.
  void update(const uint8_t* data, size_t size);

  /// Finalize and return the 64-char hex hash.
  /// After calling, the hasher must not be reused.
  std::string finalize();

private:
  struct Impl;
  std::unique_ptr<Impl> m_impl;
};

} // namespace imager
```

Implementation uses the same OpenSSL calls as `computeSha256()`:

```cpp
struct StreamHasher::Impl {
  EVP_MD_CTX* ctx;
  Impl() : ctx(EVP_MD_CTX_new()) {
    EVP_DigestInit_ex(ctx, EVP_sha256(), nullptr);
  }
  ~Impl() { EVP_MD_CTX_free(ctx); }
};

void StreamHasher::update(const uint8_t* data, size_t size) {
  EVP_DigestUpdate(m_impl->ctx, data, size);
}

std::string StreamHasher::finalize() {
  unsigned char hash[EVP_MAX_MD_SIZE];
  unsigned int len = 0;
  EVP_DigestFinal_ex(m_impl->ctx, hash, &len);
  // hex-encode (same as computeSha256)
}
```

### Pass 1: Combined Hash + Validate

The hash and validation can run in parallel on the same file in two ways:

**Option A — Sequential (simpler)**: Hash the entire file first (streaming), then validate (file-based). Two sequential reads. Simple, no coordination.

**Option B — Parallel single-read with tee**: Read the file once in chunks. Feed each chunk to the hasher. Meanwhile, the validator reads from the same file via its own file descriptor. The OS page cache ensures the data is only read from disk once.

**Recommended: Option A for simplicity.** The file is likely in page cache after the hash pass, making the validator's read essentially free. The added complexity of coordinating parallel reads doesn't justify the minimal I/O saving.

```
Pass 1 flow:
  1. Open file
  2. StreamHasher: read 4 MB chunks, update() each → finalize() → hash
  3. Close file
  4. streamValidator->validateFile(path)
     (validator opens file, reads as needed — data hot in page cache)
```

Actually, we can do even better: hash and validate in **parallel on separate threads**, each with its own file descriptor. They both read the same file but independently. The OS page cache serves both:

```
Pass 1 flow (parallel):
  1. Launch two coroutines:
     a. Hash coroutine: open file, read 4 MB chunks, StreamHasher → hash
     b. Validate coroutine: streamValidator->validateFile(path)
  2. whenAll(hash, validate)
  3. Check validation result; if invalid, abort
  4. Use hash for dedup + storage
```

This is the same parallelism as the current small-file path (validate + hash run in parallel via `coro::whenAll`), just with file-based instead of memory-based I/O.

**Recommended: Parallel** — matches the existing architecture and doesn't sacrifice throughput for large files.

## Streaming Storage Write

### `FileStorage::writeFileFromDiskAsync`

New method that copies from source file to storage roots in chunks:

```cpp
coro::Task<void> FileStorage::writeFileFromDiskAsync(
  const std::string& id,
  const std::string& ext,
  const std::filesystem::path& sourcePath,
  uint64_t fileSize
);
```

Implementation launches one coroutine per root, each with its own source `FILE*` and destination `ofstream`:

```cpp
coro::Task<void> FileStorage::writeToRootFromDisk(
  std::filesystem::path root,
  std::string id,
  std::string ext,
  std::filesystem::path sourcePath
) {
  co_await m_pool.schedule();
  metrics::Timer t(m_metrics.storage_write_root);

  auto destPath = filePath(root, id, ext);
  std::filesystem::create_directories(destPath.parent_path());

  std::ifstream in(sourcePath, std::ios::binary);
  if (!in) throw std::runtime_error("Cannot open source: " + sourcePath.string());

  std::ofstream out(destPath, std::ios::binary | std::ios::trunc);
  if (!out) throw std::runtime_error("Cannot open dest: " + destPath.string());

  std::vector<char> buf(STREAM_CHUNK_SIZE);  // 4 MB
  while (in) {
    in.read(buf.data(), buf.size());
    auto n = in.gcount();
    if (n > 0) {
      out.write(buf.data(), n);
      if (!out) throw std::runtime_error("Write failed: " + destPath.string());
      m_metrics.storage_bytes_written.add(static_cast<uint64_t>(n));
    }
  }
}
```

Parallel writes to all roots with rollback on failure (same pattern as existing `writeFileAsync`).

**Memory per root write**: One 4 MB chunk buffer. With 3 roots: 12 MB per in-flight file.

## Full Pipeline for Large Files

```
Imager::addFile(path, filename, onStage):
  1. stat(path) → fileSize
  2. ext = lowercase extension (without dot)
  3. limit = config.fileSizeLimits[ext]  (or no limit if ext unknown)
  4. if (limit && fileSize > limit):
       → REJECT: return AddResult with error "File too large for format:
         <ext> file is <fileSize> bytes, max allowed is <limit> bytes"
         (no validation, no hashing, no storage — immediate return)
  5. if (fileSize <= kStreamingThreshold):
       → existing Blob path (unchanged)
  6. else → addFileLarge(path, displayName, fileSize, onStage):

addFileLarge:
  // Stage: determine format
  7. streamValidator = findStreamValidator(ext)
     if (!streamValidator):
       log warning, fall back to Blob path (or error if OOM)

  // Pass 1: Hash + Validate (parallel, streamed)
  8. onStage(Hashing)
     Hash coroutine:
       open(path), read 4MB chunks, StreamHasher::update(), finalize() → hash
  9. onStage(Validating)
     Validate coroutine:
       streamValidator->validateFile(path)
  10. coro::whenAll(hash_task, validate_task)
  11. Check validation result → abort if invalid

  // Dedup (same as small-file path)
  12. onStage(WaitingMutex) → acquire writeMutex
  13. onStage(DedupChecking) → dbs.fileExists(hash)

  // Pass 2: Streaming Write
  14. onStage(WritingStorage)
      storage.writeFileFromDiskAsync(hash, ext, path, fileSize)

  // DB Insert (same as small-file path)
  15. onStage(InsertingDb)
      dbs.addFile(hash, name, fileSize, ext)

  // Sidecar handling (same as small-file path)
  16. original_name + orphan resolution
```

## Dry-Run Mode

Dry-run (`--dry-run`) currently loads the file into a `Blob` and calls `validateOnly(blob, filename)`. For large files, add a new method:

```cpp
// imager/Imager.h
AddResult validateOnlyFile(const std::filesystem::path& path,
                           const std::string& filename = "");
```

Implementation:
```
validateOnlyFile(path):
  1. stat(path) → fileSize, ext
  2. Check fileSizeLimits[ext] → reject if exceeded (same as addFile)
  3. if (fileSize <= kStreamingThreshold):
       load Blob, call existing validateOnly(blob, filename)
  4. else:
     a. Stream hash via StreamHasher
     b. streamValidator->validateFile(path)
     c. dbs.fileExists(hash) → dedup check
     d. Return result (no storage write)
```

`imagestore` dry-run path updated to call `validateOnlyFile(path)` instead of loading the file itself.

## Edge Cases

### 1. File exceeds format size limit

Rejected immediately with a clear error message: `"File too large for format: jpg file is 1.2 GB, max allowed is 250 MB"`. Counted in `stats.errors`. Written to the error file if `--errors` is set. No resources consumed beyond a `stat()` call.

### 2. Unknown extension with no size limit

If the extension is not in `fileSizeLimits`, no size limit is enforced. The file proceeds to the normal validator lookup, which will reject it if no validator supports the extension. This avoids blocking future formats added without size limit entries.

### 3. Validator doesn't support streaming

If `findStreamValidator(ext)` returns `nullptr` for a given format, fall back to the `Blob` path. If the file is too large for a `Blob` allocation (throws `std::bad_alloc`), report the file as an error: `"File too large to validate in memory and no streaming validator available for <ext>"`.

### 4. Source file modified between passes

The hash computed in Pass 1 may not match the data written in Pass 2 if the file changes between reads. **Mitigation**: Document that source files must not be modified during import. This is a pre-existing TOCTOU issue.

### 5. Source file deleted between passes

Pass 2 fails to open the file → error. Handled by existing error path.

### 6. Partial storage write failure

Same as today: rollback successful root writes on failure. No change.

### 7. Dry-run with large files

Uses `validateOnlyFile(path)` — streaming hash + streaming validate, no storage write. Works correctly.

### 8. Sidecar files (AAE)

AAE files are always tiny (< 10 KB). Will never exceed any reasonable threshold. No special handling.

### 9. LibRaw memory for very large NEF

LibRaw's `libraw_unpack()` allocates sensor data internally (~2× compressed size). A hypothetical 1 GB NEF would allocate ~2 GB internally — but such files don't exist in practice. NEF files top out at ~100 MB for 50 MP images.

### 10. Threshold of 0 (always stream)

Valid configuration. All files use the streaming path. Slightly slower for small files (two passes instead of one) but functionally correct. Useful for testing.

### 11. Threshold of max uint64 (never stream)

Effectively disables large file support. All files use the `Blob` path. Same as current behavior.

## Design Decisions

### Decision 1: `validateFile(path)` vs chunk-push interface

**Chosen**: `validateFile(path)` — the validator opens and reads the file itself.

**Alternative**: `begin()` / `update(chunk)` / `finalize()` push interface.

**Rationale**: All underlying libraries use pull-based I/O (they want to read data when they need it, not receive it pushed). A push interface would require complex buffering adapters for every library. `validateFile(path)` lets each validator use its library's native file I/O, which is simpler and more efficient.

### Decision 2: Parallel hash + validate in Pass 1

**Chosen**: Run hash and validate coroutines in parallel, each with its own file descriptor.

**Alternative**: Sequential (hash first, then validate).

**Rationale**: Matches the existing small-file architecture where validate and hash run in parallel via `coro::whenAll`. Both reads hit the same file; the OS page cache ensures disk I/O happens once. Wall time is `max(hash_time, validate_time)` instead of `sum`.

### Decision 3: Separate stream validators vs modifying existing validators

**Chosen**: New `IStreamValidator` implementations alongside existing `IValidator` implementations.

**Alternative**: Modify existing validators to support both buffer and file interfaces.

**Rationale**: Existing validators have thorough test suites. Adding file I/O to them increases complexity and test surface. Separate classes keep the existing code untouched and testable independently. The stream validators are thin wrappers — most reuse the same library calls with a different I/O source.

### Decision 4: Per-format size limits (reject before processing)

**Chosen**: Per-extension maximum file size with sensible defaults; files exceeding the limit are rejected immediately without any processing.

**Alternative A**: Single global threshold for all formats.

**Alternative B**: No size limits — attempt to process everything.

**Rationale**: Different media formats have vastly different valid size ranges. A 5 GB JPEG is certainly not a real photo, but a 5 GB MOV is normal. Per-format limits catch obviously invalid files cheaply (one `stat()` call) and avoid wasting CPU on files that can't be what they claim. Defaults cover 99%+ of real-world files; config file overrides handle special cases without code changes.

### Decision 5: Two-pass read (hash then write) vs temp-file approach

**Chosen**: Two-pass — read for hash+validate, then read again for storage write.

**Alternative**: Write to a temp file first (before hash is known), then compute hash, then rename.

**Rationale**: Temp-file approach requires `tempFileSize` extra disk space per file per root, adds cleanup complexity on failure, and doesn't work well with multi-root storage (need temp space on every root). Two-pass is simpler; the second read is fast from page cache.

### Decision 6: Fallback when no stream validator exists

**Chosen**: Fall back to `Blob` path; if OOM, report error.

**Alternative**: Refuse to process files above threshold without a stream validator.

**Rationale**: Graceful degradation. A new format added without a stream validator shouldn't block large file processing entirely — the `Blob` path might still work for borderline sizes. The error message clearly indicates what happened.

### Decision 7: Streaming threshold as internal constant, not user-configurable

**Chosen**: Fixed 256 MB streaming threshold, not exposed in config or CLI.

**Alternative**: Make it configurable like the per-format size limits.

**Rationale**: The streaming threshold is a memory management implementation detail, not a semantic property of the media. Users care about "what's too big to be a valid JPEG?" (per-format limits), not "at what size does the library switch internal buffer strategies?" (streaming threshold). Fewer knobs = less confusion. The per-format size limits are the user-facing control surface.

## Overhead Analysis

### Small files (below threshold)

**Zero overhead.** The only new code in the hot path is a single `if (fileSize > threshold)` comparison.

### Large files (above threshold)

| Operation | Cost vs current | Notes |
|-----------|----------------|-------|
| Disk reads | ~2× (two passes) | Second pass largely cached |
| Disk writes | Identical | Same bytes to same roots |
| CPU (hash) | Identical | Same SHA256 computation |
| CPU (validate) | Identical | Same library calls |
| Memory | **~100× reduction** | 24 MB vs 2 GB per MOV file |
| Wall time | ~10-30% slower | Extra file open + cached re-read |

The 10-30% wall time increase for large files is an excellent trade-off for 100× memory reduction.
