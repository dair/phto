# 0006 — `imagestore` Batch Import Utility

## Goal

A command-line utility that reads file paths from stdin (one per line) and stores each image/video via `libimager`. Designed for pipelines like:

```bash
find /photos -type f -name '*.jpg' | imagestore
find /media -type f \( -name '*.jpg' -o -name '*.png' -o -name '*.mp4' \) | imagestore --config /etc/imagestore.toml
```

Must handle tens of thousands of paths efficiently: parallel I/O, bounded memory, robust error handling with a persistent error-file that doubles as a skip-list.

## Usage

```
imagestore [OPTIONS]

Options:
  -c, --config PATH    Configuration file (default: ~/.imagestore.toml)
  -e, --errors PATH    Error file: skip paths listed here, append new failures
  -j, --jobs N         Concurrent image processing limit (default: nproc)
  -n, --dry-run        Validate and hash only, do not write to storage or DB
  -v, --verbose        Print progress and per-file status to stderr
  -h, --help           Show usage and exit

Input:
  Reads file paths from stdin, one per line.
  Empty lines and lines starting with '#' are ignored.
  Paths may be absolute or relative to the current working directory.

Exit codes:
  0   All files processed successfully (including duplicates, which are not errors)
  1   Usage error or configuration failure
  2   Some files failed (errors appended to --errors file if given)
```

## Command-line parameters

### `--config` / `-c`

Path to the TOML configuration file. Uses the existing `[[targets]]` format from 0002.

Default: `~/.imagestore.toml` (resolved via `$HOME`). If the default path does not exist and `--config` is not given, exit with error.

### `--errors` / `-e`

Path to the error file. This file is **read-write**:

1. **On startup**: read the file. Every line is a path to **skip** even if it appears on stdin. This allows re-running the same pipeline without retrying known-bad files.
2. **During processing**: when a file fails (unreadable, broken, unsupported format, storage/DB error), append its path to this file. Each path appears at most once (deduplicated against both the initial contents and earlier appends within this run).
3. **Format**: one absolute path per line, no headers, no metadata. Append-only during the run (no rewriting of the file).

If not given, errors are only reported to stderr (with `--verbose`) and in the exit code. No skip-list behavior.

The deduplication is implemented via an in-memory `std::unordered_set<std::string>` loaded from the file at startup. Appends are protected by a mutex (writes are rare — only on errors).

### `--jobs` / `-j`

Maximum number of images being processed concurrently. Each "job" means one file being read from disk + processed through the `addImage` pipeline simultaneously.

Default: `std::thread::hardware_concurrency()` (typically nproc). Capped at a sensible maximum (e.g., 256) to prevent fd exhaustion.

This is **not** the thread pool size (that's controlled by `libimager` internally based on the number of targets). This is the number of files being read and submitted in parallel from the utility's own worker loop.

Purpose: at 10k+ files, sequential read→addImage→read→addImage is I/O-bound on a single core. Parallel reads overlap disk I/O with CPU work (hashing, validation) and storage writes.

### `--dry-run` / `-n`

Process each file through the full pipeline (read, validate, hash) but **do not** write to storage roots or insert into databases. Useful for:

- Verifying that all files in a directory are valid before committing
- Testing the pipeline's throughput without side effects
- Estimating storage needs (could print total bytes and file count)

Implementation: call `addImage` with a `dry_run` flag (see library changes section), or perform the validation + hashing steps outside of `addImage` and skip the write/insert. The simpler approach is to add a dry-run mode to `Imager` itself.

### `--verbose` / `-v`

Print progress to stderr:

- Per-file: `OK <id> <path>`, `SKIP <path> (in error list)`, `DUP <path>`, `ERR <path>: <message>`
- Periodic summary every 1000 files or every 5 seconds (whichever comes first): `[progress] 4832/? processed, 12 errors, 3 duplicates, 47.2 MB/s`

The `?` is because total count is unknown when reading from a pipe. If stdin is a regular file (seekable), the utility could count lines first, but this is optional.

Without `--verbose`, only fatal errors (config failure, can't open error file) go to stderr.

## Architecture

### Main loop: bounded-concurrency reader

```
stdin (paths)
  │
  ├─ reader thread: reads lines, resolves to absolute paths, checks skip-set
  │
  ├─ bounded semaphore (--jobs N)
  │
  ├─ worker threads (from std::async or a local thread pool):
  │   ├─ read file from disk → Blob
  │   ├─ call imager.addImage(blob, filename)
  │   ├─ handle result (OK / DUP / ERR)
  │   └─ release semaphore slot
  │
  └─ main thread joins all, prints summary
```

The reader thread reads stdin line-by-line. For each path:

1. Canonicalize to absolute path (`std::filesystem::absolute`).
2. Check the skip-set (error file contents). If present, skip.
3. Acquire a semaphore slot (blocks if `--jobs` limit reached — backpressure).
4. Launch async work: read file → Blob → `addImage` → handle result.

This keeps at most N files in memory simultaneously, preventing OOM at 10k+ files.

### Concurrency model

The utility does **not** create its own thread pool. It uses `std::async` (or a lightweight task queue) to launch file-read + addImage tasks. The `Imager` internally has its own `ThreadPool` for coroutine dispatch. The utility's concurrency is purely at the "how many files are in-flight" level.

```
imagestore process          libimager internals
─────────────────          ────────────────────
main thread reads stdin
  │
  ├─ async task 1:          ┌─ pool thread: validate
  │   read file → Blob      ├─ pool thread: hash
  │   addImage(blob) ──────►├─ pool thread: write root₁
  │                          ├─ pool thread: write root₂
  │                          └─ pool thread: db insert
  │   ◄── result ───────────
  │
  ├─ async task 2:           (same pattern)
  │   read file → Blob
  │   addImage(blob) ──────►...
  │
  └─ ... up to N concurrent
```

### File reading

For each file:

```cpp
std::filesystem::path path = ...;

// Get file size for pre-allocation
auto fileSize = std::filesystem::file_size(path);

// Allocate Blob, read directly into writable buffer, freeze
imager::Blob blob(fileSize);
std::ifstream in(path, std::ios::binary);
in.read(reinterpret_cast<char*>(blob.writableData()),
        static_cast<std::streamsize>(fileSize));
blob.freeze();

// Extract just the filename for addImage
auto result = imager.addImage(blob, path.filename().string());
```

This uses `Blob(size)` + `writableData()` for zero-copy file reading, exactly as designed in 0003.

### Error file management

```cpp
class ErrorFile {
public:
    /// Load existing entries from file (if it exists). Each line → skip set.
    explicit ErrorFile(const std::filesystem::path& path);

    /// Check if a path should be skipped.
    bool shouldSkip(const std::string& absPath) const;

    /// Record a failed path. Appends to file and adds to in-memory set.
    /// Thread-safe. Deduplicates against both initial load and previous appends.
    void recordError(const std::string& absPath);

    size_t skipCount() const;   // how many paths were skipped
    size_t errorCount() const;  // how many new errors were recorded this run

private:
    std::unordered_set<std::string> m_known;    // loaded + appended
    std::ofstream                   m_out;       // append-mode file handle
    mutable std::mutex              m_mutex;     // protects m_known + m_out
};
```

The file is opened in append mode (`std::ios::app`). Existing contents are loaded into `m_known` at startup. `recordError` checks `m_known` before appending (dedup). The mutex is only taken on error paths, which are rare — no contention on the hot path.

### Result classification

`addImage` returns `AddResult` with an `ErrorCode`. The utility classifies each outcome:

| ErrorCode | Classification | Action |
|-----------|---------------|--------|
| `Ok` | Success | Count it. Verbose: `OK <id> <path>` |
| `DuplicateFile` | Expected | Count it. Verbose: `DUP <path>`. **Not** an error — don't write to error file. |
| `BrokenFile` | File error | Record in error file. Verbose: `ERR <path>: broken` |
| `UnsupportedFormat` | File error | Record in error file. Verbose: `ERR <path>: unsupported format` |
| `StorageError` | System error | Record in error file. Verbose: `ERR <path>: storage error` |
| `DatabaseError` | System error | Record in error file. Verbose: `ERR <path>: database error` |

File I/O errors (can't open, can't read, file disappeared between stat and read) are caught before `addImage` and also recorded in the error file.

`DuplicateFile` is explicitly **not** an error. Re-running `find | imagestore` on the same directory should be idempotent — duplicates are silently skipped (or logged with `--verbose`).

### Exit code

- `0` — all files processed, zero errors (duplicates are OK)
- `1` — usage error, config failure, or error file unreadable
- `2` — at least one file failed (partial success)

### Summary output

Always printed to stderr at the end (even without `--verbose`):

```
12847 processed, 12691 added, 142 duplicates, 14 errors, 0 skipped — 23.4s (548 files/s, 2.7 GB total)
```

With `--dry-run`:

```
12847 processed, 12691 valid, 142 would-be-duplicates, 14 errors — 8.1s (dry run, no writes)
```

## Library changes needed

### Dry-run support in `Imager`

The utility needs a way to validate + hash without writing. Two options:

**Option A — public `validateAndHash` method**: add a new method to `Imager` that does steps 1–4 (extension check, validate, hash, duplicate check) and returns the result without writing. The utility calls this in `--dry-run` mode instead of `addImage`.

```cpp
/// Validate format and compute SHA256 without writing to storage or DB.
/// Returns the hash ID on success, or error if validation fails.
AddResult validateOnly(const Blob& blob, const std::string& filename);
```

**Option B — flag on `addImage`**: add an optional parameter or overload.

Option A is cleaner — it doesn't pollute the main `addImage` path with conditionals. The utility calls `validateOnly` in dry-run mode and `addImage` otherwise.

### No other library changes

The utility is a pure consumer of `libimager`'s public API (`Imager.h`, `Types.h`, `Blob`). No internal headers needed.

## Implementation outline for `main.cpp`

```
1. Parse command-line arguments
2. Resolve config path (--config or ~/.imagestore.toml)
3. Load config via config::loadConfig()
4. Create Imager instance
5. If --errors given, create ErrorFile (loads skip set)
6. Create bounded semaphore (--jobs)
7. Create atomic counters: added, duplicates, errors, skipped, total_bytes
8. Read stdin line-by-line:
   a. Trim whitespace, skip empty lines and '#' comments
   b. Resolve to absolute path
   c. If ErrorFile and shouldSkip(path) → increment skipped, continue
   d. Acquire semaphore slot
   e. Launch std::async:
      i.   Stat file (get size, check exists)
      ii.  Read into Blob(size) + writableData() + freeze()
      iii. Call addImage(blob, filename) or validateOnly(blob, filename)
      iv.  Classify result, update counters
      v.   If error and ErrorFile → recordError(path)
      vi.  If --verbose → print status line to stderr
      vii. Release semaphore slot
   f. Store the future in a collection
9. Wait for all futures to complete
10. Print summary to stderr
11. Exit with appropriate code
```

### Memory management at scale

With `--jobs 32` and average 5 MB files, peak memory from Blobs is ~160 MB. The bounded semaphore ensures this doesn't grow unboundedly. Once `addImage` returns, the Blob is released (unless the caller holds the last reference).

The futures collection grows to `total_files` entries, but each completed future is small (just the error code). For 100k files, this is ~1–2 MB. Acceptable.

Alternatively, use a fixed-size ring of futures and periodically collect completed ones to keep memory flat. This is an optimization — the simple "collect all at the end" approach works for the expected scale.

### Thread safety

- `Imager` is thread-safe (internal `writeMutex` serializes writes, reads use `shared_lock`)
- `ErrorFile` is internally synchronized (mutex on error recording)
- Atomic counters for statistics
- stderr writes from `--verbose` are interleaved at the line level (acceptable; use `\n`-terminated writes which are atomic on POSIX for short lines)

```bash

$ find ~/photos -name '*.jpg' | imagestore -e ~/import-errors.txt

# Check what failed
$ cat ~/import-errors.txt
/home/user/photos/2019/broken1.jpg
/home/user/photos/2020/corrupt.jpg
... (14 lines)

# Second run — same find, skips known errors and already-added files (duplicates)
```
