# Plan 0023 — Content Transcoding & Format Negotiation

## 1. Requirement

The `GET /items/{id}/content` endpoint (Plan [0022](0022.SERVER.md) §6.2) must
deliver media in a format the requesting **client can play natively**, not just
the raw stored bytes. A NEF or HEIC photo, or a MOV in an exotic codec, is
useless to a browser/phone; the server must hand back something it can render.

Model: the **client sends an ordered list of acceptable formats** (separately for
images and videos). The server returns the item in the **first** listed format
that:

1. the item is **already in** → serve the original (zero work, via
   `getImagePath` streaming from 0022 §8), else
2. the server **can produce** → transcode once, **cache** the result, serve from
   cache thereafter.

Re-encoded derivatives (the obvious case being **NEF → JPEG**; for video, the
source codec → an **AVPlayer/ExoPlayer-friendly MP4**) are cached so the
expensive conversion happens at most once per (item, format, params).

> **Status:** Proposal — design only. Extends 0022; no code written here.

---

## 2. Guiding principle: many source formats in, a *tiny* target set out

Sources are whatever the validators accept (JPEG, PNG, HEIC, NEF, MOV/MP4 — see
CLAUDE.md). **Targets are deliberately minimal** — only formats with native,
no-plugin playback across **Web browsers, iOS (AVPlayer), and Android
(MediaPlayer / ExoPlayer / Jetpack Media3)**. We will *install whatever encoders
give the best quality* (LibRaw, libwebp, libavif, ffmpeg+x264, …) but the menu of
things we emit stays small.

### 2.1 Image targets

| Target | MIME | Web | iOS | Android | Role |
|---|---|---|---|---|---|
| **JPEG** | `image/jpeg` | all | all | all | **baseline — always producible, default fallback** |
| PNG | `image/png` | all | all | all | lossless / alpha when the source has it |
| WebP | `image/webp` | modern | 14+ | all | efficiency opt-in |
| AVIF | `image/avif` | recent | 16+ | 12+ | best compression, heaviest encode, opt-in |

### 2.2 Video targets

| Target | Container / codec | Web | iOS AVPlayer | Android | Role |
|---|---|---|---|---|---|
| **MP4 H.264 + AAC** | `video/mp4` (`avc1`/`mp4a`) | all | yes | all | **baseline — universal, default fallback** |
| HLS (H.264+AAC, fMP4) | `application/vnd.apple.mpegurl` | Safari native / hls.js | native | ExoPlayer/Media3 | streaming: seek + adaptive (Phase 2, §6.4) |
| MP4 HEVC + AAC | `video/mp4` (`hvc1`) | partial | yes | most | efficiency opt-in; **not** universal on web |

**Baseline guarantee.** *Every* image can be produced as **JPEG**; *every* video
as **H.264/AAC MP4**. So as long as a client's list ends with the baseline,
negotiation never fails. Notably excluded as targets because they are **not**
universally native: HEIC (no web), WebM/VP9 and AV1-in-WebM (no AVPlayer),
ProRes/raw. We decode them as sources, we never emit them.

## 3. Negotiation model

A single item is either an image or a video (decided by stored `ext`), so the
relevant ordered list is unambiguous. Three inputs, in precedence order:

1. **Query override** `?format=jpeg` (or `?format=mp4`) — explicit, wins.
2. **`Accept` header** — standard content negotiation, ordered, honoring `q=`
   weights (e.g. `Accept: image/avif, image/webp;q=0.9, image/jpeg;q=0.8`).
3. **Stored client profile** — a per-user (optionally per-device) default with
   **separate** ordered lists for images and videos. Used when `Accept` is absent
   or `*/*`. This is the "client sets an ordered list" mechanism in its durable
   form; the `Accept` header is its per-request override.

```jsonc
// client profile (stored, see §7.3)
{
  "imageFormats": ["image/avif", "image/webp", "image/jpeg"],
  "videoFormats": ["application/vnd.apple.mpegurl", "video/mp4"]
}
```

### 3.1 Resolution algorithm

```
kind     = image | video        (from stored ext)
wanted   = override ? [override] : (Accept!=*/* ? parseAccept() : profile[kind])
source   = mimeOf(stored ext)

for fmt in wanted:
    if fmt == source            -> stream original (getImagePath)        # case 1
    if canProduce(source, fmt)  -> serveDerivative(id, fmt, params)      # case 2
# nothing matched:
if wanted contains no producible target -> 406 Not Acceptable
                                            + Link to GET /items/{id}/formats
```

Clients are documented to always include the baseline (`image/jpeg` /
`video/mp4`) last so they never see a 406.

### 3.2 Derivative parameters (beyond format)

Format is the primary axis; the cache key (§7.2) also carries optional sizing so
the same machinery serves previews/mobile renditions without a redesign:

- Images: `q` (quality), `w`/`h` or `max` (longest edge, for thumbnails/previews).
- Video: `maxHeight` (e.g. 1080/720/480), target `crf`/bitrate.

Defaults come from `[transcode]` config (§8); requests may narrow within
server-enforced bounds. Unbounded/oversized requests are clamped, not honored
verbatim (DoS guard, §10).

## 4. Capability advertisement

So clients can build sensible lists, the server advertises what it can do:

| Method | Path | Returns |
|---|---|---|
| GET | `/capabilities` | global: image targets, video targets, whether HLS/video transcode is enabled |
| GET | `/items/{id}/formats` | for this item: its source format + the concrete list of producible targets |

`canProduce(source, target)` is a static matrix (NEF→JPEG/PNG/WebP/AVIF; HEIC→…;
any-video→MP4-H264; …) gated by which encoders are actually installed and whether
video transcoding is enabled in config.

## 5. Image transcoding pipeline

In-process (image conversions are fast and the codecs are permissively licensed —
LGPL/BSD — so they can be linked directly).

- **Decode** by source: NEF → **LibRaw**; HEIC → **libheif**; JPEG → libjpeg-turbo;
  PNG → libpng. (All already present as validators or trivially added.)
- **Encode** by target: JPEG → libjpeg-turbo; PNG → libpng; WebP → **libwebp**;
  AVIF → **libavif** (or libheif+AOM). Each is added via `find_package`/
  `pkg_check_modules` per project convention; encoders we don't ship simply drop
  out of the capability matrix.
- Intermediate is a decoded RGB(A) surface; apply optional resize (high-quality
  filter) before encode.
- EXIF/orientation: bake orientation into pixels on transcode (clients shouldn't
  need to re-rotate); strip GPS/other EXIF by default for privacy, configurable.

NEF→JPEG and HEIC→JPEG are the headline conversions and are fully covered by this
path with no external process.

## 6. Video transcoding pipeline

### 6.1 Decision: out-of-process `ffmpeg`, not linked encoders

Video decode+encode runs by **spawning a managed `ffmpeg` subprocess**, not by
linking encoders into the daemon. Rationale:

- **Licensing.** The universal H.264 encoder is **x264 (GPL)**. Linking it would
  impose GPL on `imagerd`. A separate `ffmpeg` executable is an independent
  process → no link-time license entanglement with the daemon.
- **Robustness.** A malformed file that crashes/hangs the encoder kills a
  subprocess, not the server. Trivially `timeout`/`kill`-able.
- **Isolation & limits.** The subprocess can be sandboxed and resource-capped
  (nice, cgroup/ulimit, wall-clock timeout) independently.
- **Proven.** This is exactly how Jellyfin/Plex/Nextcloud do server transcoding.

The existing linked `libav*` (MOV validation) stays **decode/validate-only**; it
is not extended to encode. `ffmpeg` path + capabilities are configured in
`[transcode]`; if disabled or absent, video targets drop from the matrix and the
server serves the original (or 406).

### 6.2 Baseline transcode (Phase 1)

Whole-file decode → re-encode to **MP4 H.264 (x264) + AAC**, faststart
(`-movflags +faststart`) so the `moov` atom is up front for progressive play.
Roughly:

```
ffmpeg -i <source> -c:v libx264 -preset <cfg> -crf <cfg> \
       -vf scale='min(<maxH>,ih)...' -c:a aac -b:a 160k \
       -movflags +faststart -f mp4 <cache_tmp>
```

The result is written to a cache temp path, then atomically renamed into the
derivative cache (§7). Served with **HTTP Range** support (§9) — and, because the
`moov` atom is up front, that Range support *is* native time-seek (§6.5).

### 6.3 Synchronous-with-cache, single-flight, and the in-progress contract

A full movie can take minutes; we do **not** block one HTTP request open for the
whole job naïvely, and the client must be able to **tell that transcoding has
started and a delay is expected**. Behavior:

- **Cache hit** → stream immediately (with Range/206).
- **Cache miss** → register the job in a **single-flight** map (§7.4) so
  concurrent requests for the same derivative share one `ffmpeg` run, then return
  the **in-progress contract** below rather than holding the socket. Small/fast
  conversions (images, short clips) finish inline and stream the result directly.
- A bounded worker pool (`[transcode].max_concurrent`) runs jobs; excess queue.

**In-progress contract (the "expect a delay" signal).** When a request triggers
or joins a running transcode:

```
HTTP/1.1 202 Accepted
Location: /items/{id}/content?format=mp4        # re-request the same URL
Retry-After: 3                                   # suggested poll interval (s)
X-Transcode-Status: queued | running
X-Transcode-Progress: 37                         # percent, when known
X-Transcode-Job: <jobId>

{ "status":"running", "jobId":"...", "progress":37,
  "etaSeconds":42, "format":"video/mp4" }
```

`ffmpeg -progress` is parsed to drive `progress`/`etaSeconds`. The client polls
the same content URL (or the dedicated job endpoint, §9) until it gets `200`/`206`
with the bytes. `HEAD /items/{id}/content` returns the same `202`-vs-ready status
cheaply, without downloading. On failure → `502`/`504` with
`X-Transcode-Status: failed` and an error envelope. This gives players a clear,
pollable "still working, ~Ns left" state instead of a silent stall.

### 6.4 Time-offset start (`?start=` — instant play / seek before full transcode)

Range seek (§6.5) only works once a derivative is **complete**. To play or seek
into a long video that is **not yet (fully) transcoded**, the content endpoint
accepts `?start=<seconds>` (float, accurate seek):

```
ffmpeg -ss <start> -i <source> -c:v libx264 -preset <cfg> -crf <cfg> \
       -c:a aac -movflags +faststart+frag_keyframe+empty_moov ... -f mp4 -
```

- The server transcodes **from the keyframe at/just before `start`** and streams
  the result (chunked) as ffmpeg produces it — first bytes in seconds, not after
  the whole movie. The same in-progress `202` contract (§6.3) applies if even the
  startup can't begin immediately (pool saturated).
- **Timeline semantics:** the `?start=` stream's PTS is **rebased to 0**; the
  client requested `start=T`, so it offsets its scrubber by `T`. Documented in the
  API guide so AVPlayer/ExoPlayer integrations map the timeline correctly.
- **Not cached** as a canonical derivative (arbitrary offsets would explode the
  cache). It is an ephemeral low-latency bridge. **Optionally**, a `?start=`
  request also kicks off the **full-file** transcode in the background, so once
  that lands in cache the client can switch to the cached MP4 and get full
  Range-based seeking. (Recommended; configurable.)

This is the interim seek mechanism; segment-native seeking is the HLS phase below.

### 6.5 Native time-seek via Range (completed derivatives)

For any **completed** MP4 derivative (or an original already in a playable
format), seeking needs **no special API**: `+faststart` puts the `moov` sample
tables first, so AVPlayer / ExoPlayer / Media3 read the time↔byte index, map a
seek to time T to the nearest sync-sample byte offset, and issue a standard
**HTTP Range** request (`206 Partial Content`, §9). Range support is therefore a
hard requirement for every content response, and faststart is mandatory on every
video derivative. This is the primary, zero-cost seek path; §6.4 covers only the
not-yet-cached gap.

### 6.6 HLS on-the-fly (Phase 2 — deferred)

For real seeking/adaptive on AVPlayer/ExoPlayer, add segment-on-demand HLS:
serve a generated `.m3u8` playlist and transcode `.ts`/fMP4 segments lazily as the
player requests them, caching each segment. This is the proper streaming answer
but is a sizable subsystem; Phase 1 ships progressive MP4 + Range (§6.5) +
`?start=` (§6.4), which covers seek on cached clips and instant play/seek into
uncached ones. HLS lands later behind the same negotiation
(`application/vnd.apple.mpegurl` target) for fully segment-native seeking and
adaptive bitrate.

## 7. Derivative cache

### 7.1 Stance: regenerable, **not** redundant

Derivatives are reproducible from originals, so — unlike the multi-root image
store — the cache is a **single, evictable** root (`[cache].root`). Losing it
costs CPU, not data. It is never part of the all-or-nothing multi-target writes.

### 7.2 Layout & key

Sharded like the image store:

```
<cache.root>/<id[0:2]>/<id>.<variant>.<ext>
# variant is a deterministic descriptor of format + params, e.g.
#   jpg-q85-max2048      heic source → JPEG, q85, longest edge 2048
#   mp4-h264-aac-720p    any video   → H.264/AAC MP4, max height 720
```

The variant string is canonicalized (sorted params) so equivalent requests map to
one entry. Full key = `(source_id, variant)`.

### 7.3 Metadata & eviction

A small SQLite index DB (own file, `database/`-style) tracks entries for LRU:

```sql
CREATE TABLE derivative (
  source_id   TEXT NOT NULL,
  variant     TEXT NOT NULL,
  ext         TEXT NOT NULL,
  bytes       INTEGER NOT NULL,
  created_at  INTEGER NOT NULL,
  accessed_at INTEGER NOT NULL,      -- bumped on every hit
  PRIMARY KEY (source_id, variant)
);
```

Eviction: when total `bytes` exceeds `[cache].max_bytes`, delete least-recently-
accessed entries (file + row) until under a low-water mark. Source deletion
(`DELETE /items/{id}`) cascades: purge all `derivative` rows + files for that id.

The **client profile** (§3) also persists; it belongs to a user, so it lives as a
`client_profile` table in the **auth** DB (0022 §5.1), set via
`PUT /auth/profile`, not in this cache DB.

### 7.4 Single-flight (de-dupe concurrent generation)

An in-process `map<key, shared state>` guarded by a mutex+condvar: the first
requester for a missing key creates the entry and runs the job; concurrent
requesters wait on the condvar and then read the finished cache file. Prevents N
identical `ffmpeg` runs for a popular uncached video. (In-memory is sufficient for
a single-node intranet daemon.)

```toml
[transcode]
enable_video    = true
ffmpeg_path     = "/usr/bin/ffmpeg"     # required iff video enabled

# video defaults

video_max_height = 1080
video_audio_kbps = 160

root      = "/var/cache/phto/derivatives"
max_bytes = 50_000_000_000               # 50 GB; LRU eviction above this
```

Mapped into `config::AppConfig` as `TranscodeConfig` + `CacheConfig` (extends
0022 §11). Validated at boot; if `enable_video` but `ffmpeg_path` is missing/non-
executable, the daemon logs a warning and disables video targets (does not abort).

## 9. API changes (relative to 0022)

`GET /items/{id}/content` gains negotiation and these behaviors:

- Reads `?format` / `Accept` / profile (§3); resolves per §3.1.
- **Original-format hit:** stream from `getImagePath` (unchanged 0022 path) with
  `ETag:"{id}"`, `Cache-Control: immutable`.
- **Derivative:** stream the cache file; `ETag:"{id}.{variant}"`,
  `Cache-Control: immutable` (derivatives are pure functions of id+variant);
  `Vary: Accept`.
- **HTTP Range / `206 Partial Content`** supported for *all* content responses
  (originals and derivatives) — this is the native AVPlayer/ExoPlayer time-seek
  path for completed clips (§6.5) and also serves large downloads. (Retro-improves
  the plain download in 0022 §6.2.)
- **`?start=<seconds>`** (§6.4) — instant play / seek into a video that isn't fully
  transcoded yet; streams from the requested time-mark, PTS rebased to 0.
- **In-progress generation (§6.3):** `202 Accepted` + `Retry-After` + `Location`
  + `X-Transcode-Status`/`X-Transcode-Progress`/`X-Transcode-Job` headers and a
  JSON `{status, jobId, progress, etaSeconds}` body, so the client knows
  transcoding has started and roughly how long it will take. The client polls the
  same URL until `200`/`206`. `HEAD /items/{id}/content` reports ready-vs-`202`
  cheaply.

New endpoints:
- `GET /capabilities`, `GET /items/{id}/formats` (§4)
- `GET`/`PUT /auth/profile` (client format profile, §7.3)
- `GET /transcode/jobs/{jobId}` — poll a running job's
  `{status, progress, etaSeconds}` without re-requesting content (auth required;
  a job is visible only to the user who triggered it).

## 10. Concurrency, resources, security

- **Bounded transcode pool** (`max_concurrent`) + queue; per-job wall-clock
  **timeout** → kill the subprocess and return `504`/`502`. Caps CPU blowup.
- **DoS surface.** Transcoding is the most expensive operation in the system.
  Mitigations: requests require auth (0022); per-user concurrent-job limit;
  clamp requested dimensions/bitrate to configured bounds; single-flight prevents
  amplification; cache makes repeats cheap.
- **Subprocess safety.** `ffmpeg` is invoked with an **argv vector (never a
  shell string)** — no shell, no injection. Inputs are server-owned cache/store
  paths derived from a validated 64-hex id, never client strings. Run with reduced
  privileges; sandbox (seccomp/cgroup) where available.
- **Cache integrity.** Write to a temp file, `fsync`, atomic rename into place —
  no partial/corrupt derivative is ever served; a crashed job leaves only a temp
  file (swept on startup).
- **Metadata stripping** on transcode (GPS/EXIF) by default (§5), configurable.

- **`transcode/`** (namespace `transcode::`): `ImageTranscoder` (in-process),

  profile (§7.3).

## 14. Implementation steps (in order)

1. **Config + matrix.** `[transcode]`/`[cache]` parsing; static `FormatMatrix` +
   `Mime` (ext↔MIME, source→target capability); `/capabilities` +
   `/items/{id}/formats` endpoints.
2. **DerivativeCache.** Sharded filesystem layout, SQLite index, atomic write,
   LRU eviction, cascade purge, single-flight. Unit tests first.
3. **ImageTranscoder.** NEF→JPEG, HEIC→JPEG, +PNG/WebP/AVIF as encoders allow;
   resize + orientation + metadata strip. Tests.
4. **Negotiation in `/content`.** Override/Accept/profile precedence;
   original-format short-circuit; image derivatives via cache; **Range/206** for
   all responses (native time-seek on completed clips, §6.5).
5. **Client profile.** `auth` store columns + `GET/PUT /auth/profile`.
6. **VideoTranscoder + JobRegistry.** ffmpeg subprocess (argv, timeout, kill),
   MP4 H.264/AAC faststart, bounded pool + queue; single-flight job registry with
   progress/eta from `ffmpeg -progress`; the in-progress **`202` contract**
   (headers + JSON), `HEAD`, and `GET /transcode/jobs/{jobId}`. Tests with a tiny
   fixture.
7. **`?start=` time-offset.** Accurate-seek streaming from a time-mark (PTS
   rebased to 0) for instant play/seek into uncached video; optional background
   full-file transcode so the cached MP4 + Range seek takes over once ready.
8. **e2e + docs.** Extend `test_api.sh.in` (incl. Range/`?start=`/job-poll);
   write the user-facing format + seek/timeline + ops guide; `ctest --preset
   default` green.
9. **(Phase 2, separate)** HLS on-the-fly segmenting (§6.6).
